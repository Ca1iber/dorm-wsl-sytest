Topic 100378

VCAT, VCAT? - (VeCtor ATtachment)

The VCAT command defines attachments to a label (pattern). Currently the following attachment types are supported:

  • Attachments defining x-mode areas for a pattern
  • Attachments identifying a scan instance
  • Attachments defining a synchronization point

X-mode area definitions

In the DUT view, the Pattern Debug tool can split one tester vector into several DUT oriented X-vectors (normal x-mode), or it can combine several tester vectors into one X-vector (fractional x-mode). The range of tester vectors to which a certain x-mode is applied is called an x-mode area. Different pins can have different x-modes, and the x-mode can change in the course of the pattern.

The view definition specifies the x-mode areas for every pin. The definition associates a pair of x-mode and selector with the first tester vector to which the pair is to be applied; the selector is needed to distinguish different X-vectors that are represented by the same state character. The length of the area is determined by the next tester vector that is associated with a different x-mode/selector pair.

The x-mode/selector pairs must be defined in the base wavetable that is attached to the pattern. The pattern must have been defined with APTS or SQLB.

Identification of scan instances

STIL Reader and the ASCII Interface use the VCAT command to identify scan test instances to SmarTest.

Definition of synchronization points

The VCAT command is used by the Pattern Debug tool to define synchronization markers at the X-vector level for simulation patterns in a protocol-aware multi-port setup. These markers are used to synchronize a protocol pattern with the respective simulation pattern.

VCAT

VCAT {"label_name"}, {(port)}, {"attachment_type"}, {#spec(data)}

VCAT?

VCAT? {"label_name"|ALL}, {(port)}, {"attachment_type"}

returns

VCAT {"label_name"}, {(port)}, {"attachment_type"}, {#spec(data)}

Parameters

label_name

The label must be of type MAIN or SVEC.

ALL

In the query, you can specify ALL provided that you also specify @@ for the port parameter. The query will then return the data for all labels of all ports.

port

Specifies the port to which the label belongs. In the query, you can specify @@ in combination with ALL in the first parameter to retrieve the DUT views for all labels of all ports.

attachment_type

Defines the attachment type. Possible values are:

  • AreaPatternAttachment, which defines the DUT view of a label for the Pattern Debug tool.
  • ScanInstanceAttachment, which describes a scan test instance generated by the STIL Reader or the ASCII Interface.
  • MarkerPatternAttachment, defines that synchronization points used with protocols will be specified and add to the sequencer label.

#spec(data)

 

The general format of the parameter is as follows:

#Nn1n2n...nNdata_stream

where the decimal digit N defines the number of the decimal digits ni (1 ≤ i ≤ N) which in their turn specify the length of data_stream in bytes.

The format of the data stream depends on the attachment type:

AreaPatternAttachment consists of one or more statements in the following format:

logical_vector_nr, list_of_pins_with_associated_formats

In the query, the individual statements are separated by linefeed characters for better readability. The list of pins with associated formats consists of one or more triples

(pinlist), x_mode, selector;

Note that fractional x-modes are coded by negative integers.

ScanInstanceAttachment identifies one or more scan instance definitions in the following format:

first_vector, x_vector, test_type, length, "scan_test_name", "struct_block_name";

where:

first_vector

The logical tester vector within which the scan test instance begins, counted from 0.

X_vector

The X-vector within first_vector at which the scan instance begins, counted from 0.

test_type

scan tests: test_type = 1

functional test: test_type = 0

length

Length of the scan instance, that is, the number of X-vectors. If the command was generated by the ASCII Interface, length equals the template length.

scan_test_name

Name of the scan instance. If the command was generated by the ASCII Interface, the name has the format

<template_name>_<instance_number>

struct_block_name

Name of the active structure block, empty for the default block. The structure block configures the scan chain.

MarkerPatternAttachment defines one or more synchronization markers for a protocol pattern in the following format:

tester_vector, sync_point_name, x_vector, pin_name

where:

tester_vector

The logical tester vector within which the synchronization point is located, counted from 0.

sync_point_name

The name of the synchronization point. To activate the synchronization point, this name must be specified with the setSynchronization() member function of the SYNCHRONIZED_TEST API. See also Protocol wrapper API.

X_vector

The X-vector within tester_vector to which the synchronization marker is assigned.

pin_name

The pin on which the marker is (to be) defined. This information is required if the pins of the specified port (port parameter) are assigned different x-modes in the STATEMAP section of their base wavetable.

Application

  • Pattern Debug tool
  • SCAN_TEST_RESULT test method API
  • Protocol-aware tests

Examples

Example 1

> vcat? "example",(@),"AreaPatternAttachment"
< VCAT "example", (@), "AreaPatternAttachment", #31190,(CP,I1,O1),1,std;
 1,(CP,I1,O1),-3,slow;
 4,(CP,I1,O1),2,fast;
 6,(CP,I1,O1),-3,slow;
 9,(CP,I1,O1),std,1;

The pattern of the example comprises 9 vectors (0 through 8). The last line refers to a virtual vector 9 which is needed for internal reasons. This vector need not be specified in the command, it is added internally.

Example 2

> VCAT "scan_test",(@),"ScanInstanceAttachment", #2303,0,1,24,"chain_pattern 0","";

This example identifies a scan instance in the scan_test pattern, which is associated with the default port @. The length of the data stream is 30 bytes. The scan instance starts at the first X-vector of the fourth tester vector, its length is 24 X-vectors, the name of the scan test instance is chain_pattern 0, and the default scan structure block is used.

Example 3

> VCAT? "myMainLabel", (myPort), "MarkerPatternAttachment"
< VCAT "myMainLabel", (myPort), "MarkerPatternAttachment", #250
 38, mySyncPoint,2,Pin1;
 71, mySecondSyncPoint,1,Pin1;

In this example, VCAT has attached two synchronization markers to pin Pin1 of the sequencer label myMainLabel at port myPort.

The two synchronization markers are mySyncPoint which is attached to the tester vector with the logical vector number 38 and mySecondSyncPoint which is attached to the vector with the logical vector number 71.

Synchronization takes account of place on the X-vector level. Therefore the specification of a marker contains an offset in X-vectors. If an x4-mode in assumed for the above example, the actual positions of the two markers in terms of X-vectors would be 38*4+2 = 154 and 71*4+1=285, respectively.

As the modification of the pattern is restricted to whole tester vectors the X-vector offset within the marker specification is fixed, but the tester vector offset will be updated if the pattern is modified.
