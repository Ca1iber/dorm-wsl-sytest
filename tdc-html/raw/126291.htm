Protocol wrapper API

Generates a protocol wrapper class that derives from the API class SYNCHRONIZED_TEST with the name given by the user.

It creates methods based on the protocol's transactions that can be used in the test methods.

All public methods of the SYNCHRONIZED_TEST API are still accessible through the generated wrapper.

However, the user generated wrapper class also offers additional public methods. Only these public methods are described here.

Note The term <protocol-name> will be replaced with the wrapper class name given by the user.

<protocol-name>_SYNC_TEST(const STRING& port);
<protocol-name>_SYNC_TEST(const STRING& port, const STRING& label, const STRING &wavetable, const STRING& name);

Creates a synchronized test object associated with given port.
If no name is provided, the name will automatically be generated
			from the current test suite name, the provided port and the multi-port burst label.
If no wavetable is provided, it will be specified through the
			primary specification of timing/wavetable at the time when the synchronized test object is
			constructed.
If no multi-port burst label is provided, it will be specified
			through the sequencer start label set at the time when the synchronized test object is
			constructed.
The synchronized test's protocol pattern will be generated based on the provided
				wavetable and associate it with the given multi-port burst
				label. When the according sequencer program is generated, it is hooked into
			that multi-port burst label and thus can be executed as part of a functional test running on that
			label. 
The actual test definition will be cached beyond the execution of a single test method
			so that subsequent identical definitions using the same name and same sequence of transactions
			will not require modifications of the resulting pattern.
Note If the same name is used sequentially for different
			synchronized tests for example, in different test suites) the previous definition will be
			overwritten.
Note It is not allowed to specify several protocol test objects with
			identical name existing concurrently!

Specifies the delay in cycles.

									
						

					
Waits the given number of user cycles by repeating the idle sequence specified by the
				user.
The delay cycles are applied after any synchronization to another port and to any
				delay time (if set) by adding additional idle vector repeats that cover at least the given
				number of cycles.
Note that this function creates a new transaction sequence unless the
				current transaction sequence is still
			empty.

beginSiteAccess()
siteAction beginSiteAccess();
There
				is no parameter associated with this function.
Marks the begin of a block of site-specific
				wrapper operations within a site loop (FOR_EACH_SITE block). Any wrapper
				command enclosed in this block is automatically site-specific. Thus site-specific assignments to
				transaction parameters are allowed. The site specific block has to be closed using the
					endSiteAccess() function.

		
endSiteAccess()
siteAction endSiteAccess();
There
				is no parameter associated with this function.
Marks the end of a block of site-specific
				wrapper operations within a site loop (FOR_EACH_SITE block). Any wrapper
				command enclosed in this block is automatically site-specific. Thus site-specific assignments to
				transaction parameters are allowed. The start of the site specific block has to be marked by
					beginSiteAccess().

		
setVolatile()
void setVolatile(boolean isVolatile);
This
				function determines whether the transactions of the following transaction sequences are volatile
				or not. Transactions that are set as volatile use an optimized caching mechanism. This can
				shorten the test time if the values of the transaction parameters change very often between
				executions.
The function must be called immediately after creating the test object or
				immediately after an transaction. It cannot be called immediately after any other member
				function. See also the example below.

Examples
Example 1
The following code excerpt illustrates how using a customized
				protocol wrapper can ease test method
			programming.
//line without using wrapper
myProtocolTest.transaction("write").set("phyaddr",17).set("regaddr",12),set("data",0xD431);

//same call but using customized wrapper
myProtocolTest.write(17,12,0xD431);

		
Example 2
The following example illustrates the use of the
					setVolatile() function when it is not called immediately after creation of
				the test object. 
Suppose that you want to continue the first example with another
					write() transaction, and that this transaction is to be volatile and delayed
				by 1 μs. This must be coded as
				follows:
myProtocolTest.write(17,12,0xD431);
myProtocolTest.setVolatile(true);
myProtocolTest.waitTime(0.000001);
myProtocolTest.write(32,15,0xFF01);
Note
				in particular that the requirements for calling setVolatile() are satisfied
				because it is called immediately after a transaction, so that the current transaction sequence
				is not empty at the call. waitTime() will then create a new transaction
				sequence, and the transactions of this sequence will be volatile, as desired.
Note If you call setVolatile() immediately
					afterwaitTime(), execution of the test method will be terminated with
				an error. The reason for this is that after the waitTime() call, there will
				always be an open transaction sequence, but this sequence will also always be empty, and
					setVolatile() cannot be executed when the current transaction sequence is
				empty.
