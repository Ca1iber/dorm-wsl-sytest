Topic 69309

GPIB communication flow for Delta Design RFS handlers

This section describes the GPIB communication between the driver and the handler.

The table below shows the communication between the driver and the handler. The actions and messages are listed in sequential order.

See Conventions for GPIB communication for descriptions of the syntax.

GPIB communication flow for Delta Design RFS handlers

Message from driver

Message from handler

Comments

init: <id request> <initialization> <configuration>

id request:

identify?

 

Asks for handler ID.

 

"string"

Handler returns ID, for example

TRFS 6 V3.0g.

which?

 

Asks for handler name.

 

"string"

Handler returns name.

initialization:

conehdnum?

 

Asks handler how many sites it has.

 

n

Handler returns number of site.

systemmode 1

 

Activates normal handling mode.

testermode 1

 

Activates tester binning mode.

srqmask 63

 

Sets SRQ mask to report populated sites, jams and GPIB errors.

configuration: <temperature setup> <verification setup>

Sent at startup and after each driver reconfiguration at runtime

temperature setup:

Depending on the configuration parameter temp_control, one of the following communication flows applies:

Communication flow when temp_control is set to manual

No commands are sent

Communication flow when temp_control is set to ambient

testtemp atambient

 

Sets handler to ambient mode.

Communication flow when temp_control is set to active

The following commands are sent to the handler for each chamber, where chamber can be either be storage, testsite, exit, pickandplace, or all (temperature unit according to temp_equipment_unit):

chamber setpoint n

 

Sets setpoint to given temperature.

chamber lowerguardband n

 

Sets lower guardband temperature.

chamber upperguardband n

 

Sets upper guardband temperature.

chamber heat n

 

Enables (1) or disables (0) heater.

chamber cool n

 

Enables (1) or disables (0) cooler.

 

 

The following commands are sent to the handler once:

soaktime n

 

Sets soaktime in seconds.

testtemp atsetpoint

 

Tests devices at setpoint.

tempcontrol enable

 

Activates temperature control.

verification setup:

verifytest n

 

Activates bin verification (1), if configured with verify_bin_data (set to yes).

Deactivates bin verification (0), if configured with verify_bin_data (set to no).

Note: This command is not sent if verify_bin_data is not configured.

wait for devices: [<SRQ>][<poll>][<status request>]

The driver will either wait for an SRQ or poll for the current site population. If an SRQ was received, polling is still done afterwards in cases where:

testing is done on more than 4 sites, or

not all sites that are active, based on configuration parameter handler_site_mask, seem to be populated.

This command is repeated until there is a device to test. The driver queries the status regularly if no devices are detected.

SRQ:

 

SRQ

Handler sends test start SRQ.

poll (1-4 sites):

srqbyte?

 

Driver asks for current SRQ status.

 

n

Handler returns SRQ status.

poll (more than 4 sites):

testpartsready?

 

Driver asks for current site population.

 

n

Handler returns bit-coded site population.

bin or reprobe devices:

 

 

For all sites, if verify_bin_data is not given in configuration:

sbinbin|

 

Driver sends bin information, or

sreprobe

 

Driver sends reprobe request.

 

 

If verify_bin_data is given in the configuration:

testresults bin,bin...

 

Driver sends bin and reprobe data.

 

 

Only if verification mode is active:

querybins?

 

Driver asks handler for received bin and reprobe information.

 

bin,bin...

Handler sends bin data back to driver.

releaseparts

 

Driver acknowledges correct binning data (if correct), or starts sending testresults from the beginning (max. repeat count: verify_retry_count).

stop handler:

status?

 

Asks handler for current status.

 

n

Handler returns bit-coded status information.

stop

 

Stops handler, only if received status was started.

status?

 

Asks handler for status again.

 

n

Handler returns bit-coded status information (should now be stopped).

start handler:

status?

 

Asks handler for current status.

 

n

Handler returns bit-coded status information.

 

 

Note: The handler cannot be be started by using a GPIB command, the status query is repeated until the handler is started manually.

status request:

status?

 

Asks handler for current status.

 

n

Handler returns bit-coded status information.
