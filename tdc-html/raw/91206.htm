How to prevent the data queue from running empty

The data queues can run empty when instruction density is very high and the length of the vector generating instructions very small. In this case, the system issues an error.

There are some rules of thumb by which such a complete drain of the data queue can usually be avoided. These are:

  • Do not nest your subroutine calls too deep (processing of the STVA and the RSUB instructions is particularly time consuming).
  • Try to maximize the length of your vector generating instructions.
  • Try to use RPTV instead of GENV whenever possible (this increases the speed at which vectors are written to the queue).
  • Use RPTV instead of a counted loop (LBGN) whenever possible (LBGN/LEND is internally treated as a subroutine, and therefore just as time consuming as STVA and RSUB).

If the data queue runs empty nonetheless, you can add the FLQU (FilL QUeue) sequencer instruction to sections of your test where instruction density is very high. FLQU enters fill break vectors (as defined with brk in the wavetable) into the data queue. Note that these break vectors are not recorded in the Error Map. Note also that you should use FLQU only for small user periods.

The DQUE? firmware query can help to optimize the usage of FLQU. It returns the minimum level of the data queue during the last sequencer run. It must be issued after the sequencer run.

The rate at which the data queue is filled and the minimum value of the user period depend on the hardware specifications of the different systems.

Queue behavior of the Pin Scale systems

The size of the data queue is 832 = 104 * 8 vector instances. It is refilled with a maximum rate of 1 instance in 0.625 ns whenever the sequencer does not process instructions.

Furthermore the data queue is affected by occasional memory maintenance routines, during which the sequencer cannot write any vectors to the data queue, and which occur asynchronously to the sequencer program. These routines take about 0.5 µs, which will deplete the data queue by 200 vectors at a user period of 2.5 ns. To safeguard against these asynchronous interruptions, the data queue should always contain enough vectors to bridge a time span of 0.5 µs.

The DQUE? firmware query can be used to check if this condition is satisfied.
