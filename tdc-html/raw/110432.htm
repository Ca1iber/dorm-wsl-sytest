TMLimits

The TMLimits class lets you control limits and test numbering in your testflow with data from a CSV file.

This concept of storing important testflow parameters externally in a CSV file provides greater flexibility and ease of use:

  • You can easily switch between different testing modes or stages in the same testflow for different situations. For example, you can use a looser set of limits for wafer testing and a tighter one for quality control. These modes or stages are selected using the load() function.
  • The settings in the CSV file can be easily edited even without access to SmarTest, for example, using Open Office Calc or a standard text editor. This allows you to make adaptations on the fly.

Setting the test mode

The test mode can either be defined by the TMLimit_TestMode testflow variable or with the setTestMode() and load(<limitfile>,<mode>) member functions of TMLimits. Which setting is actually valid (which can be checked with the getTestMode() member function) depends on the change history of both access methods.

Generally, the test mode of the testflow variable becomes valid if the following two conditions are both satisfied:

  • One of the following member functions of TMLimits is called:
    • getLimit(), getLimitRef(), getLimitObj()
    • load() (without parameters!).
  • The current value of the variable is different from the value it had at the last call of one of these member functions or of setTestMode().

In contrast, if the test mode is set with one of the member functions, the specified test mode becomes valid always and immediately, even if the value of the actual call equals that of the last call.

Note that this behavior holds across multiple test flow executions. If the variable is set and the testflow is executed for the first time, then its value will be the valid test mode until the first change of the test mode within the testflow. But if the testflow is executed repeatedly, the initial test mode of the later executions will depend on whether the initial value of the testflow variable is different from its value at the end of the previous execution. If it is, the value of the testflow variable will be the initial valid test mode of the actual execution. If it is not, the test mode that was valid at the end of the previous execution will be used as the first test mode of the actual execution.

TMLimits within the SMC framework

If you use TMLimits within the SMC framework together with background processing (as described in Four-step SmartCalc implementation), the following rules must be observed:

  • The functions getLimit(), getLimitRef(), and getLimitObj() for retrieving data from the TMLimits table are threadsafe.
  • Ensure that the TMLimits table is loaded into the memory before calling SMC_ARM(), for example:
    tmLimits.load("tmuVerify_limits.csv");
SMC_ARM(XXX);
  • Ensure that all required settings are done before an SMC background process is armed.
CAUTION You must not change or reload a TMLimits table while an SMC background process is armed or running. Violating this rule may result in invalid data or the crash of the test method.

getLimit()
Note For performance reasons, we recommend that you use getLimitRef(), described below, instead of this function unless you want to modify the test limits it returns.
LimitInfo& getLimit(const std::string& key);
LimitInfo& getLimit(const std::string& testSuiteName, const std::string & limitParamName);
LimitInfo& getLimit(const std::string& testSuiteName, const std::string & limitParamName, const std::string & pinName);
LimitInfo& getLimit(const std::string& testSuiteName, const std::string & limitParamName, const std::string & pinName, int testNumber);

Returns a reference to an internal LimitInfo object of the system-prepared class object tmLimits describing an individual test for use with TMLimits functions. Data of the requested test are copied from the TMLimits table into the internal LimitInfo object.

The internal LimitInfo object is available once per thread, meaning there is one object for the main thread of SmarTest and one more internal LimitInfo object for each SMC background thread.

You can change the contents of the internal LimitInfo object but changes apply only to the object that is assigned to the current thread.

Multiple calls of this function within one thread refer always to the same internal LimitInfo object. You must therefore immediately process the retrieved data before the next call is issued or you must create a local copy of the data.

Depending on the structure of the CSV file you use, there are four variants of the function:

  • If the CSV file contains a unique key for each test in the first column, use the first variant.
  • If the CSV file contains the test suite name in the first column and the test name in the second, use the second variant of the function.
  • If the CSV file contains additional a dedicated pin name in the third column use the third variant of the function and use the fourth variant if the fourth column contains a test number.
Parameters
key The unique test key describing the test in the returned object.
testSuiteName The name of the test suite that contains the described test.
limitParamName The name of the test that is described in the returned object.
pinName

The name of a pin used by a test for which you want to read the limits.

The provided pin name is matched against the Pins column in the limits:

  • If a test matching pin (and the other provided parameters) is found, the corresponding limits are returned. This includes tests where the Pins column contains a pin group that includes pin.

  • If there is a Pins column in the limits but no test matches pin, the execution will lead to an error:

    Error: no limit found for testsuite=..., testname=..., pin=..., testnumber=...

  • If no Pins column exists, pin is ignored.

This parameter is optional. If you omit it, the pin name is not considered for finding the test limits.
testNumber

The number of the test for which you want to read the limits.

This parameter is optional. If you omit it, the test number is not considered for finding the test limits.
Return value
A reference to an internal LimitInfo object of the system-prepared class object tmLimits. This internal object holds the data of the requested test.
Using the function

The following code creates a reference to the internal LimitInfo object of the system-prepared class object tmLimits. The object is available once for the current thread:

TMLimits::LimitInfo & limitInfo_1 = tmLimits.getLimit("testSuite_1","test_1");

Variable limitInfo_1 refers to an internal LimitInfo object that is filled with the requested data. Rerunning the function immediately using another variable and other parameters will override the data that limitInfo_1 refers: Both variables refer to the same internal LimitInfo object of the system-prepared class object tmLimits. In this case you must create a local copy of the internal LimitInfo object:

TMLimits::LimitInfo limitInfo_1 = tmLimits.getLimit("testSuite_1","test_1");
TMLimits::LimitInfo limitInfo_2 = tmLimits.getLimit("testSuite_1","test_2");
getLimitRef()
const LimitInfo& getLimitRef(const string& key)
const LimitInfo& getLimitRef(const string& testsuite, const string& testname, const string& pin = "", int testnumber = -1, int sbin = -1)

Returns a reference to a LimitInfo object that represents directly the requested test in the TMLimits table. Unlike getLimit(), the content of the referenced object cannot be modified.

The referenced LimitInfo object holds the data for the first test that matches all specified criteria. In the second variant of the function, you must always specify the test suite and test name. The other criteria are optional and are ignored if you do not specify them.

This function is significantly faster than getLimit() and should be preferred. If you do not need to modify the LimitInfo object, use this function for maximum performance.

The name of a pin used by a test for which you want to read the limits.

The provided pin name is matched against the Pins column in the limits:

  • If a test matching pin (and the other provided parameters) is found, the corresponding limits are returned. This includes tests where the Pins column contains a pin group that includes pin.

  • If there is a Pins column in the limits but no test matches pin, the execution will lead to an error:

    Error: no limit found for testsuite=..., testname=..., pin=..., testnumber=...

  • If no Pins column exists, pin is ignored.

This parameter is optional. If you omit it, the pin name is not considered for finding the test limits.
sbin

The software bin number of the test for which you want to read the limits.

This parameter is optional. If you omit it, the software bin number is not considered for finding the test limits.
testname The name of the test for which you want to read the limits.
testnumber

The number of the test for which you want to read the limits.

This parameter is optional. If you omit it, the test number is not considered for finding the test limits.
testsuite The name of the test suite that contains the described test.
Return value
A reference to an internal LimitInfo object of the system-prepared class object tmLimits. This internal object holds the data of the requested test.
Using the function

The following code returns a reference to a LimitInfo object that represents directly the requested test in the TMLimits table:

const TMLimits::LimitInfo & limitInfoRef = tmLimits.getLimitRef("testSuite_1","test_1");

The LimitInfo object referenced by the limitInfoRef variable, cannot be modifed. However this version is significantly faster than getLimit().

If you need to modify the requested limitInfoRef, you must create a local copy of the object as follows:

TMLimits::LimitInfo limitInfoCopy = tmLimits.getLimitRef("testSuite_1","test_1");
The local object limitInfoCopy of type LimitInfo can by modified and does not have the limitation of internal object referenced by getLimit(). However, creating the local object and filling it with the data from the TMLimits table needs about the same amount of test time as getLimit().

  • tmLimits.getLimitRef("a","test","Pin2") returns the limits for test number 302.
  • tmLimits.getLimitRef("a","test","Pin3") returns the limits for test number 303.
  • tmLimits.getLimitRef("a","test","PinNew") returns the limits for test number 300.
  • tmLimits.getLimitRef("a","test","PortOdd") returns the limits for test number 303.

getLimitObj()
LIMIT& getLimitObj(const string& LimitParamName)
LIMIT& getLimitObj(const string& LimitParamName, const string& PinName)

Returns a reference to an internal LIMIT object of the system-prepared class object tmLimits. Data of the requested test are copied from the TMLimits table into the internal LIMIT object.

The internal LIMIT object is available once per thread, meaning there is one object for the main thread of SmarTest and one more internal LIMIT object for each SMC background thread.

You can change the contents of the internal LIMIT object but changes apply only to the object that is assigned to the current thread.

Multiple calls of this function within one thread refer always to the same internal LIMIT object. You must therefore immediately process the retrieved data before the next call is issued or you must create a local copy of the data.

Parameters
limitParamName

The name of the test that is described in the returned object

In contrast to functions getLimit() and getLimitRef(), the test suite name is derived from the function call itself and must therefore also match. Otherwise the test defined by limitParamName will not been found in the limit table.
PinName The name of the pin to which the particular set of limits applies that is defined for the test described in the returned object
Return value
A reference to an internal LIMIT object of the system-prepared class object tmLimits. This internal object holds the data of the requested test.
Using the function

The following code creates a reference to the internal LIMIT object of the system-prepared class object tmLimits. The object is available once for the current thread:

LIMIT & limit_1 = tmLimits.getLimitObj("testname_1");

Variable limit_1 refers to an internal LIMIT object that is filled with the requested data. Rerunning the function immediately using another variable and other parameters will override the data that limit_1 refers: Both variables refer to the same internal LIMIT object of the system-prepared class object tmLimits. In this case you must create a local copy of the internal LIMIT object:

LIMIT limit_1 = tmLimits.getLimitObj("testname_1");
LIMIT limit_2 = tmLimits.getLimitObj("testname_2");

There are two ways to specify the object:

  • By specifying the parameter name
  • By specifying the parameter name and the pin name
    Note If you specify just a parameter name for a test that defines different limits for different pins, the function returns the first limit set for the test.
In contrast to functions getLimit() and getLimitRef(), the test suite name is derived from the function call itself and must therefore also match. Otherwise the test defined by limitParamName will not been found in the limit table.

This function sets multibin to the values contained in the TMLimits object. If multibin is used in the testflow, do not use getLimitObj() to access the TMLimits object. Instead, use getLimit() or, if you use a judgeAndLog_xxx or TEST() function, use a variant that directly accesses TMLimits (instead of through a member function).

For example, instead of code like this:

TestSet.cont(true).TEST("DC_Test", "lim1", tmLimits.getLimitObj("lim1"), mLim1);

use code like this:

TestSet.cont(true).TEST("DC_Test", "lim1", tmLimits, mLim1);
load()
int load()
int load(const string& limitfile)
int load(const string& limitfile, const string& mode)
int load(TM::LIMIT_WARNING_LEVEL = TM::LIMIT_DEFAULT_WARNING)

Loads a CSV file into the TMLimits object. There are three ways to specify the desired file:

  • If you call load() without any parameters, it uses the TMLimit_FileName testflow variable to determine the file to load and the current value of the TMLimit_TestMode variable for the desired mode.

    Note that this variant is subject to the restrictions outlined above. The test mode of the variable will only be used if it has changed since the last call of one of the member functions specified above.

  • If you specify a file when calling load() but no mode, it loads the specified file and uses the mode "Default". With the "Default" test mode, the first test mode occurring in the specified test table is selected.
  • If you call load() with both a file name and a mode, it loads the specified file and sets the specified mode.
Parameters
limitfile

The CSV file to load.

The specified name can include a path, which must be relative to the testtable/ directory within the current device directory. If just a file name is given, the file must be located in the testtable/ directory.

The file must confirm to the TMLimits data format, such as files written by saving the test table from the test program explorer. This is described in Saving test numbers as TMLimits CSV files.
mode

The mode (or test stage) from the testflow to use.

A TMLimits CSV file can contain multiple versions of any of the parameters (such as upper and lower test limits) except the key columns, with each version being assigned to a test mode. Test modes can also be specified for user-defined columns.

These modes, such as quality assurance, are user definable; a CSV file can include an unlimited number of modes.
LIMIT_WARNING_LEVEL

Warning level of type TM::LIMIT_WARNING_LEVEL.

Enables you to set the verbosity of warnings displayed to the system console and report UI window.

Available options are:

  • LIMIT_DEFAULT_WARNING

    Default.

    Use this if you want to reset the warning to default. This is, all warnings are outputted to the system console and report UI window.

  • LIMIT_NO_DUPLICATE_KEY_WARNING

    Optional.

    Sets the verbosity of reported warnings not to show duplicate keys. This is, duplicate keys will only be outputted once to the system console and report UI window.

  • LIMIT_NO_DUPLICATE_TEST_WARNING

    Optional.

    Sets the verbosity of reported warnings not to show duplicate test numbers. This is, duplicate test numbers will only be outputted once to the system console and report UI window.

  • LIMIT_NO_WARNING

    Optional.

    Sets the verbosity of reported warnings not to show any warnings. This is, no warning will be outputted to the system console and report UI window.

    Use this with caution, because no warnings will be displayed at all.

This function returns whether a test table exists and can be loaded or is already loaded.

Examples

Example 1: Declare namespace

To use the TMLimits API, you need to declare the using of V93kLimits namespace in your test method:

using namespace V93kLimits;

Example 2: Setting the test mode and performing a test

tmLimits.setTestMode("FT"); 
TestSet.TEST("pinName", "myTestName", tmLimits, 4);

Example 3: Performing a test for testflow using multibin

Use

TestSet.cont(true).TEST("DC_Test", "myTestName", tmLimits, mLim1);

instead of

TestSet.cont(true).TEST("DC_Test", "myTestName", tmLimits.getLimitObj("myTestName"), mLim1);

Example 4: Using the test table bins

Test table bins with TMLImits support different bins for one test suite.

Several tmLimits API calls remember the first failing bins, see Behavior example in TESTSET().judgeAndLog_ParametricTest().

Requirements:

  • Testflow: Multibin icon in the fail branch of test suite
  • Test table: Bins of the corresponding limit keys are defined
    TESTSET().cont(true).judgeAndLog_ParametricTest(pin, <testname>, , V93kLimits::tmLimits, <singlevalue>);

Example 5: Accessing a value from LimitInfo

This code reads the limits from the test "myTestName" of the current test suite into a LimitInfo struct and retrieves the value for the units, storing it in a string variable.

using namespace V93kLimits;

string sTestsuiteName;
GET_TESTSUITE_NAME( sTestsuiteName );
string sTestName = "myTestName";

TMLimits::LimitInfo strLimitInfo;
strLimitInfo = tmLimits.getLimit( sTestsuiteName, sTestName );
string sTestTableTestModeUnit = strLimitInfo.Units;

Example 6: Changing the values of a TMLimits object

LimitInfo& MyInfo = tmlimits.getLimit(testsuiteName, testname);
MyInfo.Lsl = 4;

This example creates a reference to a LimitInfo object for the specified testsuite and test, and changes the Lsl value of the object to 4. Note that a reference is needed for this to work.

Example 7: Using the lookup key to manually retrieve the limit with getLimitRef()

STRING_VECTOR string_vector_odd;
PPMU_MEASURE ppmu_measure_odd;
DOUBLE resultValue = 0.0;
//test setup and execution
....
//get the limit with the Limit key of ContactShort
tmLimits.setLookupKey("Limit key");
TMLimits::LimitInfo limitInfoContactShort = tmLimits.getLimitRef("ContactShort");
for (int i = 0; i < string_vector_odd.size(); i++)
{
    if (string_vector_odd[i] == "BBIOI_N_ch0")
    {
        //get the limit with the Limit key of ContactShort and with the pin of BBIOI_N_ch0
        tmLimits.setLookupKey("Limit key:Pins");
        TMLimits::LimitInfo limitInfoContactShortPin = tmLimits.getLimitRef("ContactShort:" + string_vector_odd[i]);
        resultValue=ppmu_measure_odd.getValue(string_vector_odd[i]);
        TestSet.cont(true).testnumber(limitInfoContactShortPin.TestNumber).judgeAndLog_ParametricTest(string_vector_odd[i],"Contact_Short",limitInfoContactShortPin.TEST_API_LIMIT, resultValue);
    }
    else
    {
        resultValue=ppmu_measure_odd.getValue(string_vector_odd[i]);
        TestSet.cont(true).testnumber(limitInfoContactShort.TestNumber).judgeAndLog_ParametricTest(string_vector_odd[i],"Contact_Short",limitInfoContactShort.TEST_API_LIMIT, resultValue);
    }
}

Example 8: Using the lookup key to automatically retrieve the limit in judgeAndLog_ParametricTest()

tmLimits.setLookupKey("Test number");
// use the limit with the test number of 555:
TESTSET().testnumber(555).judgeAndLog_ParametricTest("io1","test12",tmLimits,-12);
tmLimits.setDefaultLookupKeys();
// use the limit with the Pins of "io1" and with the Test name of "test12"
TESTSET().judgeAndLog_ParametricTest("io1","test12",tmLimits,-12);

Example 9: Limiting displayed warnings when loading a limits file.

This example shows all available parameter. However, it will suppress duplicate test numbers.

virtual void run()
{
    ON_FIRST_INVOCATION_BEGIN();

        tmLimits.setLookupKey("Test number:Limit_type");
        cout << "default usage" << endl;
        tmLimits.load();

        // use this to re-/set to default
        // tmLimits.load(TM::LIMIT_DEFAULT_WARNING);

        // use this to suppress duplicate key warnings
        // tmLimits.load(TM::LIMIT_NO_DUPLICATE_KEY_WARNING);

        // use this to suppress duplicate test number warnings
        tmLimits.load(TM::LIMIT_NO_DUPLICATE_TEST_WARNING);

        // use this to suppress all warnings
        // use this carefully!
        // tmLimits.load(TM::LIMIT_DEFAULT_WARNING);

    ON_FIRST_INVOCATION_END();

    return;
}
