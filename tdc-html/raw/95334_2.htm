Syntax of the firmware commands

Every firmware command is represented by a 4 letter mnemonic. Most firmware commands come in two variants, a command proper which serves to write data to the test system, and a query which serves to retrieve the current settings of these data. The query is identified by a question mark after the mnemonic. Observe that some commands can only be used as a query, and that some have no associated query.

The command parameters are positional parameters, that is, they are identified by their position in a comma separated list which follows the mnemonic. There are three types of parameters, mandatory, optional, and extra parameters. Both optional and extra parameters can be omitted. If they are, the current value of the parameter is (usually) retained.

Optional and extra parameters differ in the treatment of the commas which separate them within the list. The comma before an optional parameter must be entered in the call even if the parameter is omitted. In contrast, if an extra parameter is omitted, then the comma before it (or after it if it comes first in the parameter list) must also be omitted. Extra parameters serve to maintain downward compatibility when a new parameter is added to a command.

In the syntax descriptions, mandatory parameters are enclosed by braces ({}), optional and extra parameters are enclosed by brackets ([]):

  • Mandatory parameters:

{...}
  • Optional parameters:

[...]
  • Extra parameters:

[... ,] or [, ...]

Both braces and brackets are part of the syntax language and must be omitted in the actual command calls. In contrast, parentheses are part of the command language and must be specified in the call whenever they occur in the general syntax description. They are needed for parameters which specify tester resources (pins, ports, channels). Most of these parameters accept a comma separated list of values. These commas must be distinguishable from the commas that separate different parameters, and this is achieved by putting the value list in parentheses. Note that the parentheses must be entered even if the list contains only one item. This use of parentheses has been generalized so that tester resources must be enclosed by them even if the respective parameter accepts only one pin or port.

As an example, consider the FTSM (Functional Test Set Mask) command which serves to mask certain cycle ranges within a pattern. Its syntax description is as follows:

FTSM {SET|CLEAR}, [run_to], [mask_before], [mask_after] [,(ref_port)]

FTSM?

returns:

FTSM CLEAR,,,

or

FTSM SET, [run_to], [mask_before], [mask_after] [,(ref_port)]

The command has 5 parameters, one mandatory, three optional, and one extra, namely ref_port. The query has no parameters, but one of its possible answers has 5 of them. The specifiers in italics are place holders which must be replaced by legitimate values in the call. Strings in normal type are constants (keywords). Thus, the constants SET and CLEAR are the only legitimate values for the first parameter; the vertical bar denotes an exclusive OR.

Note Constants (keywords) must be specified without quotes. This is in contrast to variable strings, which have to be enclosed by quotes. These quotes are also specified in the syntax description. Just as the parentheses, they belong to the command language, not the syntax language. The FTSM command has no variable string parameter, but compare, for example, the SQLB command (which defines a label), where the label name is a variable string.

The following are correct FTSM calls:

FTSM SET,,25,50
FTSM SET,55,,,(port1)
FTSM?

which would return:

FTSM SET,55,,,(port1)
FTSM CLEAR,,,
