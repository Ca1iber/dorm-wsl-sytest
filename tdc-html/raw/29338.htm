Topic 29338

FLUSH

This topic contains:

  • Introduction
  • Application note
  • Syntax
  • Example

Introduction

This API reflects the changes specified by the following APIs to the setup data or hardware:
  • ROUTING_STATUS

And also, this reflects the changes specified by the following APIs to the MCD (firmware level), but does not reflect them to the hardware:

  • PRIMARY_STATUS
  • TIMING_SPEC / LEVEL_SPEC / SPECIFICATION

For the information about activating the master clock, refer to SQST, SQST? - (SeQuencer STate) and CONNECT.

Note If keep alive ports are set via the FTCG command and FLUSH(TM::APRM) (Command FLSH) is executed, the following message will be issued in case of updating the clock:
FTCG ON was specified for at least one port which cannot be retained unchanged now.
							The command "Flush" forces a clock off, resulting in a stop of all channels.
For more information, refer to Suppressing Reactivation of Primary Sets with FTCG.

Application note

In order for the FLUSH API (or an API that internally executes the FLUSH API) to reflect the changes that are specified by ROUTING_STATUS to utility lines, the sequencers must be halted.

(No FLUSH is required for the trigger() / abort() / getXXXX() / isRunning() member functions in ROUTING_STATUS.)

The following are the corresponding member functions, for which all analog modules (AWGs/DGTs/Samplers) must be halted when the FLUSH API is executed.

  • Routing.primary(), Routing.pin(), Routing.util(), Routing.uti_purpose()

The operation of the FLUSH API is contained in the behavior of the EXECUTE_TEST, START_TEST, DIGITAL_CAPTURE_TEST, and NB_DIGITAL_CAPTURE_START APIs. Therefore, in most cases, you do not need to call this API. Mainly, this API is used for debugging your test method program.

In the same manner as above, if you specify the change of the spec values by using the member functions of the LEVEL_SPEC or TIMING_SPEC API (or SPECIFICATION API for multi-port testing), the changes are reflected to the desired spec data when the FLUSH API is called. Therefore, if you debug a test method program with the Spec Tool, and you want to reflect the changes before any of the APIs listed in the next paragraph is executed, call the FLUSH API. During debugging, you can also change the spec values with the Spec Tool.

The changes specified by the PRIMARY_STATUS, TIMING_SPEC, LEVEL_SPEC, and SPECIFICATION are actually reflected to the hardware when any of the following APIs is executed. For more information, see PRIMARY_STATUS - (Primary).

  • EXECUTE_TEST
  • START_TEST
  • DIGITAL_CAPTURE_TEST
  • NB_DIGITAL_CAPTURE_START
  • FUNCTIONAL_TEST
  • FLUSH then SPEC_SEARCH (execute() member function)
  • FLUSH then SEQUENCER_STATUS (run() member function)
  • FLUSH then PMU_IFVM (execute() member function)
  • FLUSH then PMU_VFIM (execute() member function)
  • FLUSH then TASK_LIST (execute() member function)
  • FLUSH then DPS_VFIM (execute() member function)

When using the FLUSH(TM::APRM) option, if your application is changing the same spec variable, it must be called after each change command. However, If your application is changing different spec variables, the FLUSH(TM::APRM) only needs to be called once at the last line.

Note FLUSH() should be called before elements which should be "flushed" get out of scope. For example, if the elements to be flushed are declared inside an "if{}" block, then FLUSH() must also be declared within the same block. Otherwise, placing the FLUSH() outside the block will cause a FLUSH() error to occur.

Syntax

void FLUSH();
void FLUSH(const TM::FLUSH_POST_ACTION action);
void FLUSH(bool force);
void FLUSH(TM::FLUSH_POST_ACTION action, bool force);
void FLUSH(TM::FLUSH_SECTION_TYPE flush_section);
void FLUSH(bool force, TM::FLUSH_SECTION_TYPE flush_section);
void FLUSH(TM::FLUSH_POST_ACTION action, bool force, TM::FLUSH_SECTION_TYPE flush_section);
Parameters
action

This parameter controls how the setup data will be downloaded to the hardware.

You can leave it empty or use TM::APRM.

When using the TM:APRM option, the command APRM with mode set to CNL will be issued following the normal FLUSH() actions.
force

When to execute the firmware command FLSH and WSDN. It can be:

  • true: always executes the firmware command FLSH and WSDN (default)

  • false: only executes the firmware command FLSH and WSDN when necessary.
flush_section This parameter allows you to set which types of APIs to flush.
You can use the following options:
  • TM::FLUSH_PRIMARY1),
  • TM::FLUSH_UTIL2),
  • TM::FLUSH_ALL,
or a combination hereof.

This API is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/MapiFuncs.h.

Example

TM::FLUSH_PRIMARY / UTIL

Routing.util("UTI1").on();
Primary.getLevelSpec().change("S_VCC", 4.45);
FLUSH(TM::FLUSH_PRIMARY | TM::FLUSH_UTIL);
Alternatively:
TM::FLUSH_SECTION_TYPE flushType;
flushType = TM::FLUSH_UTIL | TM::FLUSH_PRIMARY;

Routing.util("UTI1").on();
Primary.getLevelSpec().change("S_VCC", 4.45);
FLUSH(flushType);

Functional changes

  1. Introduced before SmarTest 6.3.2
  2. SmarTest 7.1.3: Support of MBAV8+
  3. SmarTest 7.1.4: HW of analog modules cannot be accessed when the master clock is switched off. An error is issued and the message is displayed in the report window.
  4. SmarTest 7.6.1: Added parameter flush_section
1) FLUSH(TM::FLUSH_PRIMARY) flushes these APIs:
  • Primary Sets,
  • Timing Spec,
  • Specification Level,
  • Spec Sequencer,
  • Definition changes.
2) FLUSH(TM::FLUSH_UTIL) flushes these APIs:
  • Utility Purpose control,
  • Utility line control.
