Topic 29669

ROUTING_STATUS - (Routing)

Subtopics

  1. PIN_I
  2. UTIL_I
  3. UTI_PURPOSE_I

The ROUTING_STATUS API accesses the data container holding the routing set.

This API can be used to call the PIN_I class, UTIL_I class, and UTI_PURPOSE_I class.

You can achieve the following routing actions via the member functions of the ROUTING_STATUS API.

  • Define the predefined routing set as the primary
  • Return the current primary routing set number
  • Make a new routing setting on the specified analog module and on a DUT board using specified utility lines without any routing set

The routing set specified and the new routing settings made using this API will be downloaded to hardware by the next FLUSH or Execution API such as EXECUTE_TEST.

You have to use the system-prepared class object Routing when using the member functions. You cannot create any object of the ROUTING_STATUS API.

If you described multiple statements of this API before the FLUSH API or Execution API, the routing statements are stored in the Message Concentrator and Distributor (MCD) once temporarily, then all the routing setting data is downloaded to the hardware in the order below. For the MCD, see the manual Command Reference.

  1. Download the routing set defined as the primary by using the primary member function of this class.
  2. Download the multiplexer setting data by using the pin member function of the PIN_I class.
  3. Download the utility line setting data by using the uti_purpose member function of the UTI_PURPOSE_I class.
  4. Download the utility line setting data by using the util member function of the UTIL_I class.

It is not recommended to describe many Routing.pin, Routing.uti_purpose and Routing.util statements before the Execution API or FLUSH API. Use the Routing Set rather than these statements. This is because you can check the inconsistency of the utility line settings in the testflow by the "Debug Analog" testflow flag and you can get good throughput.

This API is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/RoutingStat.h.

Class definition

Member Functions

INT primary(INT set_num = 0);
PIN_I& pin(const STRING& pin_name);
UTIL_I& util(const STRING& util_name); 
UTI_PURPOSE_I& uti_purpose(const STRING& uti_purpose_name);

Syntax

For defining a routing set as the primary:

Routing.primary(INT set_num);

For retrieving current primary routing set number:

return_value = Routing.primary();

For make a new routing setting:

 Routing.member_func.sub_func;

member_func is a member function (pin, util, or uti_purpose) of the ROUTING_STATUS API that calls a subsidiary data container (PIN_I, UTIL_I, or UTI_PURPOSE class).

sub_func are member functions of the subsidiary data container. For retrieving data, only one member function is available.

Member functions

primary()

INT primary(INT set_num = 0);

This member function defines the specified routing set as the primary. If you call this member function, any temporary modifications that are not flushed to the hardware will be reset or discarded. This member function can also return the number of the current primary routing set. In multisite test, it works for all sites outside of FOR_EACH_SITE block and cannot be used in FOR_EACH_SITE block.

Parameter

set_num

Routing set number to be define as the primary. When you specify 0 as the parameter, nothing is executed and the current number of the primary routing set is returned.

pin()

PIN_I& pin(const STRING& pin_name);

This member function returns the PIN_I class object that represents the multiplexer setting for the specified pin. To make a new multiplexer setting, use the member function of the PIN_I class. In multisite test, it works for all sites outside of FOR_EACH_SITE block. You can also use it in FOR_EACH_SITE block to set up each site serially.

For the member functions of the PIN_I class, see PIN_I.

Parameter

pin_name

The name of the pin to be manipulated.

util()

UTIL_I& util(const STRING& util_name);

This member function returns the UTIL_I class object that turns the utility line on or off. To make a new utility line setting, use the member function of the UTIL_I class. In multisite test, it works for all sites outside of FOR_EACH_SITE block. You can also use it in FOR_EACH_SITE block to set up each site serially.

For the member functions of the UTIL_I class, see UTIL_I.

Parameter

util_name

The name of the utility line defined in the Pin Configuration.

uti_purpose() 

UTI_PURPOSE_I& uti_purpose(const STRING& uti_purpose_name);

This member function returns the UTI_PURPOSE_I class object that switches the states of the utility lines defined as a utility purpose. To apply the predefined utility purpose, use the member function of the UTI_PURPOSE_I class. In multisite test, it works for all sites outside of FOR_EACH_SITE block cannot be used in FOR_EACH_SITE block.

For the member function of the UTI_PURPOSE_I class, see UTI_PURPOSE_I.

Parameter

uti_purpose_name

The name of the utility purpose defined in the Pin Configuration.

Important Points

  • It is not recommended to describe many Routing.pin, Routing.uti_purpose and Routing.util statements before the Execution API or FLUSH API. Use the Routing Set rather than these statements. This is because you can check the inconsistency of the utility line settings in the testflow by the "Debug Analog" testflow flag and you can get good throughput.

Examples

Connect to and disconnect from AWG

This example performs the ADC and DAC linearity tests. ROUTING_STATUS is used to connect the pin to the analog module before the measurement and disconnect the pin from the analog module after the measurement. AWG_pin, capture_variable, miss_number, miss_code and min_code_size are parameters defined in this test method.

int GlobalOverOn,debug;
int off_line    ;    
ARRAY_I adc_wave;
ARRAY_I histogram;
ARRAY_D adc_dnla,adc_inla;
LINEARtype  adc_lin ;
ARRAY_I esites, csites;   // Enabled Sites array
int nsites      ;   // max number of configured Sites
# define ADC_resolution 8 // Assuming 8-BIT ADC, that is: 256 different codes
INT miss_codes [(INT) pow (2,(DOUBLE)ADC_resolution)];

ON_FIRST_INVOCATION_BEGIN() ;
  GET_TESTFLOW_FLAG("debug_analog", &debug);
  GET_TESTFLOW_FLAG("global_overon", &GlobalOverOn);
  GET_SYSTEM_FLAG("offline",&off_line);
  GET_ENABLED_SITES(esites); 
  GET_CONFIGURED_SITES(csites);
  nsites = csites.size() ; 
  CONNECT();
  /*connect and activate analog module trigger line */ 
  Routing.pin(AWG_pin).connect(TM::SINGLE);
  AWG( AWG_pin ).enable() ;  
  /* perform the test */
  DIGITAL_CAPTURE_TEST( 1.0 ) ;
  /* deactivate analog module trigger line and disconnect the analog pin */
  AWG( AWG_pin ).disable() ;
  Routing.pin(AWG_pin).disconnect();
ON_FIRST_INVOCATION_END() ;

/* retrieve measurement data */
adc_wave = VECTOR (capture_variable).getVectors ();    

/* perform computation */
DSP_HISTOGRAM ( adc_wave, histogram, 1, 255, 256);    
try {
  DSP_ADC_HISTOGRAM ( histogram, &adc_lin, adc_dnla, adc_inla, &miss_number, miss_codes, END_PT, min_code_size );
} catch (Error &exc) {
  // an error occurred; most likely because the captured waveform contains only missing codes/is a straight horizontal line
  ERROR_EXIT(TM::RETURN_TO_FLOW);
}if ( debug )
{      
  PUT_DEBUG ( AWG_pin,    "Lin_adc_wave",   adc_wave );
  PUT_DEBUG ( AWG_pin,    "Histogram",      histogram);
  PUT_DEBUG ( AWG_pin,    "Lin_adc_dnl",  adc_dnla );
  PUT_DEBUG ( AWG_pin,    "Lin_adc_inl",  adc_inla );
  cout << endl ;
}

/* compare computed result with limits and set pass/fail */
TEST( AWG_pin, "ADC_ILE", adc_lin.iamax);
TEST( AWG_pin, "ADC_DLE", adc_lin.damax);

Set and get the primary set

The member function primary defines the routing set #2 as the primary. 

Routing.primary(2);

The member function primary returns the current primary routing set number to the variable status.

INT status;
    :
status = Routing.primary();

Connect and disconnect pins

The member function connect connects the pins "Aoutp" and "Aoutn" to the analog module's core with Single-Ended mode (this is only possible for the MCB VHF AWG, where two in-phase buffers are available). 

Routing.pin("Aoutp, Aoutn").connect(TM::SINGLE);

The member function fwd connects the "Aout" pin to the analog module's "fwd_pin".

Routing.pin("Aout").fwd("fwd_pin");

The member function trigger connects the "Aout" pin to the analog module's "SYNC CLK" pin.

Routing.pin("Aout").trigger();

The member function disconnect disconnects the "Aout" pin from any pin or hardware.

Routing.pin("Aout").disconnect();

Connect and disconnect utility lines

The member function closes the relay connected to the utility line named as "util_a".

Routing.util("util_a").on();

The member function applies the settings of the utility lines in the utility purpose "ALL_ON" defined in the Pin Configuration.

Routing.uti_purpose("ALL_ON").set();

Execution sequence of routing actions

This example shows the execution sequence of the routing actions which are done with the same member function. The execution sequence of the statements is in the alphabetical order of the object. This means "Routing.util("c,d,b,a").off()" is executed after "Routing.util("a,b").on()". So the execution result of the following example is utility pin a, b, c and d are all set to off. 

Routing.util("c,d,b,a").off();
Routing.util("a,b").on();
FLUSH();

For example, test suite A is the neighbor ahead of test suite B in the testflow. At the end of test suite A, "Routing.util("c,d,b,a").off()" is executed. At the beginning of the test suite B, "Routing.util("a,b").on()" and "FLUSH()" is executed. Because of no FLUSH() after "Routing.util("c,d,b,a").off()" in test suite A, the code is kept to the next test suite. According to the execution sequence, "Routing.util("c,d,b,a").off()" is executed after "Routing.util("a,b").on()". The execution result of the three lines of test method code is that the utility pin a, b, c and d are all set to off.
