Parameter: handler_retest_bins and prober_retest_bins

Defines the equipment bins to be used for unknown test results.

A test result is unknown, if the device test was skipped or if the device was binned to SmarTest's 'otherwise' bin.

If the parameter handler_bin_ids (prober_bin_ids) IS NOT defined (this is allowed when ‘default' bin mapping is used), the entries of the handler_retest_bins (prober_retest_bins) definition are directly interpreted as the plug-in internal bin numbers (which start with 0).

Example: handler_retest_bins: [3 6] defines the bins with the plug-in internal numbers 3 and 6 as retest bins.

If the parameter handler_bin_ids (prober_bin_ids) IS defined, the entries of the handler_retest_bins (prober_retest_bins) definition are interpreted as DC/DC power units to the handler_bin_ids (prober_bin_ids) array. Note that the first entry in that array has the index number 0.

Example: handler_bin_ids: ["A" "B"]; handler_retest_bins: [1] defines the bin with the ID "B" as a retest bin. (This bin may be mapped to any handler bin by setting up one of the two handler related parameters described next.)

See Parameter: hardbin_to_handler_bin_map and hardbin_to_prober_bin_map for a more detailed example.

Some handlers and probers have the capability of binning to a retest bin when they receive an end-of-test signal without binning data. In this case handler_retest_bins ( prober_retest_bins ) can be assigned an empty list (for example, handler_retest_bins: [ ]) to use this feature. For GPIO equipment, this only makes sense when bin_coding is "explicit".

Driver default: no retest bins

Changeable at run-time: yes

Applicable for: handlers or probers, respectively

Example: prober_retest_bins: [3 4]
