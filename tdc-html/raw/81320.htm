Topic 81320

The PART_ID field in the PRR

Subtopics

  1. Subdie wafer testing

Default device identification numbering

The data formatter automatically generates unique integer identification numbers for each device in the lot. If you are executing a multisite test on four different sites, the device on each site will receive a unique integer identification number (Dev@). For example, the first devices tested would be numbered 1, 2, 3, 4 and the next set of devices on those four sites would be numbered 5, 6, 7, 8. This is the default behavior.

Subdie identification numbering

When you perform Subdie wafer testing and want each subdie to have its own part ID in the EDL report, you must set the test program parameter SubdieTestingEnable to true.

  • If SubdieTestingEnable is set to true, each subdie will have a unique PART_ID value.
  • If SubdieTestingEnable is not true, SmarTest uses the default numbering described above. All subdies at the same (X, Y) coordinate will have the same PART_ID values and will be identified as retest results.

The following code example shows how to set up SubdieTestingEnable.

{ lot
  ACTIONS
  ...
  SubdieTestingEnable = CONST_INPUT(true);
  ...
  { WAFER [({LotID}),({WaferID})] wafer:
    ACTIONS
    SubdieTestingEnable = CONST_INPUT(true);
    ...
    { DEVICE subdie:
      ACTIONS
      SubID = AUTOINCREMENT;
      SITE1_PART_ID = CONST_INPUT({SubID});
      ...
    }
    ...
  }
  ...
}

User-defined device identification numbering

You can specify custom part identification numbering from the application model. To do this, you must populate application model variables with values that follow this naming structure:

SITE<N>_PART_ID (where N is the site number)

For example, if you are testing devices on three sites and you want to set the identification numbers for those devices, you need to populate the following variables:

SITE1_PART_ID = ...
SITE2_PART_ID = ...
SITE3_PART_ID = ...

These variables must be populated before the DEVICE_TEST command in the application model. It is recommended that you populate these variables inside the DEVICE level in the application model before DEVICE_TEST is executed.

New PART_ID values for retested devices

When you retest devices, you may need each retested device to have its own new PART_ID value in the STDF output. Then, you must set the parameter OverridePartIdForRetestDevice to true in your application model file and set the variable SITEn_PART_ID to new values.

The following example shows the setup.

...
  OverridePartIdForRetestDevice = CONST_INPUT(true);
  ...
    SITE1_PART_ID = 1015;
    SITE2_PART_ID = 1016;
    ...
...

As a result of this setup, the retested devices use the new PART_ID values in the output, which are "1015" and "1016" as in the example.

If you do not set the parameter OverridePartIdForRetestDevice to true and no new PART_ID values in your application model file, the retested devices will keep using their original PART_ID values.
