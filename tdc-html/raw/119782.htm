Handling waveform definitions at the firmware level

For historical reasons, waveform shapes, as defined in a wavetable, are considered by the firmware as triples consisting of a logical waveform, a physical waveform, and a device cycle name.

In earlier releases, the edge-action sequence was defined in a logical waveform. This sequence could contain place holders for actions. The placeholders had to be substituted by fixed actions to result in an executable waveform. The physical waveform supplied these replacements and also defined the waveform index which was used to identify the executable waveform in the vector setup. The same logical waveform could be associated with different physical waveforms with different replacements and DC/DC power units. Logical waveforms without placeholders were a border case which still needed a physical waveform to determine the index.

Furthermore, neither logical nor physical waveforms could be named; not only the physical, but also the logical waveforms were identified by an index. The only way to give a waveform a name was to associate it with a device cycle. Device cycles were sequences (possibly of length 1) of logical waveforms which were to be treated as a unit, and which were identified by a device cycle name.

The actual waveform shapes are still interpreted within this framework by the firmware. They are treated as pairs of a logical and a physical waveform where the logical waveform contains no placeholders and both waveforms have the index that is specified in the waveform definition within the wavetable. The logical waveform is supposed to be associated with a device cycle of length 1 the name of which is the one specified in the waveform definition.

To realize all this will help you in the following situation:

  • You can change the runtime definitions (not the definitions in the wavetable) of waveform shapes at the firmware level, but to do that requires two steps:
    1. Issue the WFDS command with the extra parameter ALLOW_EQ to change the logical waveform.

      However, this will delete the physical waveform that was associated with the logical waveform. Since the physical waveform must be present, a second step is required:

    2. Issue the WAVE command with the extra parameter ALLOW_EQ to restore the physical waveform.

Functional changes

  1. Introduced before SmarTest 6.3.2
