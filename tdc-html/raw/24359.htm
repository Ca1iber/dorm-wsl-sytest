Data Queue

The sequencer cannot process instructions and send vectors to the DUT at the same time. In order to supply a continuous stream of vectors to the DUT (even when the sequencer is busy decoding sequencer instructions), a data queue is used.

The sequencer does not send vectors to the DUT directly; instead, it places the vectors in the data queue, and vectors are then forwarded to the DUT from the queue. In this way, vectors can be fed continuously while the sequencer is busy processing instructions. However, while the sequencer is busy, the number of vectors in the queue decreases.

When the sequencer is free again, it can refill the queue quickly, because it is able to write vectors to the queue faster than vectors are read from the queue (even at maximum execution speed). When the queue is full, the sequencer stops writing to it until the queue needs to be filled again.

When instruction density is very high, there is a possibility that the data queue will become empty before the sequencer has a chance to refill it. This is an error condition. The system will notify you of the relevant label, vector and cycle numbers, and the command number.

Keeping the Queue Filled

To avoid a complete drain of the data queue, observe the following guidelines:

  • Do not nest your subroutine calls too deeply.
  • Try to maximize the length of your vector generating instructions.
  • Where the same vector is being used more than once, be sure you are using a repeat function and not a generate function for the repeats.
  • If your data queue is emptied nonetheless, insert fill break vectors into your test.

For more information on how to query the data queue, see DQUE? - (show Data QUEue low level).

Inserting Fill Break Vectors

Use the FLQU instruction to add fill break vectors to the data queue in sections of your test where instruction density is very high. You should use it only for small base periods. The instruction allows the machine to continue executing vectors at the programmed period, while appearing to the DUT as a kind of "nop". You define the break vector with the command BWDF, BWDF? - (Break Waveform DeFinition).

Note that these break vectors are not displayed in the Error Map window.

The following figures can be used to estimate the probability of such an error:

The data queue holds 512 = 64 * 8 vectors. It is refilled at a fixed rate of 1 vector in 3.14 ns whenever the sequencer does not process instructions. Vectors are issued to the DUT at a maximum rate of 1 vector every 4 ns. Thus, to refill an almost empty data queue while vectors are generated at full speed, a linear vector stream of 2377 vectors would be required.

The time needed to process a sequencer instruction is 24 ns for most instructions. It is considerably higher for the STVA and the RSUB instructions, because these must allocate the resulting address in the vector areas.
