Topic 69314

GPIB communication flow for Delta Summit handlers

This section describes the GPIB communication between the driver and the handler.

The table below shows the communication between the driver and the handler. The actions and messages are listed in sequential order.

See Conventions for GPIB communication for descriptions of the syntax.

GPIB communication flow for Delta Summit handlers

Message from driver

Message from handler

Comments

init: <id request> <initialization> <configuration>

id request:

identify?

 

Asks for handler ID.

 

"string"

Handler returns ID, for example

Summit 1.7.3.

which?

 

Asks for handler name.

 

"string"

Handler returns name.

initialization:

numtestsites?

 

Asks handler how many sites it has.

 

n

Handler returns number of sites.

systemmode 1

 

Activates normal handling mode.

verifytest?

 

Asks handler if it is set up in bin verification mode, only if not disabled with summit_workarounds configuration parameter.

 

n

Handler returns 0 (no) or 1 (yes).

configuration: <temperature setup> <verification setup>

These commands are sent at startup and after each driver reconfiguration at runtime.

temperature setup:

Depending on the configuration parameter temp_control, one of the following communication flows applies:

Communication flow when temp_control is set to manual

No commands are sent.

Communication flow when temp_control is set to ambient

tempcontrol 0

 

Sets handler to ambient mode.

Communication flow when temp_control is set to active

recipestart file?

 

Starts creation of a recipe file.

 

recipegood file

Handler acknowledges.

lowguard n?

 

Sets lower guardband value.

 

command OK

Handler acknowledges.

highguard n?

 

Sets upper guardband value.

 

command OK

Handler acknowledges.

setpoint n?

 

Sets setpoint in specified zone to given value in Celsius.

 

command OK

Handler acknowledges.

soaktime n?

 

Sets soaktime in seconds.

 

command OK

Handler acknowledges.

recipeend file?

 

Closes recipe file.

 

recipeend file

Handler acknowledges.

recipe activategrp file

 

Activates created recipe file.

tempcontrol 1

 

Activates temperature control.

verification setup:

verifytest n

 

Activates bin verification (1), if configured with verify_bin_data (set to yes).

Deactivates bin verification (0), if configured with verify_bin_data (set to no).

Note: This command is not sent if verify_bin_data is not configured.

wait for devices: [<SRQ>][<poll>][<status request>]

The driver will either wait for an SRQ or poll for the current site population. If an SRQ is received, polling is still done afterwards in cases where:

  • testing is done on more than 1 site, or
  • not all sites that are active, based on the configuration parameter handler_site_mask, seem to be populated.

This command is repeated until there is a device to test. The driver queries the status regularly if no devices are detected.

SRQ:

 

SRQ

Handler sends test start SRQ.

devicenotify?

 

Asks for device notification code, only if corresponding bit is set in SRQ byte.

 

n

Handler returns code.

lotnotify?

 

Asks for lot notification code, only if corresponding bit is set in SRQ byte.

 

n

Handler returns code.

status?

 

Asks for handler notification code, only if corresponding bit is set in SRQ byte.

 

n

Handler returns code.

interfacenotify?

 

Asks for GPIB notification code, only if corresponding bit is set in SRQ byte.

 

n

Handler returns code.

poll (more than 1 site):

testparts?

 

Driver asks for current site population.

 

n

Handler returns bit-coded site population.

bin or reprobe devices:

 

 

For all sites, if verify_bin_data is not given in configuration:

sbin bin |

 

Driver sends bin information, or

sreprobe

 

Driver sends reprobe request.

 

 

Only if verification mode is active (not disabled with summit_workarounds configuration parameter):

querybins?

 

Driver asks handler for received bin and reprobe information.

 

bin,bin,...

Handler sends bin data back to driver.

releaseparts

 

Driver acknowledges correct binning data (if correct), or starts sending test results from the beginning (max. repeat count: verify_retry_count).

stop handler:

status?

 

Asks handler for current status.

 

n

Handler returns bit-coded status information.

stop

 

Stops handler, only if received status was started and summit_workarounds does not disable sending stop or start.

status?

 

Asks handler for status again.

 

n

Handler returns bit-coded status information (should now be stopped).

start handler:

status?

 

Asks handler for current status.

 

n

Handler returns bit-coded status information.

start

 

Starts handler, only if received status was stopped and summit_workarounds does not disable sending stop or start.

status?

 

Asks handler for status again.

 

n

Handler returns bit-coded status information (should now be started).

status request:

status?

 

Asks handler for current status.

 

n

Handler returns bit-coded status information.
