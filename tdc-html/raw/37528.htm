Structure of the KEEP_PLL_ALIVE Section

The general format of a KEEP_PLL_ALIVE section is as follows:

KEEP_PLL_ALIVE ON

PLL_PORT <pll_ports>

DATA_PORT <data_ports>

PLL_SEQ_GROUP <pll_sequencing_group>

DATA_SEQ_GROUP <data_sequencing_group>

period = <ASCII_clock_period>

PINS <clock_pins>

<state_character> <action>:<delay> [<action>:<delay> ...]

<state_character> <action>:<delay> [<action>:<delay> ...]

...

KEEP_SEQ <state_character_sequence>

...

DVC <ASCII_device_cycle>

period = <ASCII_device_cycle_period>

...

[KEEP_PLL_ALIVE OFF]

The function of the individual statements is as follows:

  • KEEP_PLL_ALIVE ON (mandatory):

    This statement marks the beginning of a KEEP_PLL_ALIVE section.

  • PLL_PORT<pll_ports> (mandatory):

    This statement specifies the clock port. You can also specify a list of clock ports, separated by blanks. This can be used to integrate the KEEP_PLL_ALIVE feature into a multi-port vector setup (see Using the KEEP_PLL_ALIVE Feature with a Multi-Port Vector Setup).

    Every pin must be contained in one of the clock ports or in one of the data ports, and no pin may be contained in more than one of these ports.

  • DATA_PORT <data_ports> (mandatory):

    This statement specifies the data port. You can also specify a list of data ports, separated by blanks. This can be used to integrate the KEEP_PLL_ALIVE feature into a multi-port vector setup (see Using the KEEP_PLL_ALIVE Feature with a Multi-Port Vector Setup ) .

    Every pin must be contained in one of the data ports or in one of the clock ports, and no pin may be contained in more than one of these ports.

  • PLL_SEQ_GROUP<pll_sequencing_group> (optional):
  • This statement defines the sequencing group to which the clock ports belong. If you do not specify it, the timing translation will create a sequencing group for the clock ports automatically.

    It is essential for the setup of a continuous clock that clock ports and data ports belong to different sequencing groups. If you let the ASCII interface create the sequencing groups, it will comply with this requirement. If you specify the sequencing groups yourself, however, you must take care that the groups are different. This is not checked by the timing translation.

  • DATA_SEQ_GROUP<data_sequencing_group> (optional):

    This statement defines the sequencing group to which the data ports belong. If you do not specify it, the timing translation will create a sequencing group for the data ports automatically.

    It is essential for the setup of a continuous clock that clock ports and data ports belong to different sequencing groups. If you let the ASCII interface create the sequencing groups, it will comply with this requirement. If you specify the sequencing groups yourself, however, you must take care that the groups are different. This is not checked by the timing translation.

  • period = <ASCII_clock_period> (mandatory):

    This statement specifies the ASCII period length for all clock pins in ns. The test system cycle length to be specified in one of the generated timing sets is calculated from the ASCII period and the KEEP_SEQ entry (see the following) by

    <ASCII_clock_period> × length of <state_character_sequence>

  • PINS <clock_pins> (mandatory):

    This statement specifies one or more clock pins, separated by blanks. It introduces a timing record for a clock pin. The syntax of the subsequent data records is the same as for standard ASCII device cycles. A timing record for a set of clock pins terminates with a KEEP_SEQ entry (see the following).

    You can specify different timing records for different clock pins. However, their KEEP_SEQ entries should all have the same length.

  • <state_character> <action>:<delay> [<action>:<delay> ...] (mandatory): Specifies a data record for the clock pins.
  • KEEP_SEQ<state_character_sequence> (mandatory):

    This statement specifies a sequence of state characters from the data records previously defined. The sequence defines the single waveform that will be created for the clock pins in question; this waveform will also be used as the break waveform for those pins. The length of the sequence is one of the factors from which the test system cycle length of the clock pins is calculated. The formula for the test system cycle length of the clock pins is

    <ASCII_clock_period> × length of <state_character_sequence>

    Note that this calculation is independent of the x-mode factor that is specified in the global configuration file for the patterns that use ASCII device cycles from the KEEP_PLL_ALIVE section.

    Note also that the ASCII interface does not expect the state characters of the clock pins to actually occur in the ASCII vector file. It will convert any state character sequence of the length that is determined by the x-mode factor of the pattern into the index of the single clock pin waveform.

    Finally, note that if different clock pins have different timing records, their state character sequences should all have the same length.

  • DVC<ASCII_device_cycle> (mandatory):

    This statement introduces an ASCII device cycle for the data pins.

  • period = <ASCII_device_cycle_period> (mandatory):

    This statement specifies the ASCII period length of the ASCII device cycle in ns. As usual, the test system cycle length to be specified in one of the generated timing sets is calculated for any PATTERNS section entry that is associated with this ASCII device cycle in the global configuration file (*.aic) by the formula

    <ASCII_device_cycle_period> × <x-mode factor>

    where <x-mode factor> is the value of the xfact column in the respective entry of the PATTERNS section.

  • KEEP_PLL_ALIVE OFF (optional):

    This statement marks the end of a KEEP_PLL_ALIVE section. If it is omitted, the ASCII interface assumes that the section extends to the next KEEP_PLL_ALIVE ON statement, or to the end of the ASCII timing file.
