Topic 343852

Multisite handling with test flow branching

Alex Roskin, COE Europe, Advantest

Paper-ID: 343852

Sometimes it is required to exclude some sites from running a digital pattern for example, during branching in a Testflow).

Generally, if there are branches within a testflow, the following rules apply to SmarTest prior to SmarTest 8:

  • In pass/fail branches, failing branches are taken before passing branches.
  • In if/then branches, FALSE statements are taken before TRUE statements.

Waiting sites (also referred to as inactive sites) receive the same data as the sites currently tested. This may change their initial status. If following tests require certain conditions, the sites may need to be re-initialized.

All sites, waiting (inactive) and currently tested (active), are enabled sites and by default receive the same setup command and execute the same sequencer program. The only difference between those is, that the waiting sites are in a connected and masked state (enabled, but not active, see also connected and masked). A site of this state receives the same vectors as all other sites. The results, however, are ignored (receivers are masked).

An example is represented in the figure below (see also Sequencer Start Labels on Failing Branches).

Testsuite 1 attempts to put devices in state 1 by clocking up a counter, ready for testsuite 3. Devices which fail are tested again - perhaps using another method - to try and get them into state 1. Devices which fail this testsuite are binned accordingly.

However, if testsuites 1 and 2 comprise tests that include a SQST label (a functional test, for example), all sequencers are started (because it is a global label). So, while the sites that failed testsuite 1 are being tested again in testsuite 2, all sites that passed testsuite 1 are receiving drive vectors, although their receive pins are masked. This process then knocks all sites that passed testsuite 1 out of the desired state.

Below are examples of APIs that set up the same condition for all enabled sites:

  • CONNECT()
  • DISCONNECT()
  • Analog.primary(set)
  • Analog.CLOCK_DOMAIN(num).setup_function()
  • Primary.setup_function(), except label per site functions
  • Routing.Pin(pin).setup_function()

Also, following are examples of APIs that execute tests on all enabled sites:

  • EXECUTE_TEST()
  • START_TEST()/WAIT_TEST_DONE()
  • DIGITAL_CAPTURE_TEST()
  • FUNCTIONAL_TEST()
  • SPEC_SEARCH(specName, specType).execute()
  • Sequencer.function()

For example, using a combination of a CONNECT() followed by a FUNCTIONAL_TEST() would lead to executing the same sequencer program with a same patterns on all enabled sites, no matter whether they are in a currently active or a waiting branch (meaning, their receivers are masked or not).

There are techniques that can be applied to ensure that a waiting site is not disturbed by a sequencer program and patterns running on the active sites.
  1. One approach to ensure that a waiting site sees a different stimulus than an active is to use label per site functionality of SmarTest. The implementation details of this feature are covered in How to execute separate patterns per site (Label per site). With that approach, a 'dummy' label is usually assigned to and executed on the waiting site, while active sites are executing a different label.
  2. Another approach is to open the AC relays on the sensitive pins of the waiting sites. A simple example:

    BEGIN_EXTENSION(sensitive_sites);

    FW_TASK("RLYC IDLE,OFF,(sensitive_pins)\n");

    END_EXTENSION();

    By doing this, protected 'sensitive_pins' of selected 'sensitive_sites' will not see any stimulus from the tester, even though the sequencer program is executed.

    You would need to reconnect sensitive pins again after corresponding sites become active again, by explicitly closing the AC relay (for instance -again- with a BEGIN_EXTENSION block definition).

  3. Another solution, if you do not need to keep a waiting site in a certain state but need to make sure it is not executing the sequencer program of the active site, is to power down the inactive site by programming digital drive levels and power supply of the waiting site to 0V. You can also keep the site powered and just reprogram the digital drive levels to 0V for example, by programming vih=vil=0V).
Note This Application paper only applies to SmarTest versions prior to SmarTest 8. Handling of Branching on SmarTest 8 is implemented differently than on all previous SmarTest releases.
