Testflow variables

The following three testflow variables are provided to control the execution of concurrent test framework. To use them in your testflow, you need to add them manually in the Variables tab of the test flow editor.

  • CCF_Concurrent

    It controls whether the CCF blocks are executed in concurrent mode or serial mode. In the serial mode, the test suites in the block are executed immediately and sequentially. In concurrent mode, the test suites in a CCF block are added to a queue of concurrent test and then executed by the framework in the last test suite concurrently.

    Its value can be:

    • 0: serial mode
    • 1: concurrent mode

      If the fag hidden_datalog_mode is turned on, test events are logged separately for each test suite. If the flag is turned off, all events are logged together in the final CCExecution test suite.

  • CCF_DevelopMode

    In concurrent mode, it controls whether the setup files in the CCF block will be merged and generated. In serial mode, it controls whether the analog and RF setup files will be generated.

    It can be:

    • 0 (production): The setup files will not be merged and generated. The timing and pattern are loaded from setup files. CCF will analyze the existing analog/RF sets (before and after merging) to collect waveform IDs (for DGT or TX pin) and function block IDs (for RF definition). This operation only happens to the first run when CCF_Concurrent = 1 so that the test time of first run of testflow will be longer than the subsequent executions. It will exit with errors if the required analog set is missing. Before running in production mode, the testflow must have been executed in other mode to get the merged multiport level, multiport timing, multiport burst pattern and analog/RF setup.
    • 1 (Learning): If the setup files have been merged and generated, use them for the test. Otherwise, merge and generate the setup files for the test.
    • 2 (development): The merging and generation of analog/RF sets, multiport level setup, multiport timing setup and multi-port burst label are done. If the setup files have been merged and generated, delete them, merge and generate them again.
    • 3 (Generate only): Merge and generate the setup files but do not run the tests.
  • CCF_VerboseLevel

    It controls the type of CCF block execution information to output to the UI report window. The error message and warning message in the execution will always be output to the UI report window. Its value can be:

    • 0: output the error message to UI
    • 1: output the error message and warning message to UI
    • 2: output the error message and warning message to UI, and log the execution time information in EDL file
    • 3: output the error message, warning message and execution information to UI, and log the execution time information in EDL file
  • CCF_AllTestPass

    It is used in the Repeat Loop node containing a CCF block to determine whether to execute the fail branch in the block. Its value can be:

    • 1: All the test suites of the CCF block passed.
    • 0: One or more test suites in the CCF block failed.

      Always set it to 1.

Functional changes

  1. Introduced in SmarTest 6.5.4
  2. SmarTest 7.1.4: New CCF_DevelopMode: -1 in TML 2.1.6
  3. SmarTest 7.2.1: New option 1 and 3 for CCF_DevelopMode in TML 2.2.0.
  4. SmarTest 7.3.1: New testflow variable CCF_AllTestPass in TML 2.2.0
