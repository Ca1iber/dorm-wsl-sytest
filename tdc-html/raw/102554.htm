Topic 102554

Waveform mapping file syntax

The syntax of the waveform mapping file is similar to that of the Timing file, although not identical to it. Wavetables for waveform mapping can be specified in three different variants of a basic syntax. These syntaxes cannot be mixed within one PINS block, but one wavetable may contain PINS blocks with different syntaxes.

Specifically, a waveform mapping file looks like this:

[ WAVETBL <wavetableName>]
[ MODECONTEXT <modeContextName>]

PINS <dutPinName>... ([<deviceCycleName>])
<waveform_specification>
...

...

The order of the statements shown must follow the example above; the various elements are identified by their positions relative to the other elements.

Italic text indicates meta-syntax, as described in Syntax conventions.

Keywords and parameters

These are the keywords and parameters in alphabetical order:

Keyword

Parameters and descriptions

MODECONTEXT

The mode context to be used for this waveform.

This keyword is optional; it is required when WAVETBL is used and ignored otherwise.

<modeContextName>: The name of the mode context, as defined in SmarTest.

PINS

The waveform mapping for a pin or pin group.

A waveform mapping file may contain any number of pin definitions.

<dutPinName>: A pin or pin group name defined in the pin configuration file of the SmarTest software. These names must be mapped to MTL pins in the Pin mapping file. There can be up to 256 DUT pin names after a PINS keyword, separated by spaces. If maintenance operations are used, waveforms for non-interruptible sequences on pins in the VEC refresh mode must have indexes between (hexadecimal) 80 and FF. (See Maintenance operations for details.)

<deviceCycleName>: This parameter should no longer be used. It was needed for Non-transparent x-modes, which we recommend you no longer use. If used, it must reference a device cycle specified by the :devCyc: keyword in the Device access file.

The parentheses are required in any case, whether a device cycle name is given or not. (The parentheses must be omitted if the WAVETBL keyword is used.)

<waveform_specification>: A specification of the waveform. The concrete form of this specification differs according to the type of syntax, as described below.

WAVETBL

Optional keyword.

The WAVETBL keyword is needed if a waveform mapping file is to be used for direct waveform mapping in place of a timing file.

If it is used, MODECONTEXT is also required and there must be no parentheses at the end of the PINS line. (See above.)

<wavetableName>: The name of this wavetable that can be referenced from the APG pattern file. The name can be any string complying with the naming conventions.

Compatible syntax

The compatible syntax offers two ways of specifying a waveform, standard and fast.

In both modes, a waveform is specified as:

<wfIndex><wfDescription><states>

The elements have these meanings:

  • <wfIndex>: A hexadecimal number that references the physical waveform index in the run-time timing settings; it must be in the range from 0 through FF.

    Note that the numbers do not need to be prefixed with 0x.

  • <wfDescription>: This is an optional sequence of the resulting waveforms. It is ignored in the waveform mapping.

    In the standard mode, each edge in this description is prefixed with the name of the edge (for example, "d1:0 d2:1"). In the fast mode, the description consists simply of the sequence of level (for example, "01").

  • <states>: The waveform that will be replaced by the corresponding index into the Timing file.

    Waveforms are described by a series of state characters. These state characters are supported:

    • For drive actions: 0 and 1
    • For compare actions: L and H
    • For both drive and compare actions: X, M, U, and Z

      You can append _ni to a state sequence to indicate that it refers to the non-interruptible version of the sequence.

The compatible syntax cannot be mixed in one wavetable with either the native or the native standard syntax.

Native syntax

In the native syntax, a waveform is specified in different ways depending on the type of pin:

  • I pins
    <wfIndex><fastWf><slowWf><states>
  • O pins
    <wfIndex><receiveWf>[<windowWf>]<states>
  • I/O pins
    <wfIndex><fastWf><slowWf><receiveWf>[<windowWf>]<states>

The elements have these meanings:

  • <wfIndex>: A hexadecimal number that references the physical waveform index in the run-time timing settings; it must be in the range from 0 through FF.

    Note that the numbers do not need to be prefixed with 0x.

  • <fastWf>: This is a description of the fast (f) waveform as a sequence of levels.
  • <slowWf>: This is a description of the slow (s) waveform as a sequence of levels.

    The fast and slow waveforms are combined to provide four levels:

    • fast 0, slow 0: vil
    • fast 0, slow 1: v3h - vih + vil
    • fast 1, slow 0: vih
    • fast 1, slow 1: v3h
  • <receiveWf>: This is a description of the receive edges a sequence of levels.
  • <windowWf>: This is a description of the window compare edges as a sequence of levels.

    This column is optional.

  • <states>: The waveform that will be replaced by the corresponding index into the Timing file.

    Waveforms are described by a series of state characters. These state characters are supported:

    • For drive actions: 0, 1, N, and . (period). N and . are considered the same.
    • For receive and compare actions: L, H, X, and . (period). X and . are considered to be different.

      You can append _ni to a state sequence to indicate that it refers to the non-interruptible version of the sequence.

The native syntax requires an HSM3G or HSM6800 card.

Native standard syntax

In the native syntax, a waveform is specified as:

<wfIndex><wfDescription><states>

The elements have these meanings:

  • <wfIndex>: A hexadecimal number that references the physical waveform index in the run-time timing settings; it must be in the range from 0 through FF.

    Note that the numbers do not need to be prefixed with 0x.

  • <wfDescription>: This is a description of the waveform as a series of pairs of edge names and levels.

    For I pins, fast and slow edges must be specified in paris, for example, "f1:0 s1:1 f2:1 s2:1". Fast and slow edges are combined as in the native syntax, described above.

    For O pins, there is a series of receive edges, for example, "r1:H, r2:L".

  • <states>: The waveform that will be replaced by the corresponding index into the Timing file.

    Waveforms are described by a series of state characters. These state characters are supported:

    • For drive actions: 0, 1, N, and . (period). N and . are considered the same.
    • For receive and compare actions: L, H, X, and . (period). X and . are considered to be different.

      You can append _ni to a state sequence to indicate that it refers to the non-interruptible version of the sequence.

The native standard syntax requires an HSM3G or HSM6800 card.

Examples

Compatible syntax

In the Pin mapping file:

...
using defaultxmode 3 
...

In the wavetable file:

WAVETBL "Compatible"
PINS pin1    # fast-mode  
"000" 000
"001" 001
"011" 011
...
PINS pin1    # std-mode  
"d1:0 d2:0 d3:0" 000
"d1:0 d2:0 d3:1" 001
"d1:0 d2:1 d3:1" 011
...

Native syntax

In the Pin mapping file:

...
using defaultxmode 3 
...

In the wavetable file:

WAVETBL "Native"
PINS pin_i  
# idx  fast  slow name
   0  "000" "000" 000
   1  "001" "000" 001
   2  "001" "001" 00Z
   3  "011" "000" 011
...
PINS pin_o 
# idx  rec   win  name  
   0  "LLL" "000" LLL
   1  "LLH" "000" LLH
   2  "LHL" "000" LHL
   3  "LHH" "000" LHH
...
PINS pin_io
# idx  fast  slow  rec   win  name
   0  "000" "000" "..." "000" 000
   1  "001" "000" "..." "000" 001
   2  "001" "001" "..." "000" 00Z
   3  "111" "111" "LLX" "000" LL
...

Native standard syntax

In the Pin mapping file:

...
using defaultxmode 3 
...

In the wavetable file:

WAVETBL "Native_std"
PINS pin_i
# idx  fast&slow                      name
   0  "s1:0 f1:0 s2:0 f2:0 s3:0 f3:0" 000
   1  "s1:0 f1:0 s2:0 f2:0 s3:0 f3:1" 001
   2  "s1:0 f1:0 s2:0 f2:0 s3:1 f3:1" 00Z
...

PINS pin_o
# idx  receive         name
   0  "r1:L r2:L r3:L" LLL
   1  "r1:L r2:L r3:H" LLH
   2  "r1:L r2:H r3:L" LHL
...
