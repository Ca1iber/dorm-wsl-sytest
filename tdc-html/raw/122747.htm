Generic Test Program Setup

Subtopics

  1. Multisite Programming Techniques
  2. Usage of Parallel Hardware (PPMU)
  3. Semi-parallel best practices
  4. Code Clean-up

To reduce test times, you should use multisite and multiport tests wherever possible and do concurrent tests if your device allows it.

Also you should allow parallel testing by setting the test flow flag "parallel_mode" in the Flow Data Editor to "on" and ticking the flag "Allow Parallel" for each testsuite in the Testflow Properties view.

In general, when setting up your test program the following are some things to consider:

  • For doing measurements, you should use the sequencer based setup and not the register based setup.

    This is because sequencer based measurements do not slow down when the number of channels increases as the sequencer program only needs to be created and downloaded to the test-processor memory once.

    Register based measurements slow down when the number of channels increases because all channels taking part in a measurement need to be programmed serially.

  • Avoid any unnecessary ABORT_TEST() or FLUSH() APIs wherever possible.
  • Make parallel measurements where possible.
  • Use the ON_FIRST_INVOCATION test method concept.
  • Design your measurements with SW triggers at the beginning and change them to HW triggers adding the right wait times, repeats and capture points.
  • Reduce WAIT_TIME to keep your settling times to a minimum.
  • Use pointers in your test program in place of constantly calling up a routine.

Test suite considerations

There is a small overhead between test suites, but on the other hand, self-contained test suites contribute greatly to the maintainability and flexibility of the test program.

Where possible:

  • Eliminate unnecessary test suites.
  • Make a reasonable judgment on how to organize test method code in test suites.
  • Minimize timing and level switches between test suites because they increase the overhead.
  • Use the PPMU for Continuity tests instead of the programmable-load, because SmarTest can optimize only one DC test using the programmable-load.

Testflow considerations

For improving the test flow there are a number of aspects to consider such as:

  • Optimizing the individual test suites.
  • Setting the test flow flags appropriately.
  • Using the test flow optimizer.
  • When sites take different routes in the test flow, execution can no longer be parallel.
    • Try to avoid branching
    • Do the branching as late as possible
    • Reduce the branch-path as much as possible
