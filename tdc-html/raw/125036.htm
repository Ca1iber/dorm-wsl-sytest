Transaction

A transaction is a well-defined sequence of information exchange and derived activities in order to contribute to a protocol specification.

From the clients' perspective a transaction is to be treated as one unit and cannot be reasonably further divided. Thus it always needs to be completed in its entirety and provides the unit for (parameterizable) reuse within a specific protocol.

A simple transaction request could be to write a specific value with one data package to a specific data register.

A higher-level protocol could also specify both a write request within a data package and an acknowledge command for confirmation within another data package. This way one 'invisible' transaction would be built. At this level of abstraction the data integrity has to be ensured by tracking the successful completion of the 'invisible' transaction.

Transactions with fixed values for transaction parameters like data register and value are considered static. If any parameter refers to variables that may change from execution to execution, the transaction is a dynamic transaction.

It's important to distinguish static transactions from dynamic transactions for throughput reasons. The V93000 uses a highly efficient caching strategy for static transactions to avoid translating content repeatedly.

Static transaction

Static transactions are transaction that will not change for any number of test executions. This means basically if you execute such a transaction several times you can exactly overlay the resulting signal as there is no significant variation in level, timing or data content.

Transactions that involve handshaking within a tolerated time interval can still be considered static if the sender tracks the complete time intervals for the receiver's acknowledge.

Dynamic transaction

Dynamic transactions are transactions with content that is subject to change from test execution to test execution, which essentially means, that the underlying bit sequence keeps also changing.

In case of dynamic transactions, the V93000 will check the sequencer program and only modify the changed vector data.

Sequenced packages that could appear in different order are dynamic, too. In order to test such protocols in a simple way, some DFT rules need to be applied:

  • The test system always acts as a master, i.e. initiates transaction execution. This is a typical use case of the V93000 software-based host interface (HIF) protocols.
  • The test system is able to fully control package (re-)ordering, i.e. the feature of the DUT to re-order packages can be turned off on demand.
