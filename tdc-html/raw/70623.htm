Topic 70623

Configuring the contents of the STDF file

If you wish to change the STDF format settings you may edit the configuration file called formatter.stdf.main.conf located in the /etc/opt/hp93000/soc_common/datalog directory. If you delete the file or delete an option, the formatter will use default values.

Note If you need another copy of the formatter.stdf.main.conf file you may obtain a new version by copying the file formatter.stdf.main.conf.template also located in the /etc/opt/hp93000/soc_common/datalog directory.

You may choose to have your STDF format settings apply only to a particular device and not to all devices tested on the tester. To do this, place the configuration file formatter.stdf.main.conf in a directory called "datalog" which exists in your device directory. As an example for the device called myDevice, the path location of the STDF format configuration setting file would be $HOME/devices/myDevice/datalog/formatter.stdf.main.conf.

The options available in the formatter.stdf.main.conf file are described below (in the order in which they typically appear in the file):

The optional section of the FTR, PTR and MPR records are logged for every record every time.

enableMPR

Boolean

True (default)

Results in output of MPR records for tests that contain individual pin results. (See the example 4 of Judge and log examples in TESTSET.)

False

Results in output of PTR records only. Multiple PTR records are written for tests with multiple pin results. Each pin value is represented in a single PTR.

PTR records, which contain pin/pin group results from the same call of TESTSET() or TEST(), contain the same test number.

When per-pin results are logged, the pin name is appended in the TEST_TXT field after a user-configurable separator character is defined.

forceAllParametricToMPR

Boolean

True

All parametric test data will be logged into MPRs. Data that would normally appear in PTRs will be logged into MPRs.

False (default)

Parametric data will be logged to the most appropriate MPR or PTR. This assumes enableMPR is set to true.

softBinNumberInterpretation

String

dec (default)

Results in displaying the software bin number string as a decimal value when populating the SBIN_NUM field of the SBR record. The soft bin number is interpreted as a base-10 number when it is translated into an integer to be logged to the STDF file.

hex

Results in converting the software bin number string from a hexadecimal value to an integer when populating the SBIN_NUM field of the SBR record. The software bin number is interpreted as a base-16 number when it is translated into an integer to be logged to the STDF file.

prefixBinNameWithBinNumber

Boolean

True

The bin number and a colon will appear before the bin name (bin description) in the HBIN_NAM and SBIN_NAM fields. For example, "1:GoodBin".

False (default)

The bin name will appear in the

HBR HBIN_NAM and SBR SBIN_NAM fields. For example, "GoodBin".

stdfFileContentLevel

String

lot

Results in one STDF file per lot.

In order for the formatter to detect where the lot boundaries are, there must be a level named "lot" in the application model. If the level that represents a lot is otherwise named, please use the alternateLotLevelName option (see Configuring the STDF file locations) to specify it.

wafer

Results in one STDF file per wafer.

auto (default)

If "auto" is selected, then there will be one file per lot for package test and one file per wafer for wafer test.

baseSiteIndex

Integer

0

The formatter will generate 0-based site numbers.

1 (default)

The formatter will generate 1-based site numbers.

generateRecordForBypassedTestSuite

Boolean

True

An STDF record is created if a test has been bypassed using any of the Bypass Test flags. If a test has been bypassed, or the test suite does not contain any test results, one PTR record for the test suite is generated.

False (default)

No STDF record is created for a test suite that has been bypassed.

resultFormatString

String

%7.9f (default)

resultFormatString specifies the ANSI C format string used by consumer programs of STDF, for example the STDFreader, to format the result, low limit, and high limit data in the PTR and MPR records for display.

If the lowLimitFormatString parameter (see below) is specified, resultFormatString does not apply to the low limit data. Similarly, if highLimitFormatString is specified, resultFormatString does not apply to high limit data.

Valid resultFormatString values include any valid ANSI C format strings. The value specified for resultFormatString determines how the STDFreader displays the values in the PTR.RESULT, MPR.RTN_RSLT, and PTR/MPR LO_LIMIT and HI_LIMIT fields.

Unless lowLimitFormatString and highLimitFormatString have been specified, the PTR and MPR fields C_RESFMT, CLLMFMT, and C_HLMFMT are also populated with the resultFormatString value.

Changing resultFormatString will affect the number of precise digits that are displayed. For example, if resultFormatString=%7.9f, the value displayed in the PTR.RESULT field may be 12.999999999. Specifying resultFormatString=%7.3f will cause the same PTR.RESULT value to be displayed as 13.0000.

lowLimitFormatString

String

%7.9f (default)

This parameter is similar to resultFormatString (above), but applies only to low limit data.

highLimitFormatString

String

%7.9f (default)

This parameter is similar to resultFormatString (above), but applies only to low limit data.

gdrSupressPadBytes

Boolean

True

Pad byte fields will not be generated in the GDRs. This allows fields to not be aligned on even byte boundaries.

 

 

False (default)

Pad bytes are included to align data fields.

gdrSupressSequencesOfGDR

Boolean

True

This disables the convention for sequences of associated GDR records. This convention inserts two fields as the first two fields of the GDR, that facilitates identification of groups of GDRs.

Each GDR is treated separately. A series may be generated, based on very large data. However, the two header fields associated with labeling and sequences will not be written in the GDRs.

 

 

False (default)

The convention for sequences is generated.

True

No GDRs are created in the STDF file for FFC and FFV results.

False (default)

FFC and FFV results are logged in GDRs after the corresponding FTRs.

disableDTROutput

DTRs are not logged to the STDF file

False (default)

DTRs are logged to the STDF file

disableGDROutput

Boolean

True

GDRs are not logged to the STDF file.

False (default)

GDRs are logged to the STDF file.

testnameIncludesTestsuite

Boolean

True (default)

The full unique test name is unchanged.

 

 

False

Eliminates everything before and including the first ":" in the full unique test name.

testnameIncludesLoopLevels

Boolean

True (default)

The full unique test name is unchanged.

 

 

False

Eliminates everything between the first and last ":" in the full unique test name. This eliminates the ":L#:" entries that detail and uniquely identify the loops. If only a single ":" appears, no action or change will result.

testnameIncludesPortsAndPins

Boolean

True (default)

The full unique test name is unchanged.

 

 

False

Eliminates everything after the first "@" symbol in the full unique test name.

Port and pin information are indistinguishable within the formatter. Therefore, there is no method of controlling these two segments of information independently.

Boolean

True

The following symbols are converted to underscores:

False (default)

Symbols are not converted to underscores.

0 (default)

1

The test name is truncated based on the specified maximum length. For example, testnameMaximumLength = 25

ignoreAppModelPART_ID

True

False (default

ftrConfig

String

Summary (default)

One FTR record is generated per functional test.

 

 

PerFailingCycle

One FTR record is generated per failing cycle.

This option is often used to view failing pins per vector for error analysis.

We recommend, with this setting, to enable FFC for the test suites of interest and to log failing pin information for every failing vector. This can be achieved by putting the "log first" test suite entry early enough to cover all subsequent failing vectors.

 

 

PerFailingEdge

One FTR record is generated per failing edge.

This setting enables very deep data analysis for debugging. It requires Fine result granularity to be enabled.

We recommend, with this setting, to log failing pin information for every failing vector. This can be achieved by putting the "log first" test suite entry early enough to cover all subsequent failing vectors.

disableTestTxtOverride

Boolean

True

False (default)

Text specified using the testtext() function replaces the current content of the Test_TXT field.

useUTCTime

Boolean

True

All timestamps are UTC times. UTC is universal time and does not include local time zones or daylight saving time adjustments.

Timestamps reflect the time that has passed since 1970-01-01T00:00:00 UTC.

 

 

False (default)

All timestamps are local times according to the internal clock of the workstation computer.

Timestamps reflect the time that has passed since 1970-01-01T00:00:00 UTC plus any adjustments for local time zone and daylight savings time (if currently in effect).

Boolean

True (default)

TSR records are generated according to the STDF standard.

 

 

False

The content of the TSR record is slightly modified and an additional record containing test times instead of test values is created. (This is incompatible with the STDF standard.)

Boolean

True (default)

The TSR.TEST_LBL field is the test suite name.

 

 

False

The TSR.TEST_LBL field is the pattern name. (This makes the records noncompatible with the standard definition.)

This setting is effective only if useStandardTSR (above) is also false.

bypassLoggingAfterFirstFailing

Boolean

True

Logging of test results in the STDF files stops after the first fail result occurs in a test. The remainder of the test suite and any subsequent test suites are not logged in the STDF file.

Note that this does not affect the execution of the tests (the test suites are executed normally, even if they are not logged) or logging in the internal EDL data log file (which includes all results that are omitted from the STDF file).

 

 

False (default)

Logging continues normally after the first fail.

*The data type referred to as variable can either be an application variable, system environment variable, or a constant.

**The value is a string beginning with any of the special prefixes "AppVar:", "SysVar:", or "Constant:" and then specifying the corresponding variable name or literal value.

For example, you could have any of the following configuration file entries:

  • MIR_LOT_ID_SRC = AppVar:MyLotID

    The formatter will populate the MIR field LOT_ID with the value of the application model variable named "MyLotID".

  • MRR_DISP_COD_SRC = SysVar:MyDispCode

    In this case, the formatter will query the system variable named "MyDispCode" and the value will get put into the MIR record in the DISP_COD field.

  • MIR_NODE_NAM_SRC = Constant:MyComputerName

    In this case the string "MyComputerName" will be the content for the MIR record in the NODE_NAM field. Every time a new STDF file is generated, it will use this same constant.

See Example configuration file for examples of how the application model variable, system variable and constant values are used.

Changes to the STDF configuration

If you make changes to the STDF configuration settings in the formatter.stdf.main.conf file, these changes will take effect at the next TestProgramStart event. However, any changes that you make to the STDF configuration settings in the global.conf file will not take effect until you shut down and re-start SmarTest.
