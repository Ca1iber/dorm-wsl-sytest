How to handle the fatal errors with SET_EXCEPTION_HANDLER

This section explains the prim error handling approach using the SET_EXCEPTION_HANDLER API.

Note Do not throw any exceptions from inside any of the Special test suites, as the handling is not compatible with the testflow executor.

With SET_EXCEPTION_HANDLER, you can set up the error handler for a fatal error in the specified API category. The API category means a group of similar or related APIs, and corresponds to the groups of the Test Method Panel's menu. You can also run your custom routine (function) as an error handler. Further, you can specify how to terminate the current testflow or test program execution. A SET_EXCEPTION_HANDLER sets up an error handler for one API category.

Note Starting with the 7.3.3.1 patch release, the crash and exception handling is easier and more straightforward. It is not necessary to register an exception handler via SET_EXCEPTION_HANDLER.

The tm_crash_as_fatal will be evaluated firstly:

  • When it is off: all affected sites are binned to the otherwise bin. Use this setting if your test method code can handle a restart of the test method process at any time (for example proper re-initialization of all your cached data) and you want to continue the lot testing.
  • When it is on: all of the not-binned sites are binned to the otherwise bin. Use this setting if you don´t allow any unhandled issue in the test program. However, the lot testing will be aborted in case an issue happens.

If SET_EXCEPTION_HANDLER is executed, it sets the error handler in a testflow globally, that means it is effective for all subsequent test method programs. Therefore, it is advisable to use this API at the beginning of the testflow or the testmethod-based test suites. You do not need to use this API in every test method program. The registered exception handler is valid until a restart of the test method process, which can be done manually in Eclipse by clicking Run > Terminate Test Method Execution, or until calling RESET_EXCEPTION_HANDLER().

You can select an API category that you want to set up as an error handler by using the case parameter (first parameter) of SET_EXCEPTION_HANDLER. The system supports the enumerator TM::EXIT_CASE for the case parameter as follows: SETUP, EXECUTE, RESULT, COMPUTATION, TEST_CONTROL, DC_TEST, GPIB, MULTI_SITE, MISC, DIGITAL_TEST, SPECSEARCH, SEQUENCER_CONTROL, COMMON_CLASS, or ALL. This category corresponds perfectly to the grouping of the Test Method Panel's menu, except for ALL.

For example, if you specify the GPIB for the case parameter, the error handler that you set will be executed when a fatal error occurs in any GPIB API.

You can select the desired error handler type from the following table using the type parameter (second parameter) of the SET_EXCEPTION_HANDLER. The system supports the enumerator TM::EXIT_TYPE for the type parameter as follows:

Error Handler Type (TM::EXIT_TYPE)

Description

ABORT_FLOW

All sites that have not been binned yet will be aborted and binned to the otherwise bin.

The testflow execution ends after the current run. It needs user interaction to restart the next testflow execution.

EXIT_FLOW

All sites of the current test suite, which are to be executed, are sent to the otherwise bin.

All other sites continue their normal flow logic. There is no termination at the end of the current testflow execution.

EXIT_TO_BIN

A failing site of the current test suite is disconnected and sent to the otherwise bin. Test suite execution continues with the other sites. There is no termination at the end of the current testflow execution.

RETURN_TO_FLOW

For the current test site the test method execution is terminated and the test suite is set to fail (continues a fail branch in case of a "run and branch" node). The test method will be called for all the remaining sites without any more special handling.

RETRY

For the current test site the test method execution is retried after the current result is logged as unreliable.

INTERACTIVE

A dialog box opens. You can select one of the above error handler actions in the dialog box interactively.

THROUGH

The test method program execution is continued even if an error occurs. Note that this is valid only for GPIB and Computation API (GPIB_XXXX and DSP_XXXX).

NONE

No exception is thrown. The previously installed exception handlers will be removed.

In addition to these, you can specify your custom function name instead of the enumerator for the type parameter. In this case, if a fatal error occurs in the specified API category, your specified custom function is called. The error handler action including how to terminate the program execution depends on the contents and the returned value of the custom function.

There are the following APIs for the SET_EXCEPTION_HANDLER.

  • RESET_EXCEPTION_HANDLER

    This resets all the current settings of the error handler.

  • GET_EXCEPTION_HANDLER

    This retrieves the current settings of the error handler.

For details of these APIs, see the API Reference.

The following shows a typical example using the SET_EXCEPTION_HANDLER API.

SET_EXCEPTION_HANDLER(TM::GPIB, TM::RETRY);
SET_EXCEPTION_HANDLER(TM::COMPUTATION, TM::THROUGH);

The first SET_EXCEPTION_HANDLER sets to retry the current test suite execution if a fatal error occurs in the GPIB API category. Then, the second SET_EXCEPTION_HANDLER sets to ignore a fatal error that has occurred in the computation API category.
