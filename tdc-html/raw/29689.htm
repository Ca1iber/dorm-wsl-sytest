UTIL_I

The member functions of the UTIL_I class makes a new utility setting data for the target utility line specified by the util member function of the ROUTING_STATUS API because the UTIL_I class is always called as the subsidiary data container of the ROUTING_STATUS API. Therefore, the UTIL_I class does not have a constructor. For related topics, see ROUTING_STATUS - (Routing).

If you described multiple Routing.util statements, the settings of the Routing.util statements are sequentially stored in the Message Concentrator and Distributor (MCD) once temporarily, then all the settings are download to the hardware in parallel when the next Execution API or FLUSH API is executed. At this time, the Execution API or FLUSH API waits the longest settling time of all the utility lines specified in the pin configuration after controlling the utility lines. For the MCD, see the manual Command Reference.

This class is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/UtilI.h.

Class definition

Member Functions:

 void on();
 void off();

Member functions

on()

void on();

This member function turns the specified utility line on.

off()

void off();

This member function turns the specified utility line off.

Important Points

  • If you described the Routing.util statements in conjunction with the Routing.uti_purpose statements before the FLUSH API or Execution API,

    (1) the settings of the Routing.uti_purpose statements are sequentially stored in the MCD, then

    (2) the settings of the Routing.util statements are sequentially stored. In the MCD, if any statements in them control the same utility line, the setting of the utility line is overwritten by the later setting.

    Then all settings are downloaded to the hardware in parallel when the next FLUSH API or Execution API is executed.

    The following example assumes the "UTI101" is controlled by both the lines "B" and "C".

    A: Routing.uti_purpose("group1").set();

    //UTI103:OFF, UTI104:OFF

    B: Routing.util("relay1").off(); //UTI101:OFF

    C: Routing.uti_purpose("group2").set();

    //UTI101:ON, UTI102:ON

    D: Routing.util("relay2").on(); //UTI105:ON

    E: FLUSH();

    The settings of the statements in the above example are stored in the MCD in the following order:

    1. "A" Routing.uti_purpose("group1").set();

    //UTI103:OFF, UTI104:OFF

    2. "C" Routing.uti_purpose("group2").set();

    //UTI101:ON, UTI102:ON

    3. "B" Routing.util("relay1").off();

    //UTI101:OFF

    4. "D" Routing.util("relay2").on();

    //UTI105:ON

    In this case, the setting data of the line "C" for "UTI101" is overwritten by the setting data of the line "B". Therefore, the FLUSH API downloads the following settings to hardware finally.

    UTI101 UTI102 UTI103 UTI104 UTI105

    ----------------------------------

    OFF ON OFF OFF ON

Example

Routing.util("util_a").on();

The member function closes the relay connected to the utility line named as "util_a".

Functional changes

  1. Introduced before SmarTest 6.3.2
