Topic 94261

Measuring the test time

About this task

In production, test times must be short and reproducible across multiple testers. To ensure this, test times must be measured and compared.

This topic only discusses standardization of test time measurement. It does not deal with the question how test time can be saved by skillful programming of the test flow.

Procedure

  1. Before the measurement, prepare your testflow to eliminate all time delay factors without affecting the purpose of the test:
    1. If you use event data logging, set all system flags referring to GDF to off. As event data logging does not affect the test time significantly, the delay caused by logging the data log stream is small, and the data formatter, which converts the log stream into STDF format, is not called when a test is running.
    2. To enable test time measurement, set the debug_mode testflow flag to 3 or 4. For more information about the debug modes, see debug_mode.
    3. For a linear testflow (no branching), set the global_overon testflow flag and the Overon flags of all stop bins to on. This setting makes the testflow continue even if a device falls into a stop bin. This ensures that the sample size for the statistical analysis is the same for all test suites.
    4. Disable the features that are not required in your test in the model file (/etc/opt/hp93000/soc/model) as they can also prolong the test time unnecessarily. For example, if differential receivers are enabled in the model file (diff entry in misc column of the IOCHANNEL section), then all timing sets must be downloaded in two versions, one for single-ended termination and one for differential mode, which can prolong the download time by up to 40 %. Similarly, initializing the wavetable takes longer for 256 waveforms than for 32.
  2. Prepare a suitable test program that contains no prober or handler calls if you are only interested in the testflow time. In principle, you can also use an existing test program that contains prober or handler calls. In this case, the total test time and the execution time of the testflow (without prober or handler calls) have different values.
    1. Load the testflow.
    2. Select the application model /opt/hp93000/soc/applic_models/sublevel_dialog. This application model is shipped with the SmarTest software. It prompts you to define how often the test program is to be executed, but contains no prober or handler calls and thus loops over one and the same device. Furthermore, sublevel_dialog does not support GDF data logging. You can use event data logging, which is independent from the application model. But even in this case you would have to customize the application model if you want to store the data log stream in a file (using MOVE_EVENT_STREAM command).
    3. Save the test program under an appropriate name.
  3. Create a workorder for the test program. The test program must be started in supervisor mode. If you start it in engineering mode, for example, from the testflow editor, execution will be slowed down by background processes, for example, of the Pattern Debug Tool.
  4. Before you run the workorder, eliminate all delay factors that are caused by the local system configuration as far as possible.
    • Save the data log to a local file, not a remote one.

      The output files of the SmarTest Data Formatter are defined in the /etc/opt/hp93000/soc_common/datalog/global.conf file. The relevant keywords are formatter.stdf.detailedFileLocation and formatter.stdf.summaryFileLocation.

      If you want to transfer the event data log stream into a file without using STDF, you must add the MOVE_EVENT_STREAM command to the sublevel_dialog application model.

      The GDF data log file is defined in the application model. The location of the GDF workorder status file depends on where the workorder directory is located.

    • Make sure that SmarTest is located on a local disc.
    • Make sure that no unnecessary processes are running on the system controller. You can view the active processes with the ps -ef shell command. In particular make sure that no SmarTest offline sessions, Java processes (this includes the jstart process) or VNC servers are active on the system controller. The first two requirements can be forced by rebooting the system controller and then starting SmarTest in supervisor mode. (Using supervisor mode ensures that none of the Java processes that are needed for engineering mode is started.) To check whether a VNC server is running, use the ps -ef | grep vnc shell command.
  5. Run the workorder. Note that the first run usually takes considerably longer than the following repetitions. One reason is that in an optimized testflow many time-consuming operations are performed only during the first run (more precisely, when the respective test suite is executed for the first time). But even in an unoptimized testflow, the first run is slower than the following ones because of certain initializations.

Results

The timing information for the complete test and for every level of the application model appears in the report window.

Example

A simple testflow comprises two test suites, cont and func, in this order. cont performs a continuity test and func a functional test. Both test suites only ask for a global PASS/FAIL result. The testflow is executed three times for two sites, resulting in six devices.

Observe the following points in the listing:

  • The # of measure. column in the TESTFLOW INFORMATION specifies the number of testflow repetitions. The number of measurements that is specified on the test suite level in the seq setup and test suite exec. rows specifies how often the respective test suites are executed. If the testflow is not optimized, this number is the number of testflow repetitions multiplied by the number of sites. The reason for this is that the two sites are processed serially in an unoptimized testflow, so that the test suite must be called twice in every testflow repetition.
  • The time spent for executing connect and disconnect sequences is not explicitly specified in an unoptimized testflow. It is included in the test suite execution time. This is in contrast to the output for optimized testflows, as explained below. In both optimized and unoptimized testflows a test suite executes a connect or disconnect sequence only if this is necessary.
  • The test suites are ordered as they are defined in the testflow file.
  • The total time for running the testflow is greater than the sum of all total test suite times. There are several reasons for this. For example, the testflow can contain nodes which are not test suites, such as Assign Value nodes.

The second figure displays the results after the testflow has been optimized:

Observe the following points in this listing:

  • An additional line set connect is specified for the test suite func, but not for cont. This shows that a connect or disconnect sequence is executed for func, but not for cont. In fact, since the tester is in the DISCONNECTED state at the start of a testflow, and the continuity test of the first test suite must be executed in the DISCONNECTED state, it is not necessary to disconnect it again. But the functional test of func must be executed in the CONNECTED state, and therefore a connect sequence must be executed at the start of the second test suite.
  • The benefit of downloading the setup data only once can be seen in the seq setup line of cont. The advantage of executing all sites in parallel can be seen in the test suite execution lines of both test suites. The parallel execution of the two sites is also reflected in the number of measurements for the seq setup and test suite execution rows (three instead of six).
