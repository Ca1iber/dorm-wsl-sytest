Calculating the buffer cycles for JMPE and RETC (and match loops)

There are three instructions that jump to a subroutine or return from a subroutine conditionally.

JMPE (JuMP on Error) and COGO (COnditional GO to)

The purpose of the JMPE (and the COGO) instruction is to perform a jump to a subroutine if at least one error has occurred in a preceding sequence of cycles. The cycles on whose global result the jump is to depend, and the vectors from which they are generated will be called the "relevant" cycles or vectors. JMPE is informed about the global outcome of the relevant cycles by an error flag which is set after every failing cycle.

Now the JMPE instruction cannot be placed immediately after the last relevant vector of interest for two reasons:

  • JMPE evaluates the error flag only after all preceding vectors have been flattened to cycle level and written to the data queue (see Data transfer from the vector area to the data queue). However, it does not wait until all these vector instances have actually been applied to the DUT. Therefore, if it would be called immediately after the last relevant vector, the first failing relevant cycle may still be in the data queue. In this case the error flag would still be unset and JMPE would erroneously infer that all relevant cycles have passed. Consequently, the jump would not be performed although it should.
  • If a relevant cycle fails, a certain amount of time is required in order to set the flag. Now suppose that the first failing cycle has been applied to the DUT immediately before the JMPE call. In this case too, JMPE would come to the erroneous conclusion that all relevant cycles have passed because the error flag has not yet been actualized.
Therefore, the evaluation of the error flag must be delayed
  1. until all the remaining relevant cycles have been shifted out of the data queue to the DUT, and
  2. the outcome of the last of these is reflected by the error flag.
This can be achieved by inserting a sufficient number of buffer cycles between the last vector of interest and the JMPE instruction. The buffer cycles can be break cycles or user cycles. In the latter case, however, they must not contain any compare actions. The required number of buffer cycles can be determined with the EPRC? query.

RETC (RETurn Conditionally)

RETC serves to return from a SVEC label to its calling label in dependence on the error flag that also controls JMPE. In contrast to JMPE, you can select whether the return is performed when the error flag is set or when it is not set. The propagation delay must be taken account of in the same way as with JMPE.

Note If you use the LMAP error map mode, FLBL ignores the RETC clearing flag for failures.

Using EPRC? to determine the number of buffer cycles

In order to determine the number of buffer cycles you must call the firmware query EPRC?. EPRC? calculates this number based on the current primary sets. It returns the number of repetitions for a user defined block of vectors. EPRC? can be called in offline mode.

The coding effort that is required to actualize the sequencer program according to the reply of EPRC? is kept to a minimum if you

  1. insert an RPTV <n>,1 instruction into your sequencer program immediately before the JMPE (or RETC) call, where <n> is as required, and define appropriate vectors for it,
  2. create a test method that
    1. calls EPRC? and stores its reply in a variable (with the FW_TASK API),
    2. extracts the number of repetitions from this variable,
    3. passes a command string

      SQPG <command_nr>,RPTV,<n>,<nr_of_repetitions>,,(<port_name>)

      (where <command_nr> is the command number of the line immediately before the JMPE call) to FW_TASK in order to overwrite command line <command_nr>.

      Note EPRC? can also be used if you want the number of dummy vectors in a new style counted match loop (MACT and MRPT sequencer instructions) to be fixed and known. Run EPRC? with a block size of 1. Then the number of repetitions returned is the number of dummy vectors that you must define for the match loop. For more details on counted match loops see Counted match loops.
