Avoiding rounding problems with different clock groups

A second option to avoid rounding problems is to put pure Smart Scale ports into different clock groups. Clock groups can only be used in a setup that contains pure Smart Scale ports.

Only pure Smart Scale ports can be included in a user defined clock group. All ports that are not included in any user defined clock group, in particular all non-pure ports, belong to a predefined default clock group.

Note Where an explicit clock group is not needed, use the default clock group. Assigning all ports to your own "default" group adds about 800μs to the test time.

Clock groups in pure Smart Scale setups are treated differently from clock groups in mixed setups, that is, setups that contain at least one non-pure port.

Clock groups in pure Smart Scale setups

If user defined clock groups are present, the operation of channels whose ports belong to the same clock group is no longer controlled by the system clock (SCLK), but by a clock group specific event clock (abbreviated "EVCK"). The period of this event clock must be an integer multiple of the clock resolutions of all ports that belong to the respective clock group, but is not required to be directly divisible by the master clock period or the clock resolutions of any port that belongs to a different clock group. Also, the SCLK period is no longer required to be directly divisible by the clock resolution of any port.

If user defined clock groups are present, the SCLK period and the EVCK periods of all clock groups (including the default clock group) are calculated as follows:

  1. The SCLK period of the specification is calculated first. It must be directly divisible by the master clock period (but not by any ECLK).
  2. The system checks for every clock group if the SCLK period calculated in step 1 is also directly divisible by the clock resolutions of all ports within the clock group. If this is the case, it will set the event clock period of this group to the SCLK period. Otherwise, the EVCK period will be calculated exclusively from the clock resolutions of the clock group ports.

    The point of this step is to keep the event clock period as short as possible. If the EVCK period does not equal the SCLK period, it must be at least 4 times as long as the SCLK period.

Note that all this holds only if at least one user defined clock group is present. If this is not the case, that is, if only the default clock group exists, then the SCLK period must be directly divisible by the clock resolutions of all ports (even if all of them are pure Smart Scale ports), and the EVCK period of the default clock group will equal the SCLK period.

Clock groups run asynchronous

If two ports belong to different clock groups, they cannot be synchronized in any way. It follows from this that a sequencing group can only be effective in such a setup when all its ports belong to the same clock group. If a sequencing group overlaps with two clock groups, it will be split by the system. Only the part that belongs to the same clock group can still be synchronized.

Clock groups and the fract() function

Defining the user periods as fractions of some global value may lead to an EVCK overflow within one clock group, because the event clock period of a clock group must be an integer multiple of the ECLKs of all ports within the group. In this case again, the fract() function can be used to calculate the least common multiple of all the ECLKs from the original fractions in the period definition (see Avoiding rounding problems with the fract() function), and thus to prevent a clock overflow.

But note that fract() is also exploited by the check in step 2 described above. By defining the period with fract() you enable the system to set the event clock period of a clock group to the SCLK period in cases where the clock resolution derived from the fract() statement divides the SCLK period directly, but the quotient of the division does not. If therefore fract() is used at least once, it should be used in all period definitions that use the respective global variable, even across clock groups.

Example

Example 1

We first show the results for a pure Smart Scale setup. In this case the clock resolutions (third parameter of CLKR) are as follows:

>  CLKR? EXACT,"mu_burst",(@@)
<  CLKR "mu_burst",12,1.5,(PortA)
<  CLKR "mu_burst",17,1.7,(PortB)
<  CLKR "mu_burst",20,1.25,(PortD)
<  CLKR "mu_burst",7.8,1.56,(PortE)

If no user defined clock groups exist, the result for the SCLK and EVCK periods is:

>  sclk? "mu_burst"
<  SCLK "mu_burst",13260
>  evck? "mu_burst",(@@)
<  EVCK "mu_burst",13260,(PortA)
<  EVCK "mu_burst",13260,(PortB)
<  EVCK "mu_burst",13260,(PortD)
<  EVCK "mu_burst",13260,(PortE)

SCLK? returns the SCLK period, EVCK? returns the EVCK periods. The SCLK period is rather large because it must be directly divisible by the clock resolutions of all 4 ports.

If PortA is in clock group "g1", and the other ports in the default clock group, one gets:

>  sclk? "mu_burst"
<  SCLK "mu_burst",480
>  evck? "mu_burst",(@@)
<  EVCK "mu_burst",480,(PortA)
<  EVCK "mu_burst",13260,(PortB)
<  EVCK "mu_burst",13260,(PortD)
<  EVCK "mu_burst",13260,(PortE)

The SCLK period is now at its minimal value (for the big testhead) because the SCLK period is no longer required to be directly divisible by any of the clock resolutions. Furthermore, this case shows, by the example of "g1", that if the SCLK period is directly divisible by the clock resolutions of all ports within a clock group, the SCLK period is taken as its EVCK period.

If both PortA and PortB are in clock group "g1", and PortD and PortE in the default clock group, one gets:

>  sclk? "mu_burst"
<  SCLK "mu_burst",480
>  evck? "mu_burst",(@@)
<  EVCK "mu_burst",2448,(PortA)
<  EVCK "mu_burst",2448,(PortB)
<  EVCK "mu_burst",3120,(PortD)
<  EVCK "mu_burst",3120,(PortE)

This example demonstrates how an appropriate grouping of the ports within the clock groups can make the test faster. By putting both PortA and PortB into the user defined clock group "g1" the maximal event clock period is 4 times smaller than in the previous setup. The disadvantage is that PortB is no longer synchronized with PortD and PortE.
