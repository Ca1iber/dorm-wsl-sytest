Uploading results with TMU_TASK and TMU_PINS

In order to post-process the measurement results, you must upload these results from the result area (in the channel memory) into a result cache (on the workstation). A result cache is a map whose values are TMU_RESULTS objects, and which admits two key types, string and integer (intended for distinguishing different pin lists and different shots). A TMU_RESULTS object can hold all result types, raw data as well as computed data, for one pair of pin list and shot. You can upload the measurement results on the TMU_TASK and on the TMU_PINS level.

The results are uploaded for all sites, but only if the latest measurement was executed after the last upload.

Using TMU_TASK

The general form for uploading the results from a TMU_TASK object with, for example, the uploadRawResults() member function, is

<task_name>.uploadRawResults(<shot_number>)

If no shot number is specified, this format will upload the results for all shots. A default result cache, which is structured by pairs of pin list (TMU_PINS object, as defined with the pin() member function of the TMU_TASK object) and shot, will be created automatically.

If, for example, two pin lists have been defined by the pin() member function of the TMU_TASK object, and two shots are executed for both of them, four TMU_RESULTS objects will be created. The keys of these objects are built up from the pin list and the shot number, in this order.

The default result cache is retrieved by the getResultCache() member function of the TMU_TASK object. The generated TMU_RESULTS objects must be accessed according to the structure of their keys, that is, the pin list must be specified before the shot number. Accordingly, the general form of accessing the results for one pair of pin list and shot is

<task_name>.getResultCache().pins(<pinlist>)[<shot_number> -1]

or

<task_name>.getResultCache().pins(<pinlist>).shot(<shot_number>)

If you specify a shot number > 0 with uploadRawResults(), the upload will be restricted to the specified shot. However, you still have to specify the shot number as in the default case.

If, for example, you want to upload only the results of shot 2, the correct format is

<task_name>.getResultCache().pins(<pinlist>).shot(2)

or

<task_name>.getResultCache().pins(<pinlist>)[1]

See TMU_TASK for more details on the TMU_TASK class.

Using TMU_PINS

The general form for uploading the results from a TMU_PINS object with the uploadRawResults() member function is

<task_name>.pin(<pinlist>).uploadRawResults(<result_cache>,<shot_number>)

When you use a TMU_PINS object for uploading, you must specify the target result cache with the uploadRawResults() function. You can specify any key or index with this cache: If the respective object does not yet exist, it will be created. As with the TMU_TASK member function of the same name, the results for all shots of the pin list in question will be uploaded by default; in this case, a TMU_RESULTS object will be created for each shot. Thus, the general form for accessing the results for one shot is

<result_cache>[<shot_number> -1]

or

<result_cache>.shot(<shot_number>),

where result_cache is the object specified in the uploadRawResults() function.

See TMU_PINS for more details on the TMU_PINS class.

Examples

Description

The following code performs TMU measurements for two pin lists. Two shots are executed for each of them.

TMU_TASK task;

ON_FIRST_INVOCATION_BEGIN();

task.pin("P1,P2").setNumShots(2).set ...;
task.pin("P3,P4").setNumShots(2).set ...;

task.setup();
task.setAsPrimary();


for(i=0;i<2;i++)
{
  task.execute();
}

ON_FIRST_INVOCATION_END();

The measurement results can be uploaded in different ways. The following code segments show 5 options to create four TMU_RESULTS objects each of which contains the measurement values for one combination of pin list and shot (on all sites).

Upload with TMU_TASK (1)

task.uploadRawResults();

TMU_RESULTS P1_P2_result_1 = task.getResultCache().pins("P1,P2").shot(1);
TMU_RESULTS P1_P2_result_2 = task.getResultCache().pins("P1,P2").shot(2);
TMU_RESULTS P3_P4_result_1 = task.getResultCache().pins("P3,P4")[0];
TMU_RESULTS P3_P4_result_2 = task.getResultCache().pins("P3,P4")[1];

In this example, the four TMU_RESULTS objects of the default result cache are transferred into four different user defined result objects.

Upload with TMU_TASK (2)

task.uploadRawResults();

TMU_RESULTS P1_P2_result_1 = task.getResultCache()["P1,P2"].shot(1);
TMU_RESULTS P1_P2_result_2 = task.getResultCache()["P1,P2"].shot(2);
TMU_RESULTS P3_P4_result_1 = task.getResultCache()["P3,P4"][0];
TMU_RESULTS P3_P4_result_2 = task.getResultCache()["P3,P4"][1];

This example differs from the first one only in that the pin string key is specified in abbreviated form.

Upload with TMU_PINS (1)

TMU_RESULTS P1_P2;
TMU_RESULTS P3_P4;

task.pin("P1,P2").uploadRawResults(P1_P2["one"],1);
task.pin("P1,P2").uploadRawResults(P1_P2["two"],2);
task.pin("P3,P4").uploadRawResults(P3_P4.shot(1),1);
task.pin("P3,P4").uploadRawResults(P3_P4.shot(2),2);

In this example, two different caches are used for the two pin lists. One cache is keyed by strings, the other by integers.

Upload with TMU_PINS (2)

TMU_RESULTS& P1_P2;
TMU_RESULTS& P3_P4;

task.pin("P1,P2").uploadRawResults(P1_P2);
task.pin("P3,P4").uploadRawResults(P3_P4);
TMU_RESULTS P12_1 = P1_P2.shot(1);
TMU_RESULTS P12_2 = P1_P2.shot(2);
TMU_RESULTS P34_1 = P3_P4[0];
TMU_RESULTS P34_2 = P3_P4.shot(2);

In this example, two intermediate result caches are used. With each of these, the uploadRawResults() function (lines 3, 4) creates two TMU_RESULTS objects, one for every shot.

Upload with TMU_PINS (3)

TMU_RESULTS result_array;

task.pin("P1,P2").uploadRawResults(result_array[0],1);
task.pin("P1,P2").uploadRawResults(result_array[1],2);
task.pin("P3,P4").uploadRawResults(result_array[2],1);
task.pin("P3,P4").uploadRawResults(result_array[3],2);

In this example, one integer keyed cache is used for all four combinations of pin list and shot.

Note The calls of the uploadRawResults() function are placed after the ON_FIRST_INVOCATION block so that this block can be identical in all examples. But in a real application they should be included in the ON_FIRST_INVOCATION block.
