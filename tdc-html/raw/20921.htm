With SmarTest, you can run a test suite that has a test method program with multi-site testing by setting up the Parallel Mode Enable testflow flag and Allow Parallel test suite flag (see Setting Flags for Parallel Execution and Allow Parallel); also, you can run a test suite that has a test method or user procedure. However, the test method program is run sequentially for all sites, such as a user procedure. This serial execution for all sites means that maximum performance is not achieved.

To achieve maximum performance, some APIs must be added to optimize your test method program. This optimization enables parallel execution of setup and test, shown in the figure below. Then, post-test processing (getting result, computation, judgment, and so on) is achieved serially for all sites.

Note Optimizing the testflow has no effect on the parallel execution of the test method program. It only affects the DC measurements in the test method program.

The following figure shows the program flow of the test method program optimized for parallel execution, and describes the behavior briefly.

In the multi-site test, you can define a block for parallel execution, called the first-invocation block. This block is executed for all sites when the program is run for the first tested site. Hence, in this block, the setup and execution APIs work in parallel for all sites. Also, you can focus some sites for site-specific setup - setup focus.

The Result APIs always work for the currently-tested single site when the program is run for each active site - query focus. They store the measurement data of all sites into the cache temporarily when the program is run for the first tested site. They return the measurement data for the currently tested site from the cache at each execution.

The following APIs control these states of test sites. That is, these APIs control which sites are addressed by the APIs that follow.

  • APIs controlling the setup focus or the query focus:
    • ON_FIRST_INVOCATION_BEGIN

      Declares the beginning of the block where you can execute setup and test for all sites in parallel, when the program is run for the first tested site.

    • ON_FIRST_INVOCATION_END

      Declares the end of the first-invocation block that is started by ON_FIRST_INVOCATION_BEGIN.

    • FOR_EACH_SITE_BEGIN

      Declares the beginning of the block where you can execute setup sequentially for all sites before parallel test.

    • FOR_EACH_SITE_BEGIN_WITH_QUERY

      Declares the beginning of the block where you can execute setup and queries sequentially for all sites.

    • FOR_EACH_SITE_END

      Declares the end of the each site loop block that is started by FOR_EACH_SITE_BEGIN or FOR_EACH_SITE_BEGIN_WITH_QUERY.

    • FOR_SEMI_PARALLEL_TEST_BEGIN

      Declares the beginning of the semi-parallel testing block that enables you to set up and execute test for the sites in semi-parallel. The semi-parallel groups are to be defined by API SEMI_PARALLEL_CONFIG ().

    • FOR_SEMI_PARALLEL_TEST_END

      Declares the end of the semi-parallel test block which is started by FOR_SEMI_PARALLEL_TEST_BEGIN.

  • APIs controlling the setup focus for a limited selection of other APIs as defined in Site-Specific Setup:
    • SET_TEST_FOCUS

      Sets the specified sites in the currently-enabled sites to setup-focus state. Also, this can simultaneously set all enabled sites except for the specified single site to not setup-focus state. Further, this returns the previous state of sites.

    • UNSET_TEST_FOCUS

      Sets the specified site in the currently setup-focused sites to not setup-focus state, and returns the previous state of the sites.

  • APIs that deliver information for controlling multiple sites:
    • GET_TEST_FOCUS

      Returns the number of the setup-focused sites and the site numbers.

    • GET_CONFIGURED_SITES

      Returns the number of sites that were set up in the pin configuration, and the site numbers.

    • GET_ENABLED_SITES()

      Retrieves information of the current enabled sites that are intended for multi-site testing.

    • GET_ACTIVE_SITES()

      Retrieves information of the current active sites that are intended for the execution of the test method program currently.

    • CURRENT_SITE_NUMBER()

      Returns the site number of the current site under test.

The APIs listed above except for GET_TEST_FOCUS, GET_CONFIGURED_SITES, GET_ENABLE_SITES, GET_ACTIVE_SITES, and CURRENT_SITE_NUMBER are ignored in single-site testing. Thus, you can develop test method programs that are compatible with both single-site and multi-site tests. These APIs for the multi-site testing make it possible to upgrade from single-site testing to multi-site testing if the need arises.

If two TIA cores are connected to one front-end module in the GP-TIA/HP-TIA, and these two TIA cores are assigned to two sites for multi-site testing, you need to select the special core identifier called the default core in the following APIs. The default core means a TIA that was assigned to each site. The default core of the TIA is defined in the pin configuration.

  • ANALOG().TIA()
  • Analog.TIA()
  • Routing.pin().connect()
