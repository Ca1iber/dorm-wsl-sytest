Topic 90370

Parameters for the ExecutionEngine test method

These parameters are available in the ExecutionEngine test method:

Parameter

Value and description

Create_Bitmap

Yes or No

Whether bitmap data is generated during the execution of the test.

If this parameter is set to No, all other parameters are unavailable.

Immediate_bitmap_data_to_file

Yes: The test method generates a failure data file for later analysis (for example, by the Bit Fail Map Viewer). The file name is generated automatically.

No: No failure data file is generated.

bitmap_format

The format of the generated bitmap:

  • Binary: A binary bitmap is generated.
  • ASCII: An ASCII bitmap is generated.

The default value is Binary.

bitmap_file_name

Lets you enter a string to name the generated BFD files. (If you do not enter a name here, the generated BFD files will get default names.)

You can enter a name along with application model variables, testflow variables, and the following reserved variables to display more information in the file name, such as wafer, site, port information and etc.. The syntax to enter a variable is ${variable name}.

  • ${time}: The file name will show the time at which the BFD file is generated.
  • ${pattern}: The file name will show the name of the memory pattern (per pin subroutines generated by the MTL compiler) that the BFD file is generated from.
  • ${label}: The file name will show the name of the start label where in the pattern to start generating the BFD file.
  • ${port}: The file name will show the name of the port that the pattern belongs to.
  • ${site}: The file name will show the site number.
  • ${test}: The file name will show the name of the test suite.

Example:

  • ${time}-Lot${LOT_ID}-Site${site}-${pattern}

If an entered variable is an application model variable and a testflow variable too, the file name will display the value of the application model variable.

If the entered string does not contain any variable, all generated BFD files will have the same name and the later one will overwrite the earlier one. You will get only the lastest BFD file.

If the string does not contain the ${time} variable, you will not get both the BFD file generated with an execution of a test and the BFD file generated with RA when you have enabled RA and set the RA_end_action parameter to "RA_end_use_BFD". The reason is the two BFD files share the same name except different time stamps. Without time stamps in their names, the later one will overwrite the earlier one.

By default, all generated BFD files are saved to: device/mts/bitmap/bitmap_data. You can change the file path of the BFD file generated with the execution of a test by using MTP_MEMORY_TEST.setBitMapFilePath(). But you cannot change the file path of the BFD file generated with RA.

If you do not enter a name here, by default:

  • The name of each BFD file generated with an execution of a test is ${time}-${label}-${pattern}-${port}-Site${site}.bfd, which does not contain wafer information.
  • The name of each BFD file generated with RA when you have enabled RA and set the RA_end_action parameter to "RA_end_use_BFD" is ${time}._port${port}_${lot}_${cassette}_${wafer}_${die_x}_${die_y}.bfd. This BFD file is binary format, which is not affected by the bitmap_format parameter.

Multi_Pattern_Result_Mode

If a main label contains multiple memory patterns, this parameter sets the mode to generate and log the address-based test results, such as fail bit count, bit map file and fail address list, for all patterns.

Available modes:

  • FIRST_FAILING_PATTERN (Default mode): Only the first failing pattern's address-based test results are generated and logged.
  • PER_PATTERN: Every individual pattern's address-based result is logged and generated. And an additional fail bit count for all failing addresses combined from all patterns is generated and logged.
  • ALL_PATTERNS_COMBINED: Combines all failing addresses of all patterns, and generates and logs a fail bit count, a failing address list, and a BFD file naming as the main label for these combined failing addresses.

    Note that this option dose not generate the individual BFD file, fail bit count and failing address list for each individual pattern.

The alternative way is using the MTP_MEMORY_TEST.setMultiPatternResultMode() member function.

Number_of_testsuite_failingcycles_to_acquire

The number of failing cycles that the test method is to acquire. A value of -1 specifies an unlimited number of failing cycles to be acquired.

In most situations there will be no reason to limit the number. However, characterization and failure analysis may require repetitive testing with large patterns (and large numbers of failures); in that situation, you may want to save time by limiting the number of failing cycles that are captured.

Result_upload_start_cycle

The number of the cycle after which capturing of data begins.

To begin with the first cycle, specify zero. To begin with cycle n, specify n-1.

Result_upload_stop_cycle

The number of the cycle with which data capturing ends.

Specify -1 to capture data until the last cycle in the pattern.

Restrict_to_channel_capture_memory_size

Yes: When the captured data reach the capacity of the channel memory, the test is stopped.

No: When the captured data reach the capacity of the channel memory, the data is uploaded and the test is repeated. In the repetition data capture starts at the point where it stopped during the previous test execution. This process is repeated until the entire test data has been captured.

Max_failing_addresses_to_reconstruct_per_pin

The maximum number of failing addresses to be reconstructed for each pin.

A value of -1 specifies an unlimited number of failing addresses to be reconstructed.

Limiting the number of addresses to reconstruct can speed up test times for characterization or failure analysis.

Fail_list_information

Pass_Fail_only: Pass/fail information is not differentiated according to whether the failed bit should have been a 0 or a 1.

Failed_for0/1: Pass/fail information is differentiated according to whether the failed bit should have been a 0 or a 1. Separate "Failed_for0" and "Failed_for1" result files (viewable by the BFM viewer) are generated.

Log_first

The number of failing addresses (in physical order) to log for each pin:

  • 0: No failing addresses are logged.
  • n (where n is a positive integer): The first n failing addresses per pin are logged.
  • -1: All failing address are logged. This can have a negative impact on performance.

The default value is 0.

Result_pins

A comma-separated list of pins and pin groups for which address-based results are to be calculated.

(@) specifies all pins. This is the default value.

RA_enabling

Whether redundancy analysis is enabled or disabled:

  • RA_disable: No redundancy analysis is performed; all other test method settings related to redundancy analysis are ignored.
  • RA_enable_standalone: The redundancy analysis is performed in a single test suite. Whether a bitmap is generated is controlled by the RA_generate_individual_bitmap parameter (see below).
  • RA_enable_begin: The redundancy analysis is begun in the test suite that contains this setting. It is continued in subsequent test suites (see RA_enable_continue and RA_enable_end, below).

    The redundancy analysis related settings in the test suite containing the RA_enable_begin statement are in effect for the entire redundancy analysis.

  • RA_enable_continue: The redundancy analysis is continued from earlier test suites with the RA_enable_begin or RA_enable_continue settings.

    The redundancy analysis related settings from test suite containing the RA_enable_begin setting are used.

  • RA_enable_end: The redundancy analysis begun in earlier test suites is concluded.

    The redundancy analysis related settings from test suite containing the RA_enable_begin setting are used.

The default value is RA_disable.

Note When RA is executed on multiple test suites, the results (including RA results) are generated on the last test suite (RA_end test suite) and DUT has to be available during execution of the last test suite. Do not specify any BIN before the RA_end test suite to ensure that both the execution is not interrupted and the results are generated correctly. For example, do not specify BIN for the false case of the RA_begin or RA_continue test suite. If you do, the RA result as well as the DUT test result cannot be generated correctly and error messages could occur.

For multisite cases, do not create RA_continue test suites in subflow branches based on pass or fail result of the previous RA test suite such as RA_begin or RA_continue.

RA_begin_action

On what bitmap to base the redundancy analysis:

  • RA_begin_start: Analysis is based only on the bitmap generated in this test suite.
  • RA_begin_use_BFD: Any previous bitmaps available available as bit fail maps (.bfd) with a matching RA service ID are loaded and the test suite is executed, which may generate new bitmaps. If the previous redundancy analysis indicated that the device is not reparable, this test suite is skipped.

This parameter is available only when RA_enabling is set to RA_enable_begin.

The default value is RA_begin_start.

RA_end_action

What to do after the redundancy analysis data have been gathered:

  • RA_end_execute: The redundancy analysis ends. If specified, repair starts .
  • RA_end_use_BFD: The generated data are saved in a bitmap file. The name of the file is a time stamp and the RA service ID (RA execution name, DUT information, and port name). In addition, a BFDL file is generated that contains the overlay bitmap file path. Its name is the RA service ID.

This parameter is available only when the RA_enabling setting is RA_enable_end.

The default value is RA_end_execute.

RA_generate_overlaid_bitmap

Whether to generate an overlaid combination bitmap of multiple memory test executions:

  • YES: An overlay bitmap is generated for all executions.
  • NO: No overlay bitmap is generated.

This setting is required when redundancy is performed over multiple testflows (that is, when the first testflow has the RA_begin_enable setting for the RA_enabling parameter). In that case, this parameter must be YES. Overlay bitmaps can also be used for results analysis.

The default value is NO.

RA_execution_name

An arbitrary string hat serves to group test suites. All test suites belonging to the same redundancy analysis, whether they are contained in the same testflow or in different testflows, must have the same value for RA_execution_name.

The default value is RAStd.

RA_config_file

The configuration file to use. You can supply an absolute path or a relative path. (Relative paths use the mts/ra/config directory within the current device directory as the starting point.) Make sure to include the .xml file name suffix.

The syntax of the configuration file is described in Redundancy analysis configuration file.

RA_counting

When the failing cell counts generated during the tests are to be summed up by the built-in RA counting algorithm:

  • Disable: No summing is performed.
  • Enable_on_concurrent_mode: The failed cells are summed each time when a bit fail map is ready after a test suite has been executed.

The default value is Enable_on_concurrent_mode.

RA_algorithm

When the redundancy analysis algorithm is to be executed:

  • Disable: The algorithm is not executed.
  • Enable_on_concurrent_mode: The algorithm is executed each time when a bit fail map is ready after a test suite has been executed.

The default value is Disable.

RA_use_counting_results

Whether to use the counting results in the execution of the redundancy analysis algorithm:

  • YES: The counting results are used. This requires that RA_counting is enabled, that RA_algorithm is enabled, and that the redundancy analysis algorithm supports using the counting results in its analysis.

    Note that any combination of concurrent and delayed enabling for counting and algorithm is supported. However, when you specify delayed counting and concurrent execution of the algorithm, the algorithm cannot leverage the counting results.

  • NO: The redundancy analysis algorithm does not use the counting results.

The default value is YES.

Fail_count_enabling

Whether the Fail bit count (FBC) is to be used to determine overall pass or fail results:

  • YES: The fail counts are used to determine pass/fail results. This setting is required to enable the limit_per_device, limit_per_DQ, and limit_per_bank parameters. If one of these limits is exceeded, the test fails, which interrupts the redundancy analysis.
  • NO: The fail counts are not used to determine pass/fail results.

The default value is NO.

limit_per_device

The maximum number of total fails for a device.

If redundancy analysis is enabled and this number is exceeded, the device is reported as unrepairable and the redundancy analysis is interrupted.

If the value is negative, no limit checking is performed.

The value is a long integer.

This parameter is available only if Fail_count_enabling is YES.

limit_per_DQ

The maximum number of total fails for a data pin.

If redundancy analysis is enabled and this number is exceeded, the device is reported as unrepairable and the redundancy analysis is interrupted.

If the value is negative, no limit checking is performed.

 

The value can be a long integer or a list of long integers. (See limit_per_device, above.)

This parameter is available only if Fail_count_enabling is YES.

limit_per_bank

The maximum number of total fails for a bank.

If redundancy analysis is enabled and this number is exceeded, the device is reported as unrepairable and the redundancy analysis is interrupted.

If the value is negative, no limit checking is performed.

The value can be a long integer or a list of long integers. (See limit_per_device, above.)

This parameter is available only if Fail_count_enabling is YES.
Note No results (bitmap information) will be generated if more than 1,000,000 device maintenance (refresh) events happen during pattern execution. An error message will be shown instead. Testflow execution will not be interrupted.

Functional changes

  1. Introduced before SmarTest 6.3.2
  2. MTP 2.6.5: New test method Execute_RA
  3. MTP 3.0.1: The ExecuteEngine test method replaces the Memtest test methods.
  4. MTP 3.0.3: (MTP on SOC 103.0.0.) ExecutionEngine supports redundancy repair analysis.
  5. MTP 3.0.3: (MTP on SOC 103.0.0.) Added bitmap_format parameter.
  6. MTP 3.0.4: Added Log_first parameter.
  7. MTP 3.1.6: (MTP on SOC 103.3.0) New parameter Multi_Pattern_Result_Mode is added.
  8. MTP 3.2.1: The MTP on SOC and MTP on HSM two software are combined into one software called MTP software.
  9. MTP 3.2.1: Obsoletes the parameters, Device_output_pin_oring, RA_blocking, RA_timeout, and RA_generate_individual_bitmap.
  10. MTP 3.2.2: Add a new parameter bitmap_file_name.
  11. MTP 3.3.2: Obsoletes the Enable_on_delayed_mode option for both the RA_algorithm and RA_counting parameters.
