Overview of the SLIMbus solution

The Serial Low-power Inter-chip Media Bus (SLIMbus) is a standard interface between baseband or application processors and peripheral components in mobile terminals. The interface supports many digital audio components simultaneously, and carries multiple digital audio data streams at differing sample rates and bit widths.

SLIMbus tests as synchronized protocol tests

Testing of SLIMbus is implemented in SmarTest within the Protocol Aware (PA) framework as a synchronized protocol test. In contrast to standard HIF protocol testing, the required protocol (including the timing and level setup) is predefined and should not be modified by the user.

The protocol assignment must be established manually. The protocol comprises two boot frames, one for dynamic booting and one for user defined booting, and one communication frame.

Note Do not confuse a PA frame, which is a SmarTest construct that provides a transaction template, with a SLIMbus frame, which is a substructure of a SLIMbus superframe. In this overview, the term "frame" will always refer to PA frames. Similarly, the term "parameter value" will always refer to parameters of PA frames, not to the parameters of SLIMbus messages; and the term "transaction" will always refer to transactions of a PA test.

The communication frame has one parameter, which serves as a container for one SLIMbus superframe, that is, its length is 6144 bits. The size of some boot frame parameters is even greater. Furthermore, the value of the communication frame parameter must represent the extremely variable internal structure of a superframe.

For these reasons the write, read, and capture transactions of a SLIMbus protocol test are not, as with standard HIF protocol testing, explicitly coded in the test method, but are created programmatically by the translate() member function of the SlimBusController TM API, which is the main tool for programming a SLIMbus test. In particular, the translate() function converts the content of the respective superframe into a parameter value of the communication frame. The parameter values for the boot frames are either determined automatically (dynamic booting), or they are directly defined in an external file (user defined booting).

The transactions that are defined by the SlimBusController API are first converted into sequences of state characters. In a second step, these state character sequences are translated into sequences of waveforms according to the statemap sections in the predefined wavetable. Note that the test method uses the state characters that are defined in the predefined timing for this translation. Therefore this timing must not be modified.

Like all PA tests, a SLIMbus test requires that

  • the start label is a multiport burst,
  • all ports that take part in the test except the protocol port are present in this multiport burst,
  • the protocol (= SLIMbus) port is omitted from this burst.

Protocol definitions and test method library

After the installation, the protocols are located in the /opt/hp93000/protocols/SW/SLIMbus/<version_no>/protocols directory. To make them available to SmarTest, import them into the current device by right-clicking on Protocols in the Test Program Explorer, and then selecting Import....

The SLIMbus library is stored by the installation in the /opt/hp93000/protocols/SW/SLIMbus/<version_no>/library directory. In order to make it available to SmarTest, copy it into the directory where your test method is located.

Accessing the test results

The test results (both compare and capture results) must be prepared for further processing with the decode() function of the SlimBusController API. This function also integrates the results into the Superframe Viewer file (if this file has been created, see Using the Superframe Viewer). In case of a multi-site test, results are site specific; if creation of the Superframe Viewer file is activated, a separate file is created for every site.

The capture results can be presented in a message oriented or a data channel oriented format. In the first format every result is paired with its message; the message is identified by its type and a running number. In the second format, the results of every data channel are returned in one value list across superframes.

External input and output files

The content of a superframe is usually defined in an external file, the so called sequence file (see Displaying and editing the sequence file). SmarTest provides a special editor with which you can view and edit the sequence file. If you specify only the file name, SmarTest assumes that the file is located in the xml subdirectory of the current project; if you have placed it elsewhere, you must specify the absolute path.

If you want to customize the boot process, you must specify an external boot file in the test method. This file is only needed for the data pin; the input for the clock pin is defined in the PA frame for user defined booting.The file must already be coded with state characters. The state characters used must be present in the statemap section of the predefined wavetable for the data pin. If you specify only the file name, SmarTest assumes that the file is located in the vectors/BootPattern subdirectory of the current device; if you have placed it elsewhere, you must specify the absolute path. Note that user defined booting is mainly intended as a fallback solution and for debugging.

You can cause SmarTest to store the state character sequence that was generated from the sequence of superframes in a file of its own. This file is located in the report subdirectory of the current device. You then can view the state characters with a special tool, the so called Superframe Viewer (see Using the Superframe Viewer). The Superframe Viewer displays the state character sequence in such a way that you can recognize in detail how it represents the superframe structure. Moreover the Superframe Viewer file also contains the test results, and in fact the Superframe Viewer provides the easiest access to these results, especially the compare results, which must otherwise be retrieved in the test method with hasFailed(), a member function of the controller, superframe, and message objects.
