Using execution contexts

Execution contexts allow you to run subsets of one or even more than one multiport burst independently and in parallel. Such an execution context consists of a port list that is associated with a name. In order to activate it, you must specify the name when you start the test. Generally, the ports of the context must be a subset of the ports in the current start label.

Another option to execute only a proper subset of the ports in a multiport setup is to define an incomplete multiport burst (see Incomplete multi-port setups). Execution contexts, however, are more flexible, because you do not have to create a new multi-port burst for every port subset. But their main advantage is that they allow you to execute different sequencer tasks in parallel, which is not possible with an incomplete multi-port burst.

Thus you can, for example, first select a multi-port burst mu_burst1 as the start label and start an execution context c1 with a subset of the ports in mu_burst1, then change the start label to the multi-burst mu_burst2 and start an execution context c2 referring to mu_burst2. If c1 is still running when c2 is started (and all boundary conditions are satisfied), both contexts will then run in parallel. This example will be shown in detail below.

Note Incomplete multi-port bursts and execution contexts do not exclude each other. You can also define and run an execution context for a port subset of an incomplete multi-port burst.

The usage of execution contexts is subject to several restrictions. This holds in particular for systems that are not pure Smart Scale systems, but contain also DC Scale channels.

Restrictions

The usage of execution contexts is restricted by the following conditions:

  • An execution context can only be run if all its ports are included in the current start label.

    Note that protocol ports are an exception to this. Protocol ports are not allowed to occur in the start label. This also holds if the protocol port is contained in a context. For details see Independent protocol test.

  • Two execution contexts can run in parallel only if they share no channel.

    If an execution context A is running and you try to start another execution context B that shares a channel with A, an error message to this effect will be issued, and B will not be started. A will continue to run.

  • Two execution contexts can run in parallel only if the context that is started first is executed in with SQST RUN (or the test method API START_TEST()). If it is started with FTST() (or one of the test method APIs FUNCTIONAL_TEST() or EXECUTE_TEST()), the second context will only be started after the first one has returned its global PASS/FAIL result.
  • Recalculation of the master clock period will stop all user defined sequencer tasks. Therefore, changes of the primary timing involving such a recalculation must be avoided between the start of two execution contexts that are to run in parallel.
  • If two execution contexts both contain a port with a DC Scale channel, they cannot be run in parallel.

    If an execution context A that contains a DC Scale channel is running, and you try to start another context B for which this also holds, then an error message to this effect will be issued, and B will not be started. A will continue to run.

Related firmware commands

An execution context is defined with the SQEC command and started by adding its name to the command/query that executes the test (for example FTST? or SQST RUN). Execution contexts are deleted with the SQRC command.

There are two queries that inform about the execution contexts that were started last. SQLC? retrieves this information per port, SQSC? returns it over all ports.

Related Test Method APIs

Execution contexts can be programmed with the following APIs:

SEQUENCER_CONTEXT

SEQUENCER_CONTEXT_ITEM

INDEPENDENT_TEST (Protocol Aware)

Example

For a test method example, see the description of SEQUENCER_CONTEXT.

The following firmware example first displays the current start label, then shows its definition and that of another multi-port burst, then defines two execution contexts each of which is related to one of the two multi-port bursts, and finally executes these two contexts, changing the start label after starting the first context:

> SQSL?
< SQSL "mu_burst1"
> SQLB? "mu_burst1",MPBU,(@@)
< SQLB "mu_burst1",MPBU,6,7,,(PA)
< SQLB "mu_burst1",MPBU,6,7,,(PB)
< SQLB "mu_burst1",MPBU,10,11,,(PC)
< SQLB "mu_burst1",MPBU,4,5,,(PD)
> SQLB? "mu_burst2",MPBU,(@@)
< SQLB "mu_burst2",MPBU,3,4,,(PX)
< SQLB "mu_burst2",MPBU,8,9,,(PY)
> SQEC "c1",(PA,PD)
> SQEC "c2",(PY)
> SQST RUN,"c1"
> SQSL "mu_burst2"
> SQST RUN,"c2"

If c1 has not yet been finished when c2 is started, c1 and c2 will now run in parallel, provided that the ports PA, PD, and PY are disjunct, and at least one of the two contexts contains only Smart Scale channels.

Note also the following points in this example:

  • The primary timing has not been changed between the start of c1 and c2. If it had, then most probably the master clock period would have been recalculated, and this would have stopped c1.
  • The first context is started with SQST RUN, not FTST?. This is required for parallel execution; using FTST? would block the firmware interface until execution of c1 is finished and FTST? has returned its global PASS/FAIL result.
  • If both contexts contain DC Scale channels, c2 will not be started, and an error message will be issued. c1 will continue to run.
