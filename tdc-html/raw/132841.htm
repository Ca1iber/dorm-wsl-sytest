SmarTest project configuration

The following section gives some background information on Eclipse projects and also some hints about setting up projects in the SmarTest Eclipse environment.

Projects vs. workspaces

Efficient use of Eclipse requires an understanding of the differences between Projects and Workspaces and also how they are used together. A lack of this understanding can easily lead to increased effort, frustration, and lost work.

Projects

Whenever you do any new development work in Eclipse you first create a project. A project is the base unit for building and deploying code in Eclipse. Physically, a project is also a directory on the file system where your code is stored (along with some meta-data). Stated another way, projects are "what" you work on in the Eclipse world. It is also worth noting that Eclipse projects stand alone: you cannot nest projects within projects in Eclipse.

There are many different types of projects in Eclipse, including built-in types such as C++ and Java projects, and custom types such as SmarTest Device projects. Each of these has certain characteristics, but they all adhere to the basic Eclipse project concepts.

In addition to these inherent characteristics, projects also have user-modifiable properties which are stored in the project directory and which persist between working sessions.

Workspaces

Workspaces, in contrast are where you do your work on projects. All project work in SmarTest takes place inside of a workspace. You may have more than one workspace, each with different tools and materials (though some may be shared between workspaces), and you have to keep them clean and organized.

Like projects, workspaces are also directories on the file system. In SmarTest, workspaces a located by default in your $HOME directory, but you can create them in other locations as well.

Workspaces contain meta-data, preferences, references to projects, and even project code itself. That said, while you can place actual code in an Eclipse workspace, it is not a recommend practice. Sooner or later you will need to clean (or delete) a workspace and you Do not want to lose precious code in the process.

A better practice is to reference projects from your workspace. This means that the project code resides in its own project directory, separate from the workspace. You then simply import the project into the workspace (this happens by reference), but you Do not physically copy it there.

Another benefit of not storing your project code inside of workspaces is that it makes sharing projects more straightforward. Projects are always outside of workspaces, you always gather the necessary projects into your workspace by reference. Workspace configurations are persistent, so once you create a workspace, its particular set of projects will be loaded whenever you open it.

Because workspaces are not necessarily backward-compatible between SmarTest (or Eclipse) releases, one best practice is to use separate workspaces for different major releases of SmarTest.

It takes some getting used to at first, but once you become familiar with how projects and workspaces function, their efficient use will be come second nature.

SmarTest specific projects

  • Device directories

    SmarTest device directories that have been created with Eclipse or changed to from Eclipse (using change device) are also Eclipse projects. They have the same metadata and preferences information as other Eclipse projects. This means that when you share your SmarTest device directories you are also sharing your preferences.

  • Test method directories

    Universal Test Methods (UTMs) are handled by Eclipse like standard C++ projects. The Test Method source code resides outside of the device directory and only the Test Method shared library is copied into the device directory. For details, see ADD LINKS.
