Generic Recommendations

Following these rules will save Re-Work and Test time so they should be done from the beginning

  • All test applications C++ code should now be using UTM's, so familiarity with import/export of UTM's into a test program is key.
  • For RF/SOC programming the use of Hardware triggering should be included from the beginning, as it will definitely be needed in later stages of program development.
  • There is no need to use external Timer.h or custom timer programs in your test program development. SmarTest now has API's and built in tools for test time measurement.
  • Using a version control system for test program development (svn or subclipse for example) is highly recommended, especially for team projects.
  • The use of Analog API's for Mixed Signal and RF tests are highly recommended as it makes code easily reusable, and easier to modify.
  • Analog data acquisitions should be done in a single block whenever possible, and Analog burst upload should be used in conjunction with multiple captures.
  • SmartCalc structure should be added to the code from the beginning to take advantage of Hidden upload and multi threading. IE. all data upload, calculations, and testing should be contained in one function. No use of MEAS_DEF.getComplexWaveform should be in test program, instead use SMC_GET_COMPLEX_WAVEFORM(); in conjunction with HW TRiggering.
  • All methods need to be written multi-site ready. If you do a _grep ON_FIRST_INVOCATION and get no hits, its not a viable method. It does not matter if the program is never planned to be more than one site.
  • All methods need to be written with Multiport in mind.; Multiport is a key driver for CCT and other TTR techniques, therefore all patterns should be assigned to a specific port and not the "@" port during the conversion process.
  • Before code is written, authors must ask themselves, whats the best way to implement the requested test on OUR platform. Without a firm understanding of the above, coding should not start.
  • Whenever possible and prudent, there should not be multiple methods for production and characterization, the characterization method should also be capable of being sized down, via a method flag, to production duty. This reduces the work required to optimize and creates a more readable and usable piece of code.
  • Golden rule: Do not use APIs or FW commands if you have already retrieved information previously. For example, there is no need to query the contents of a pin group in each suite if the pin group wont change& make the results a global variable or similar.
  • D2S should be used whenever variable register writes are done
  • Limits should all be done with V93kLimits.
  • Data log profiles should be used to set all flags (testflow, system, test suite) this allows for consistent and easy to manage flags settings. They should also be used to enable dynamic/diagnostic data logging which can save test time.
  • Digital patterns should use Physical Waveforms only, and UMM only.
  • Setup Master Files should be used to break down the Testflow, Timing, levels, Vector, analog control, and limits files. This should be used in conjunction with a version control system (CVS/SVN).
  • For Upload of Captured Digital Data: the Hidden Error Map should be used.
  • Use RH5 and Use Z800 Workstations. No reason to slow down the test time because of old HW/SW. For Z800/Z400 workstations, make sure the power management is switched off.
  • Use "Label Per Site"
  • Supports shared pins with 6.5.3 [before feature was not usable]
  • Consider to use it for Trim/Fuse burn test instead of vector label edit per site
  • Consider to use it for Heterogeneous test
