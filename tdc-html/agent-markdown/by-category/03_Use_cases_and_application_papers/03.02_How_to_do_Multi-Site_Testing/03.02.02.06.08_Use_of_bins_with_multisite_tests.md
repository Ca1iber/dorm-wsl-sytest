# Use of bins with multisite tests

Using bins with multisite tests is basically the same as with single-site tests. You can use stop bins (good or bad bins) and otherwise bins, see [Bins](<../../02_System_reference/02.08_Setup_and_Result_Tools/02.08.04.32.01.02.06_Bins.md>).

Each bin has its own out of control (OOC) rules. These rules are identical for all sites, but in a multisite environment they are evaluated for each site individually.

## General rules

- Never define one bin with the same number but different properties, for example, reprobe (for more information, see Reprobing section below), bin_description, overon.
- Select one of the following bin configurations for your binning strategy in one flow:

  - Testflow bins
  - Test table bins.

Do not mix both solutions in one flow. If you mix them, the testflow bin overwrites test table bins, which are set by the [TMLimits](<../../02_System_reference/02.07_Test_Method_Reference/02.07.04.01.250_TMLimits.md>) API.

- The [SET_MULTIBIN()](<../../02_System_reference/02.07_Test_Method_Reference/02.07.04.01.212_SET_MULTIBIN.md>) API requires a stop bin or floating bin in the testflow.

For details on specific binning rules for multibins, see [Use of multibins](<03.02.02.06.07_Use_of_multibins.md>).

- For SmartCalc applications:

Use the [SMC_TEST()](<../../02_System_reference/02.07_Test_Method_Reference/02.07.04.01.231.45_SMC_TEST.md>) API for binning.

We recommend using the [SMC_TEST()](<../../02_System_reference/02.07_Test_Method_Reference/02.07.04.01.231.45_SMC_TEST.md>) API with test tables.

If you use the [SMC_TEST()](<../../02_System_reference/02.07_Test_Method_Reference/02.07.04.01.231.45_SMC_TEST.md>) API with the limit object instead of the test table limit, you must define the limit.

For more information, see:

  - [Working with test tables](<../../02_System_reference/02.10_Data_Logging/02.10.01.08.03_Working_with_test_tables.md>)
  - [Working with TMLimits](<../../02_System_reference/02.10_Data_Logging/02.10.01.08.02_Working_with_TMLimits.md>)
  - [LIMIT](<../../02_System_reference/02.07_Test_Method_Reference/02.07.04.01.126_LIMIT.md>)

## Reprobing

Each bin can carry an overon flag or a reprobe flag.

- If the overon flag is set, the testflow continues even if a device falls into a stop bin.
- If the reprobe flag is set, the device will be tested again after it has been binned.
- If specified within the application model, a reprobe action can be performed (reconnecting the device, for example).

In a multisite test, reprobing is not done before all sites have been binned. The system automatically reprobes all sites. So, it might happen that sites that previously passed, now fail or even get damaged.

You should consider carefully whether reprobing is worth the time (for example, you might specify within the application model that reprobing only is done if more than half of all sites fail).

Note When one site gets binned, the sequencers are switched off for all sites (all test system channels). So all channels (drive) go to tri-state. This is one more reason for using self-contained test suites. You can also avoid early binning by implementing a "soft-binning strategy"; see [Solution I - Overon Enable](<03.02.05.01.01_Delay_Binning_I__Overon_Enable.md>) and [Solution II - Assign Variables to Failing Parts](<03.02.05.01.02_Delay_Binning_II__Assign_Variables_to_Failing_Parts.md>) for examples of this strategy. A user procedure can disable the site to be binned, store the result and move the binning process to the end of the testflow.

## Using the RLYC command

  CAUTION When using this command in a multisite configuration, you must be careful as it can lead to incorrect binning and possible corruption of devices.

A [RLYC](<../../02_System_reference/02.06_Command_Reference/02.06.02.02.206_RLYC__RLYC__-__ReLaY_Control.md>) command that is issued after the testflow already binned one device does not only affect the still enabled device, but all devices.

At the end of the testflow, the still enabled device is disconnected and the relays are opened. But the already binned device is marked as disconnected in the shared memory already and is thus not disconnected again and the relays stay closed! This can lead to incorrect binning and possibly corruption of devices due to insertion with active levels as the relays are in a different state than expected.

Example

```
   site#1     site#2
     | |
   test1      test1
     | |
   test2      test2
   (PASS)     (FAIL) -> binned
     |        site#2 stops here
   test3      UI status is "disconnected"
   (PASS)
 |
   test4
   (PASS)
 |
   RLYC ON   <- this RLYC commands affect both site#1 and site#2(disabled site)
```

After execution of the RLYC command for site#2, the user interface still recognizes site#2 is disconnected because direct execution of the firmware does not update the user interface status. But the actual relay setting has changed to "connect" status. The relays of site#2 which are directly controlled by the firmware command are never disconnected by SmarTest at the end of the flow because the user interface status considers them to be disconnected.

Programming tip: Replace the FW_escape commands by a user procedure or test method doing a PSFC (see [PSFC, PSFC? - (Parallel Setup FoCus) (Jump Template)](<../../02_System_reference/02.06_Command_Reference/02.06.02.02.191_PSFC__PSFC__-__Parallel_Setup_FoCus.md>) ) to the enabled sites only before doing RLYC and then switching back to PSFC ALL.
