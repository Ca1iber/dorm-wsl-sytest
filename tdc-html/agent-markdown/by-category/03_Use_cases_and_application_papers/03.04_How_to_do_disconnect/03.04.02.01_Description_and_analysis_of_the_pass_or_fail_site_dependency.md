# Description and analysis of the pass or fail site dependency

In multi-site testing, some devices require [Keeping the Clock Alive](<../../02_System_reference/02.11_Data_Conversion_and_Bridges/02.11.02.02.06_Keeping_the_Clock_Alive.md>). The reasons which lead to a pass or fail site dependency issue for these devices are discussed here.

While performing multi-site testing, the standard disconnect sequence cannot deal with the devices that require a continuously running clock.

The situation is that if, after running test suite "A", a device fails and goes into the bad bin, in the following test suite "B", other devices at the sites which have remained enabled will also fail. This behavior is called the pass or fail site dependency issue in multi-site testing.

Reasons for failing are explained below:

- The test suite is not self-contained ([Self-contained test suites](<../03.02_How_to_do_Multi-Site_Testing/03.02.02.06.05_Self-contained_Testsuites.md>) are independent of the output from previous test and provide the device with all the required initializations).
- When the bad device is binned out, SmarTest executes the [Standard disconnect sequence](<03.04.01.02_Standard_disconnect_sequence.md>).

This sequence issues an SQST OFF firmware command, which is applied to all the sequencers across all sites and sets all pins to a High-Z state. As a result, the PLL keep-alive clock in the device is interrupted, or a control pin of the device (which needs to stay at a certain state) might be set to a different level; consequently, devices in other sites lose their state.

Given the facts above, you need choose other disconnect methods.

If you require any shared digital pins (for example trigger pins for analog instruments), you need distinguish them from non-shared pins in your disconnect sequence because shared pins typically need to stay connected until binning of the last site happens (for example at the end of the test flow).

## Example

A typical example for the pass or fail site dependency issue:

- One dual-site test flow has both sites enabled.
- f1 and f2 are two successive functional tests in the test flow.
- When any site fails in f1, the other site will fail in f2.
