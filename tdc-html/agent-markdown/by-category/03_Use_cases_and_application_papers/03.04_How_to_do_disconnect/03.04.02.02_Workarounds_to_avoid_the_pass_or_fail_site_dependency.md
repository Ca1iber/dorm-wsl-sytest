# Workarounds to avoid the pass or fail site dependency

The recommended solution to avoid [the pass or fail site dependency](<03.04.02.01_Description_and_analysis_of_the_pass_or_fail_site_dependency.md>) for Pin Scale systems is the [Multibin SmartDisconnect test suite](<03.04.01.05_Multibin_SmartDisconnect_test_suite.md>) or the [Special test suite bin_disconnect](<03.04.01.04_Special_test_suite_bin_disconnect.md>) for devices which require [Keeping the Clock Alive](<../../02_System_reference/02.11_Data_Conversion_and_Bridges/02.11.02.02.06_Keeping_the_Clock_Alive.md>). However, the following tips show workarounds for Pin Scale systems.

## Making test suites self-contained

The most straightforward workaround is to make all the test suites in your test flow [Self-contained](<../03.02_How_to_do_Multi-Site_Testing/03.02.02.06.05_Self-contained_Testsuites.md>). Non-self-contained test suites are one reason for causing this issue, as explained in [the pass or fail site dependency](<03.04.02.01_Description_and_analysis_of_the_pass_or_fail_site_dependency.md>).

Pros:

- Test suite can be placed at any location in the test flow.

Cons:

- A significant test time penalty may arise for devices that require PLL keep-alive as each test suite needs to include a full initialization and the synchronization to the clock pin.

## Workarounds for non-self-contained test suites: Using global_overon flag and overon bins

Setting the test flow flag global_overon to "on" and activating the Overon flag in the relevant bin will delay the binning of a failing device to later bins in the test flow.

Pros:

- Easy to do. Setting the global_overon flag allows the test flow to continue after stop bins that are marked as overon bins. Binning happens at a later stage in the test flow.

Cons:

- Usually introduces a test time penalty (more information in [Overon Enable](<../03.02_How_to_do_Multi-Site_Testing/03.02.05.01.01_Delay_Binning_I__Overon_Enable.md>)) because failing devices still need to run through subsequent test suites.

## Workarounds for non-self-contained test suites: Delaying binning with test flow variables

This workaround assigns variables to failing sites and checks them later in the test flow so that failing sites needn't run through all the test suites the same way as passing sites do.

Pros:

- No big test time penalty, and flexible when compared with the overon method.

Cons:

- If the rest of your test flow contains several match loops, time is wasted waiting for failing sites within the match loops.
- Use of the variables with the overon flags and user procedure could result in a complex test flow. For more details, refer to topics:

  - [Delay Binning II - Assign Variables to Failing Parts](<../03.02_How_to_do_Multi-Site_Testing/03.02.05.01.02_Delay_Binning_II__Assign_Variables_to_Failing_Parts.md>)
  - [Delay Binning III - Assign Variables and Activate Overon Enable](<../03.02_How_to_do_Multi-Site_Testing/03.02.05.01.03_Delay_Binning_III_-_Assign_Variables_and_Activate_Overon_Enable.md>)
  - [Delay Binning IV - Assigning Variables & User Procedures](<../03.02_How_to_do_Multi-Site_Testing/03.02.05.01.04_Delay_Binning_IV_-_Assigning_Variables___User_Procedures.md>)
  - [Delay Binning V - user procedure instead of test suite](<../03.02_How_to_do_Multi-Site_Testing/03.02.05.01.05_Delay_Binning_V_-_user_procedure_instead_of_test_suite.md>).

## User-defined disconnect sequence: Removing SQST and DLSO

For devices that Do not use shared pins in a multi-site test, this workaround can solve the site dependency issue while keeping PLL alive.

Pros:

- Allows replacing [Standard disconnect sequence](<03.04.01.02_Standard_disconnect_sequence.md>) with a [user defined sequence](<03.04.01.03_User-defined_disconnect_sequence.md>) just by removing the sequencer commands SQST and DLSO.

Cons:

- Hot-switching of AC-relays takes place because neither SQST nor DLSO are executed to put the relevant channels into high impedance. This could potentially damage both the DUT and the mechanical relays on the channel cards.
