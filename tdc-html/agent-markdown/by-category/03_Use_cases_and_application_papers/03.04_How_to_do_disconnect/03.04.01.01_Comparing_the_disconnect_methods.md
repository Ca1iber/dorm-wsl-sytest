# Comparing the disconnect methods

## Differences of doing disconnect when different disconnect methods are coexistent

- When both disconnect.user_def and bin_disconnect are defined, to do the disconnect only bin_disconnect will be executed after binning. This disconnect sequence is defined differently from the standard disconnect sequence or the user-defined one.
- If a disconnect.user_def is defined, it will be executed for the [DISCONNECT](<../../02_System_reference/02.07_Test_Method_Reference/02.07.04.01.41_DISCONNECT.md>) API, or the disconnect button in Eclipse.
- If a disconnect.user_def is not defined, the standard disconnect sequence will be executed for the [DISCONNECT](<../../02_System_reference/02.07_Test_Method_Reference/02.07.04.01.41_DISCONNECT.md>) API, or the disconnect button in Eclipse.
- When both bin_disconnect and the Multibin SmartDisconnect test suite are defined,

  - the Multibin SmartDisconnect test suite takes precedence for disconnect sequences within the flow and
  - for the final disconnect with all sites binned, bin_disconnect is performed.
We recommend therefore, programming a clean solution defining only the Multibin SmartDisconnect test suite and, at the end of the test flow, inserting a test suite in order to perform a clean disconnection of the remaining (passing) sites.

## Special disconnect methods

The [Standard disconnect sequence](<03.04.01.02_Standard_disconnect_sequence.md>) works for single-site and multi-site testing for most standard devices, except the following cases:

- If the test suites within a test flow require a running clock or if the control pin of a device has to be kept at a certain state.
- If you need to disconnect different utility lines among the test suites within a test flow.
- If you need to disconnect power pins separately.

For these exceptions, SmarTest provides a number of special methods, including using the overon flags (the [global_overon](<../../02_System_reference/02.08_Setup_and_Result_Tools/02.08.04.32.01.02.07.01_Alphabetical_list_of_flags.md#_342556__row_global_overon>) test flow flag and the bin [Overon flag](<../../02_System_reference/02.10_Data_Logging/02.10.03.03.05_Overon_flag.md>)), [User-defined disconnect sequence](<03.04.01.03_User-defined_disconnect_sequence.md>) and the [special test suite bin_disconnect](<03.04.01.04_Special_test_suite_bin_disconnect.md>).

If the test suites are not [Self-contained](<../03.02_How_to_do_Multi-Site_Testing/03.02.02.06.05_Self-contained_Testsuites.md>), the overon flags have to be enabled. However, in some cases this is not appropriate. For example:

- Some failing devices need to be disconnected, to avoid causing damage to testers in the subsequent test suites.
- The throughput may be reduced, if the failing devices keep running in match loops.

Given these conditions, you can use the user-defined disconnect sequence, or the special bin_disconnect test suite to solve the exceptional situations that cannot be covered by the standard disconnect sequence.

For this purpose, you can run a series of firmware commands in a file, or in a test method. However, you need know exactly what each firmware command will do.

A user-defined disconnect sequence can disconnect the site related power pins separately through a pin list. It can also be used to keep the clock alive in Pin Scale systems. However, to achieve a running clock [an additional test suite](<03.04.01.03.02_Implementing_a_conditional_final_disconnect_with_disconnect.user_def.md>) in front of each bin needs to be used, together with the user-defined disconnect.

Using the special test suite bin_disconnect, by defining different disconnect sequences you can control the disconnect sequence of different utility lines in the test suites.

Also the most attractive usage of bin_disconnect is to keep the clock alive or maintain the control pin of a device at a certain state (for Pin Scale systems only).
