# Parallel test execution

There are three levels of concurrent test execution:

- The first one is related to the use of multi-port for the benefit of addressing timing and perhaps vector requirement needs. In this case, the level of parallel execution is specific to application needs.
- The second level is concurrent test execution for the benefit of saving test time execution by testing the device in a mode compatible to the system level operation (for example, the processor working simultaneously with an ADC and a DAC). Non concurrent test execution limits the test coverage to individual core functionality. Problems related to noise, power, and other problems are often not visible. With concurrent test coverage that emulates system level behavior leading to an increase on the test coverage while the test time is reduced as a result of the parallel test execution.
- On the third and final level, parallel test execution is heavily focused on test time reduction needs. At this level, all CCT benefits are applied related to cost of test and tester utilization. It is important to note that there are some considerations to be accounted for so that the test time reduction does not result in an increase to overall device cost by unnecessary reduction on yield or consecutive and sub-sequential test executions. It is always important to note that test time reductions should be measured on the production test and not on the test time of a single good device. In general and for this level of operation, multisite test should be considered first and when possible combined with parallel test for maximum benefit on test time reduction.

When core isolation is considered for parallel test execution, the test engineer needs to consider the following:

- reason for parallel test execution (application need, capital cost savings, emulation of system test, test time reduction, etc.)
- system level operation's needs (which cores will be active at the same time during different system level operations)
- power available to the device (can the device handle more than the required cores to be active simultaneously)
- core isolation (which cores are isolated for individual access, control, and observability)
- clock domains (the required period resolution and the resulting port specific periods as well as the availability of the tester clock domains and tester model)
- core test time (the effort should justify the means. Only cores of significant to the overall device test time should be considered to run in parallel. Consider the case of the following cores at test times (in percentage) to overall device test time:

  - coreA=10%
  - coreB=12%
  - coreC=2%
  - coreD=1.4%

The parallel execution of the cores can theoretically result in a test time reduction of 12%. The parallel test execution of coreC and coreD will have an insignificant effect on the overall test time reduction. For test time reduction applications, the longest test executions should be considered as the first CCT candidates.

- core yield information (cores of incompatible yield to test time relationship can have negative effects. For example, the parallel test execution of a 100 ms test with a 20 ms which fails at the rate of 20% will negatively effect the production test time, provided that the 20 ms was the first to be tested in the sequential program).
- the core functionality ( digital and analog cores when combined in a parallel test execution will have a different test time than a linear combination of their core test time).
