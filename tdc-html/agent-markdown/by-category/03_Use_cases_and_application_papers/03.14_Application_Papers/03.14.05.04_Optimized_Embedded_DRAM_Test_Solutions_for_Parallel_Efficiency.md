# Optimized Embedded DRAM Test Solutions for Parallel Efficiency

ChungDa Wang, Verigy

Yu Hu, Verigy

Takashi Itoh, Verigy

Paper-ID: 120510 April 2010

## Abstract

As the semiconductor technology grows more mature, embedded DRAM (eDRAM) is gaining increasing popularity in the SOC design to achieve lower power consumption and better system performance. Memory BIST (built-in self test) and BISR (built-in self repair) technologies are usually adopted as the test solution for eDRAM. These DFT (design for testability) technologies can help minimize the required number of test channels and avoid deep conventional testing patterns.

The BIST/BISR tests can be implemented with functional or digital capture test. Depending on the design, its test usually involves judgments on the current test results to decide the consequent steps. In the high-volume manufacturing (HVM) test, where a multi-site test is widely adopted to ensure the throughput, this result-dependent attribute would deteriorate the parallel efficiency dramatically in some scenarios. Therefore thorough consideration must be made on both the test solution creation and the design of BIST/BISR engine to streamline the test flow and maximize the parallel efficiency.

This paper showcases a common structure of the memory BIST/BISR engine in a SOC device and recommends test solutions for V93000. A counted match-loop solution with optimized parallel efficiency is explicitly presented. This solution was applied to a customer device on PinScale 400 for HVM test. It has been proven with extremely satisfactory results, i.e. around 90% of parallel efficiency for quad-site test.

## Introduction

Because memory is one of the important elements that influences the system performance, seeking for a better performance memory solution has never stopped. Thanks to the advanced process technologies that can integrate memory and logic on the same silicon, the embedded memory has become one of the options available for better performance. Among the various types of embedded memory, the embedded DRAM is increasingly gaining popularity over the past few years. It has been widely adopted in applications like game consoles, multimedia processors, high-end networking, digital consumers, etc... In comparison with the stand-alone commodity DRAM, the eDRAM has the following advantages [1].

- Better performance
- Lower power consumption
- Finer granularity for memory size and IO bus
- Reduced pin count and chip number on board

On the other hand, it brings penalties and challenges, for example, larger die size, higher cost, more complicated design and fabrication process etc... There are also new problems emerging when testing the embedded DRAM. The conventional solution cannot be applied because the memory interface cannot be accessed directly at the IO pins. Memory BIST (built-in self test) and BISR (built-in self repair) are usually the most effective solution to tackle this issue. In this paper a customer's device with BIST/BISR design will be discussed as well as the test solutions on V93000 with satisfactory parallel efficiency.

## Device and test strategy

## Structure of embedded DRAM and DFT

The structure of the embedded DRAM in customer's SOC device is illustrated in Figure 1. The eDRAM consists of several memory macros. Each of them contains an independent BIST and BISR engine, which can perform the pre-programmed test and repair the memory macro. The test can be configured by writing the setup data into the registers in the BIST engine. A variety of tests can be programmed such as checkerboard, march, and retention [2]. A test can also be started by writing a "1" into the start-test register in the BIST engine after it has been programmed. Then the test status can be queried by reading out the status bit of the register to judge whether the test has finished or not. Once the test has finished, the test result along with other information such as fail bit count and fail bit address are available in the related registers. A similar mechanism applies to the repair operations. The BIST/BISR engines in all the macros can be activated simultaneously in a broadcast mode so that the parallel test can be carried out.

 ![Optimized Embedded DRAM Test Solutions for Parallel Efficiency](<../../../../raw/120527.png>)

Figure 1. Structure of embedded DRAM

A JTAG port, IEEE standard 1149.1 [3], is used to access all the registers in the BIST/BISR engines. The JTAG port operates on 5 dedicated pins: TDI (test data in), TDO (test data out), TMS (test mode select), TCK (test clock) and Trst (test reset), which allows the BIST/BISR to be carried out by very limited tester resources. By driving the device through an appropriate sequence of states in the JTAG state diagram, data can be written into the registers through TDI, or read out from the registers through TDO. All the test and repair operations are performed by executing a series of digital vectors. The results and fail information can be retrieved by digital capture or inquiring the error map after the functional tests.

Figure 2 shows the flowchart for the BIST and BISR operations. The BIST is activated first and when it fails the BISR can be activated to repair the failed cells. After the BIST/BISR is activated, the status can be checked. The check is repeated until the test done signal is detected or it exceeds the predefined wait time. The repair capability is somewhat limited. It only fixes the first fail location in the preceding test with a row redundancy. After the repair is successfully done, the test is repeated. The first fail location then moves to the next and the repair is activated again to repair it. It might take several iterations of BIST and BISR before the device can be completely repaired. The loop carries on until it exits on two conditions: first the BIST passes (either it passes without repair or it has been completely repaired) and second a repair error is encountered. For the first scenario, E-fuse writing then takes place to preserve the repair data in the E-fuse onboard. For the second scenario, a repair error indicates that there is no more redundancy available to repair the current error. A device in this condition is then binned out as un-repairable.

## The digital capture solution

To fulfill the customer's need for flexibility in device debugging and data collecting, a V93000 test method is introduced to implement the BIST/BISR flow. In the test method, digital patterns are executed to program and start the test/repair, while digital capture is used to acquire the test/repair status and to retrieve test results and other data. Additionally the status inquiry can be implemented with a while-loop in which the time out condition can be easily evaluated.

The flexibility of the test method brings great benefits to the engineering. The BIST/BISR flow or the evaluation conditions can be changed in minutes, and the retrieved data can be processed easily, which are great values in the debug or characterization phases. However when it comes to the high volume manufacturing test, in which the test time and parallel efficiency have become the main interest, the un-optimized test method turns into a major problem. The BIST/BISR flow itself makes it difficult to construct an optimized test method structure. This is because it involves test/repair result judgment to decide its consequent steps. At the test/repair result evaluation stages, memory macros with different results are forced to take different paths. Some might pass at the first BIST execution, while others need a couple of more iterations to pass, or eventually turn out to be un-repairable. It would need a complicated structure to handle the results and paths taken by various memory macros and it gets even more complicated to construct a multi-site test method.

## New device and the flowchart

In order to optimize test efficiency and device performance, the customer undertakes a design change based on the lesson learned from the previous debugging. The new design enhances its repair capability and attempts to repair all the fail locations within one single invocation. It does not need several iterations of BIST and BISR before the final results can be acquired. We can tell whether a device is repairable or not with one single execution of repair. In addition the BISR activation would automatically start the pre-programmed BIST and then engage the repair operation once the test fails. This saves the programmer's efforts to issue test start command and constantly inquiry for test status. All these new features help streamline the BIST/BISR flow and smooth the solution construction. ## Test solutions for parallel efficiency

## The match loop solution

With the new design, a match loop solution is proposed to take the advantage of the streamlined flowchart for better parallel efficiency. The new solution is also test method based and it replaces the digital capture pattern with a match loop pattern to implement the wait loop and the test/repair status evaluation. The match loop avoids the data uploading, which is required by digital capture, and shortens the test time. However there are a few items need to be addressed. For example, there needs to be a way to tell whether the test is failed by a repair error or a time out error.

An example to illustrate the new test execution flow is shown in Figure 4. After the BIST/BISR initialization, the BIST starts at the same time on all 4 sites, however, may end with different processing time depending on the test results. After BIST is completed, site 2 finishes BIST pattern A without error, therefore no BISR action is required. The remaining sites of 1, 3 and 4 then engage the repair actions. Site 1 and 3 accomplish the repairs in time and their results are then evaluated, while site 4 is binned out immediately after the time out limit is exceeded. Therefore, from the high level point of view, the overall evaluation for the BISR action can be separated into 2 parts: the BISR time out judgment and the repair pass/fail judgment.

 ![Optimized Embedded DRAM Test Solutions for Parallel Efficiency (4)](<../../../../raw/120530.png>)

Figure 4. Quad-site BIST/BISR example

In order to achieve high parallel efficiency for multi-site testing, BISR (invoking BIST) patterns should have different loop numbers to accommodate specific wait time for each pattern. The counted match loop is used to implement the wait time and evaluate if a time out error has occurred. After the time out judgment, "FAIL" site (time out site) will be binned out, and "PASS" sites (BISR is done in time) will continue with BISR error check. The features for counted match loops are:

- User can specify the maximum number of repetitions. When executing if no match is found after this maximum loop number is exceeded, the match loop is terminated and the test fails.
- User must specify the dummy vectors after the match loop explicitly. This is to create a delay for the evaluation if a match is found in the match loop. The system would automatically repeat the dummy vectors as often as required.
- If the match loop fails in a multi-site setting, only the sites that actually fail will be considered as a failure. For the others, the test will be continued.

Since both the time out error and test fail error would lead to a FTST fail, the question of how to distinguish these two errors for binning is brought into focus. The hardware structure and the truth table in Figure 5 are explained in order to demystify the principle. In V93000, different registers are used to judge the pass/fail condition and the time limit condition (i.e. ax register). The result of the FTST query is determined by the logical AND combination of the global P/F result and the ax register. This is the reason why prohibiting compare actions before the match loop execution is an essential prerequisite. If the test fails before the match loop, this failure will be stored in the global P/F, which interferes with the root cause judgment. In the case of time out, the ax register will be set to zero. Then the sequencer will stop and the FTST result will be set to Fail. For those functional tests that do not have the match loop, the ax register is set to 1 automatically and has no influence on the overall FTST results.

Figure 6 shows how the test pattern, composed of 3 subroutines, is arranged.

Based on such pattern structure, the result can be categorized into three different cases:

- When the overall FTST passes, it indicates that the BIST/BISR has finished in time without any error.
- When the overall FTST fails, "ERCT?" query which returns the error count, is used additionally to distinguish two failure cases:

  - error count> 0: the repair is finished in time but with repair error
  - error count= 0: time out failure

Therefore in the test method the data can be acquired and evaluated to determine what the overall test result is: pass, fail with a repair error, or fail with a time out error.

## Further optimization with the burst-all solution

Another test methodology, the burst-all solution, can yield even better parallel efficiency, however requires more efforts to implement. The self-explanatory burst-all solution integrates all the BIST/BISR patterns into one large burst and uses the Jump-on-fail feature of V93000 platforms to deal with the un-deterministic wait time for each BIST/BISR action. As illustrated in Figure 8, the burst-all solution allows each site to execute the large burst pattern independently and avoids the idle which occurs on those PASS sites that still need to wait for the FAIL sites to finish the repair actions. The only unavoidable idle would be at the end of this burst pattern when the numbers of failed sub-patterns disagree among the activated sites and cause the unbalanced execution time. However this issue can be improved when more patterns are put into the burst. As the size of the burst grows, more likely the failed sub-pattern number difference among the sites could be minimized given that the failures are evenly distributed among the devices from a statistical perspective. With the test time difference among the activated sites being reduced and the idle being eliminated, better parallel efficiency and throughput can be

achieved.

 ![Optimized Embedded DRAM Test Solutions for Parallel Efficiency (12)](<../../../../raw/120538.png>)

Figure 8. Burst-all solution in a dual site scenario

Similar to the match loop solution, one thing that must be taken into account is that for the Jump-on-fail solution each jump also introduces internal latency time for the error propagation, which is test system specific and primary sets dependent and therefore should be optimized.

The implementation scheme is illustrated in Figure 9. The Jump-on-fail instruction can be used to return from the repair status inquiry subroutine when the "repair done" signal is detected. The loop to query the repair status has to be flattened to implement the wait time, 10 iterations as in our example in Figure 9. The implementation of the burst-all solution does require a lot more efforts. The patterns have to be reconstructed, flattened and then integrated together. Also post processing of the test results is required to determine which pattern has failed and what the failure is, repair error or time out. In fact the burst-all solution has never been implemented on the customer's device due to the huge efforts required. Most importantly the match loop solution has already produced a satisfactory result.

## Summary

The embedded DRAM is now extensively utilized in SOC applications that demand better performance, lower power consumption and higher flexibility. However, it also brings the new challenges in several aspects. The DFT technologies, BIST and BISR, can effectively overcome the challenge on the testing of eDRAM. The V93000 match loop solution has been proposed and validated on a customer's device successfully. The remarkable enhancement on parallel efficiency and test time makes it the standard test solution for production of the customer. In addition the burst-all solution has also been proposed to further optimize the parallel efficiency. Nevertheless it might be rather inefficient or even ineffective to improve the parallel efficiency from the testing perspective alone, especially when DFT is involved. Only if the designer and the test engineer collaborate to streamline the device test flow could the ultimate optimization be achieved.
