# Running a script (external tool)

After discussing the theory and capabilities of external tool launching, some practical examples are given. These should be taken as examples to understand the concept. In daily work with SmarTest, users may have a set of individual external tools which could be integrated into the SmarTest Work Center, using this technique.

The following examples all use the concept of external tool configuration as described above. Instead of screen shots, the content for the Location and Arguments fields are given.

## Direct Call

A typical example is to launch an external shell script or Perl script. This is pretty easy to achieve, just by specifying the script as the Location of the launch, and by adding any needed options into the Arguments section. Example:

Location:

```
/home/userx/cmd/check_device.pl
```

Arguments:

```
${project_loc}
```

${project_loc} is replaced with the path to device directory, as selected in the Navigator view.

## A Script as an Argument

The next example demonstrates the use of a short shell script from inside Eclipse. The external program to launch is the shell /bin/ksh, while the argument list takes the -c option to specify the script (see man ksh). In this example, the shell script's purpose is to print some device and setup file specific information.

Location:

```
/bin/ksh
```

Arguments:

```
-c "
echo 'HOME:              ' ${env_var:HOME}
echo 'Project Location:  ' ${project_loc}
echo 'Project Name:      ' ${project_name}
echo 'Project Path:      ' ${project_path}
echo 'Resource Location: ' ${resource_loc}
echo 'Resource Name:     ' ${resource_name}
echo 'Resource Path:     ' ${resource_path}
echo 'Workspace:         ' ${workspace_loc}
"
```

After selecting a testflow file in the Navigator view and launching the script, the output may look as following [shortened for formatting reasons]:

```
HOME:      /home/mv
P. Loc.:   /home/mv/devices/WPonline
P. Name:   WPonline
P. Path:   /WPonline
R. Loc.:   /home/[...]/testflow/tf.wp
R. Name:   tf.wp
R. Path:   /WPonline/testflow/tf.wp
Workspace: /home/mv/workspace_6.5
```

All following examples use the same Location (/bin/ksh), so it is not repeated for each example.

## tar the Device Project

The next example is how to take a quick snapshot of the current device project and to save it in an archive. It makes use of a combination of user prompts and system variables.

Working Directory:

```
${project_loc}/..
```

Arguments:

```
-c "
tarfile=${file_prompt:target tar archive}
if [ -e $tarfile ]
then
	echo \"Error: won't overwrite existing file $tarfile. Please chose different name or delete file first.\"
else
	tar cvf $tarfile ${project_name}
	echo
	echo \"tar file created:\"
	ls -l $tarfile
fi
"
```

Please note the definition of the working directory. It is set to one level higher that the current project directory. The tar command finally targets on the project (device) name.

## tail MCDLog

The last given example is how to quickly snoop at firmware communication as a matter of debugging.

Arguments:

```
-c "
hpt=$XOC_LEGACY_ROOT/fw/bin/hpt
mcdlog=/var$XOC_LEGACY_ROOT/MCDLog
if [ ! -x $hpt ]
then
	echo \"can not find executable hpt under $hpt\"
	exit 1
fi

echo 'DIAG 2' | $hpt >> /dev/null 2>&1

echo 'NOOP \"start logging\",,,' |\
	$hpt  >> /dev/null 2>&1

sleep 2
( sleep 60 ; \
	echo 'NOOP \"stop loggin\",,,' |\
	 $hpt ; echo 'DIAG -2' | $hpt ) \
	>> /dev/null  2>&1 &

tail -f $mcdlog
"
```

The implementation sends DIAG 2 to start logging. Sixty seconds later, logging is stopped with DIAG -2 (in background), while tail is looking at the log in parallel. The execution ends by pressing the Terminate button in the Console view.
