# Generic Data Record (GDR)

#### Subtopics

- [Logging GDR records with test methods](<02.10.03.05.27.01_Logging_GDR_records_with_test_methods.md>)
- [Logging GDRs from the application model](<02.10.03.05.27.02_Logging_GDRs_from_the_application_model.md>)
- [FFC and FFV information in GDR records](<02.10.03.05.27.03_FFC_and_FFV_information_in_GDR_records.md>)

The Generic Data Record contains information that does not conform to any other record type defined by the STDF specifications. Such records are intended to be written under the control of job plans executing on the test system. This data may be used for any purpose that the user desires.

The Generic Data Record can appear anywhere in the data stream after the initial sequence. When more than 255 sites are tested, a specific GDR record is inserted into the initial sequence, as described below in [GDR for tests with more than 255 sites](<02.10.03.05.27_Generic_Data_Record__GDR.md#_68925__gdr-for-more-than-255-sites>).

- 13 = Unsigned integer data stored in 4 bits of a byte (nibble)
 |

The GDR is a catch-all data type for all kinds information that does not fit into any of the other record types.

GDR records are created with [GenericDataEventType](<02.10.01.06.03.08_GenericDataEventType.md>) EDL events. (See [Logging GDR records with test methods and user procedures](<02.10.03.05.27.01_Logging_GDR_records_with_test_methods.md>) for more information.) The actual content of the fields is therefore under control of the test method, and the ultimate source of the data depends on the individual program logic.

If you have switched to STDF V4 (as opposed to STDF V4-2007), certain record types are not supported by the standard and SmarTest outputs them as GDR records. See the respective records type descriptions for information on their content. This affects:

- [Chain Description Record (CDR)](<02.10.03.05.21_Chain_Description_Record__CDR.md>)
- [Scan Cell Name Record (CNR)](<02.10.03.05.19_Scan_Cell_Name_Record__CNR.md>)
- [Name Map Record (NMR)](<02.10.03.05.18_Name_Mapping_Record__NMR.md>)
- [Pattern Sequence Record (PSR)](<02.10.03.05.12_Pattern_Sequence_Record__PSR.md>)
- [Scan Structure Record (SSR)](<02.10.03.05.20_Scan_Structure_Record__SSR.md>)
- [Scan Test Record (STR)](<02.10.03.05.17_Scan_Test_Record__STR.md>)
 |

## Pad field

The pad field (Data Type 0) is a special pad field used to force alignment of following data types in the record. In particular, it must be used to ensure even byte alignment of two byte unsigned integers, four-byte unsigned integers, two-byte signed integers, four-byte signed integers, four-byte floating point numbers and eight-byte floating point numbers.

The GDR begins on an even byte boundary, and the GDR header contains four bytes. The first GEN_DATA field therefore begins on an even byte boundary. You must provide the pad bytes needed to ensure data boundary alignment for the CPU on which it will run.

## GDR for tests with more than 255 sites

If a test was performed on more than 255 sites, a special GDR is inserted between the last SDR of the [initial sequence](<02.10.03.05.32_Sequence_of_STDF_records.md>) and the first PMR.

This record contains two fields:

- The first field has the code 10 (character string) and the content EXTENDEDSITES.
- The second field has the code 2 (unsigned integer) and as the content the number of sites, up to a maximum of 4096.
