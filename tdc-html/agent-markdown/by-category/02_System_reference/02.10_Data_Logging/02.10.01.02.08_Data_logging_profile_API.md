# Data logging profile API

#### Subtopics

- [ProfileMgr class](<02.10.01.02.08.01_ProfileMgr_class.md>)
- [Profile class](<02.10.01.02.08.02_Profile_class.md>)
- [Rule class](<02.10.01.02.08.03_Rule_class.md>)
- [Property class](<02.10.01.02.08.04_Property_class.md>)
- [Data logging profile API examples](<02.10.01.02.08.05_Data_logging_profile_API_examples.md>)

With the [data logging profile](<02.10.01.02_Data_Logging_Profiles.md>) API you can create and handle data logging profile and their rules and properties. It consists of the following classes:

- [ProfileMgr class](<../02.07_Test_Method_Reference/02.07.04.01.169.01_ProfileMgr_class.md>)
- [Profile class](<../02.07_Test_Method_Reference/02.07.04.01.169.02_Profile_class.md>)
- [Rule class](<../02.07_Test_Method_Reference/02.07.04.01.169.03_Rule_class.md>)
- [Property class](<../02.07_Test_Method_Reference/02.07.04.01.169.04_Property_class.md>)

The classes model the various profile-related objects and their relationships:

- The ProfileMgr instance contains zero or more Profile instances.
- A Profile instance contains zero or more Rule instances.
- A Rule instance contains a logging definition in the form of a string, such as "*leakage*.*.*.datalog_detail=2"

## ProfileMgr class

With the ProfileMgr (profile manager) class, you can create, activate, load, save, and delete data logging profiles. There is just one ProfileMgr object that serves as the repository for all profiles.

The ProfileMgr interface provides an access method to obtain the singleton instance `getInstance()` which should be called first:

```
ProfileMgr* mgr = ProfileMgr::getInstance();
```

The instance can optionally be freed at anytime with a call to `freeInstance()`.

## Profile class

The Profile class encapsulates the core functionality that is associated with a data logging profile, such as creating, loading, saving, and manipulating rules that are part of the profile

Once the ProfileMgr instance exists, you can use the Profile class to create and manage profiles. A typical starting point is to create a profile via the following call:

```
Profile* profile = mgr->createProfile(WildcardProfileType);
```

Always use the `WildcardProfileType`. The only other option, `ProdSettingProfileType`, is used internally by SmarTest for compatibility with the production settings feature.

Alternatively, a profile can be created and automatically populated when a profile already exists on the file system as follows:

```
Profile* profile = mgr->createProfile(<filename>);
```

Once the profile exists, it needs to be populated with rules. This is usually done by simply passing the rule strings directly to the `createRule()` method. For example, the following three calls together create the content of the default data logging profile `datalog_ON.prf`:

```
profile->createRule("*.*.*.log_events_enable=1");
profile->createRule("*.*.*.datalog_level=3");
profile->createRule("*.*.*.datalog_detail=2");
```

## Rule class

The Rule class is an abstract interface that contains all of the variables and methods necessary to store and manipulate the content of a general property rule, such as the context information, the property name, and its value.

A rule is a logical part of a profile. A Profile instance contains zero to many rule instances. The rule string passed to the constructor is described in [Data logging profile rule syntax](<02.10.01.02.06.03_Data_logging_profile_rule_syntax.md>).

An empty rule can be created and then populated by calling the set methods offered by the Rule class one by one:

```
Rule* rule = profile->createRule();
rule->setTestSuite("*leakage*");
rule->setTestMethod("*");
rule->setTestName("*");
rule->setPropName("per_pin_on_fail");
rule->setPropValue(1);
```

The Rule class also includes corresponding get methods for the categories listed above (for example, `getTestSuite()`).

At this point, the profile and its rules are stored in memory, but are not yet visible to other processes via the file system. To save the content of the profile to the file system, call the `save` method:

```
profile->save(<filename>);
```

Ideally, the file name indicates the name of the device and the profiles subdirectory to make sure the profile is visible to SmarTest.

After a profile has been saved, it can be activated, which means the rules in the profile apply to the next test execution. This is done by calling the `activateProfile` method:

```
profileMgr->activateProfile(profile);
```

Alternatively, the file name can be specified instead of the profile instance:

```
profileMgr->activateProfile(<filename>);
```

## Property class

The Property class is used by the test methods to determine the value of a particular data logging property within the current execution context. The property instance determines its value by first obtaining the active profile and then by querying the value of the property within that profile.

There are predefined system properties, and you can define your own user defined properties. For a description of the predefined system properties see [Data logging profile rule syntax](<02.10.01.02.06.03_Data_logging_profile_rule_syntax.md>).

To query the logging configuration from within a test method, use the Property class.

The value of a property can be obtained directly using the static `value()` convenience method of the class:

```
int datalog_detail = Property::value("datalog_detail");
if (datalog_detail > LOG_PER_PIN_VALUES)
 {
 }
```

Or you can obtain the value of a property can be obtained by creating a Property object and using it directly:

```
Property datalog_detail("datalog_detail");
if (datalog_detail > LOG_PER_PIN_VALUES)
 {
 }
```

Notice that, in the second case, the Property's int cast operator maps to the `value()` method, allowing you to treat the Property object as an integer.

The individual rules in a profile can be accessed using the `getRule()` method. This can also be done using a `for` loop:

```
for (int i=0; i<profile->getRuleCount(); i++)
{
Rule* rule = profile->getRule(i);
.
.
}
```

The rule content of a particular position can be overwritten using a call to `setRule(i, rule)`;

Once the Rule object is available, the content of each rule can be modified using the APIs of the [Rule class](<../02.07_Test_Method_Reference/02.07.04.01.169.03_Rule_class.md>).
