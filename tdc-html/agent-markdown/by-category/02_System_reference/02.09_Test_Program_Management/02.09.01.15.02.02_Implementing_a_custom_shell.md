# Implementing a custom shell

A similar sequence of events is required if you want to create a custom production test shell. If this shell is also to provide the feature that you can select whether to call SmarTest in supervisor or operator mode, then the main tasks required by the test shell are the following:

- Create a GUI that displays the workorders available to the user. Note that these workorders are simply text files residing in a directory pointed to by the WORKORDER_PATH parameter in the org file in /opt/hp93000/soc/prod_env. Since you can specify a full path from the command line, using the org file is optional.
- After the operator selects a workorder (by clicking it once), the following needs to happen:

  - Display the workorder contents (device name and test program name) in a separate panel (for verification).
  - Display the test parameters (as labels) in a separate panel, and provide a way to assign data to them (text entry fields, combo boxes, etc).
  - Display the tester status (SmarTest mode [Operator|Supervisor], and Online Status [Online|Offline]) in a separate panel. Along with these labels, provide a button to start testing, and another button to kill SmarTest.

- Once the Start Testing button has been pressed, write the test parameters that were assigned by the user to a file (for example, /tmp/parmsfile) so that they can be read in by an EXEC_INP_CALL( ) routine once SmarTest has started. Other methods of interprocess communications (for example, shared memory) could be used instead of writing to a file, but the file method is the simplest.
- Use a configuration file to configure the test shell. The test shell reads in this file at startup, and extracts general parameters (for example, debug level used to control logging), SmarTest parameters (for example, online/offline mode, operator/supervisor mode), and the definitions of the test parameters (for example, LotID, OperatorID, and so on). The test parameters should also have associated with them their types (int, string, combo box, and so on). The test shell will create a panel containing the test parameters along with an appropriate method to assign values to them.
- A log file should be generated that follows the execution of the Test Shell with its resolution depending on the Debug Level specified. The log file will be helpful during the troubleshooting of the program.

The details of the implementation differ depending on whether the shell calls SmarTest in operator mode or in supervisor mode.
