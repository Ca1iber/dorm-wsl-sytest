# SMC_BACKGROUND_ENABLE()

The SMC_BACKGROUND block in the run() function of a test method class is defined by SMC_BACKGROUND_ENABLE() and SMC_BACKGROUND_DISABLE(). The block encloses non-SMC APIs and marks a time slot where the SmartCalc framework can initiate hidden uploads. The code inside of the block is executed in parallel to hidden uploads and must not access the hardware.

SMC_BACKGROUND_ENABLE() and [SMC_BACKGROUND_DISABLE()](<02.07.04.01.231.05_SMC_BACKGROUND_DISABLE.md>) are intended to be used in the run() function of a test method class and must always be implemented together.

## Principle of operation

Creating background processes by the [SmartCalc framework](<02.07.10_SmartCalc_framework.md>) may result in conflicts if both the run() function of a test method class and an [SMC_backgroundProcessing()](<02.07.04.01.231.01_SMC_ARM.md#_120107__s_SMC_backgroundProcessing>) function access the tester hardware at the same time.

The SmartCalc framework can therefore perform hidden uploads only if the tester hardware is not accessed by another process. Identifying these time slots and using them in a background process is done automatically if only SMC APIs are used in the run() function and in the background process.

 For non-SMC APIs, separate handling is required for test time consuming sections of the run() function and for hardware access in a background process:

-

The SMC_BACKGROUND block in the run() function encloses non-SMC APIs that do not access the tester hardware. This block allows hidden uploads while the code in the block is executed.

- An [SMC_HIDDEN_EXECUTION](<02.07.04.01.231.22_SMC_HIDDEN_EXECUTION_BEGIN.md>) block in the background process encloses non-SMC APIs that access the tester hardware. The SmartCalc framework executes the code in the block only while no other process accesses the tester hardware.
  The SMC_BACKGROUND block thus provides a time slot that allows SmartCalc performing hidden uploads in the background:

- No access to the tester hardware is allowed in the SMC_BACKGROUND block.
- The code within the block is executed independently of and in parallel to the background processes.
- The execution of the run() function will stop at the end of the block until the currently processed part of a hidden upload has been finished.
- There is no fixed relationship between an SMC_BACKGROUND block in the run() function and an SMC background process. The block enables hidden uploads that previously have been placed in the queue by the SmartCalc framework.

## Syntax

```
void SMC_BACKGROUND_ENABLE();
```

This API is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/SMART_CALC2.h.

  List of parameters There are no parameters. Return value There is no return value.

## Example

### SMC_BACKGROUND_ENABLE example

The example consists of two test suites which have to be executed in succession:

- Test method class Test_1_SMC_BACKGROUND_ENABLE performs a digital capture test on pins "dig1" 鈥?"dig4" using API [SMC_DIGITAL_CAPTURE_TEST()](<02.07.04.01.231.08_SMC_DIGITAL_CAPTURE_TEST.md>). A hidden upload of the captured data is done by [SMC_GET_VECTORS()](<02.07.04.01.231.17_SMC_GET_VECTORS.md>).
- Test method class Test_2_SMC_BACKGROUND_ENABLE performs an [SMC_FUNCTIONAL_TEST()](<02.07.04.01.231.13_SMC_FUNCTIONAL_TEST.md>) that already grants a hidden upload in the queue access to the tester hardware for the time while the pattern is running. An SMC_BACKGROUND block outside of the ON_FIRST_INVOCATION block emulates processing of data and allows the background processes accessing the tester hardware for some more time.
Some items to consider for the example:

- You need to set up the four pins for digital capturing and create also a [Digital Capture setup](<../02.08_Setup_and_Result_Tools/02.08.01.02.07.02.05.01_Creating_a_Digital_Capture_setup.md>) using the vector variable "cap1".
- The example utilizes an optional pair of curly brackets "{" and "}" for the ON_FIRST_INVOCATION block and the SMC_BACKGROUND block. These optional curly brackets are used for simplifying the correct indentation with assistance of the related Eclipse tool.
- The example shows only how to use the SMC_BACKGROUND block and contains therefore no real test code.

Test method class for the first test suite:

```
#include "testmethod.hpp"
#include "mapi.hpp"

using namespace std;

class Test_1_SMC_BACKGROUND_ENABLE: public testmethod::TestMethod {

protected:

    virtual void initialize()
    {
    }

    virtual void run()
    {
        STRING testName;

        GET_TESTSUITE_NAME(testName);

        ON_FIRST_INVOCATION_BEGIN();
        {
            RESULT_AREA_CONFIG resultAreaConfig("dig1,dig2,dig3,dig4");

            resultAreaConfig.appendArea("16KBITArea",3072).activate();

            cout << testName << " - run(): " << "SMC_DIGITAL_CAPTURE_TEST" << endl;

            SMC_DIGITAL_CAPTURE_TEST("16KBITArea");

            ARRAY_I activeSites;

            GET_ACTIVE_SITES(activeSites);

            cout << testName << " - run(): " << "Arming common SMC thread" << endl;

            SMC_ARM(activeSites);
        }
        ON_FIRST_INVOCATION_END();

        return;

    } // virtual void run()

public:

    virtual void SMC_backgroundProcessing(ARRAY_I& activeSites)
    {
        STRING testName;

        SMC_GET_TESTSUITE_NAME(testName);

        cout << setw(50) << "" << testName << ": Entering common SMC thread" << endl;

        for (int siteIndex = 0; siteIndex < activeSites.size(); ++siteIndex)
        {
            INT currentSite = activeSites[siteIndex];

            ARRAY_I vectorArray;

            vectorArray = SMC_GET_VECTORS(currentSite, "cap1", "16KBITArea");

            cout << setw(50) << "" << testName << ": Vector data for site " << currentSite << " = " << vectorArray << endl;
        }

        cout << setw(50) << "" << testName << ": Leaving common SMC thread" << endl;

    } // virtual void SMC_backgroundProcessing(ARRAY_I& activeSites)
};

REGISTER_TESTMETHOD("Test_1_SMC_BACKGROUND_ENABLE", Test_1_SMC_BACKGROUND_ENABLE);

```

Test method class for the second test suite:

```
#include "testmethod.hpp"
#include "mapi.hpp"

using namespace std;

class Test_2_SMC_BACKGROUND_ENABLE: public testmethod::TestMethod {

protected:

    virtual void initialize()
    {
    }

    virtual void run()
    {
        STRING testName;

        GET_TESTSUITE_NAME(testName);

        ON_FIRST_INVOCATION_BEGIN();
        {
            cout << testName << " - run(): " << "SMC_FUNCTIONAL_TEST" << endl;

            SMC_FUNCTIONAL_TEST();
        }
        ON_FIRST_INVOCATION_END();

        cout << testName << " - run(): " << "SMC_BACKGROUND_ENABLE for site " << CURRENT_SITE_NUMBER() << endl;

        SMC_BACKGROUND_ENABLE();
        {
            //
            // Wait time emulates time required for calculations
            //
            // No access to tester hardware in this block!
            //
            WAIT_TIME(2 ms);
        }
        SMC_BACKGROUND_DISABLE();

        cout << testName << " - run(): " << "SMC_BACKGROUND_DISABLE" << endl;

        return;

    } // virtual void run()
};

REGISTER_TESTMETHOD("Test_2_SMC_BACKGROUND_ENABLE", Test_2_SMC_BACKGROUND_ENABLE);
```

Note

The example above contains several calls of cout in function [SMC_backgroundProcessing()](<02.07.04.01.231.01_SMC_ARM.md#_120107__s_SMC_backgroundProcessing>). cout is not thread safe. In production test cout must never be used in a background process.

When using cout in a background process, you have to expect a mix up of the output in the ui_report window and possibly other unwanted behavior. For more information, refer to [Thread safety](<02.07.10.02.02_Thread_safety.md>).

For a test program with four configured and enabled site, the code above results in an output in the ui_report window similar to the following text:

```
Test_1 - run(): SMC_DIGITAL_CAPTURE_TEST
Test_1 - run(): Arming common SMC thread
                                                  Test_1: Entering common SMC thread
Test_2 - run(): SMC_FUNCTIONAL_TEST
                                                  Test_1: Vector data for site 1 = {    0,  }
Test_2 - run(): SMC_BACKGROUND_ENABLE for site 1
Test_2 - run(): SMC_BACKGROUND_DISABLE
Test_2 - run(): SMC_BACKGROUND_ENABLE for site 2
                                                  Test_1: Vector data for site 2 = {    0,  }
                                                  Test_1: Vector data for site 3 = {    0,  }
                                                  Test_1: Vector data for site 4 = {    0,  }
                                                  Test_1: Leaving common SMC thread
Test_2 - run(): SMC_BACKGROUND_DISABLE
Test_2 - run(): SMC_BACKGROUND_ENABLE for site 3
Test_2 - run(): SMC_BACKGROUND_DISABLE
Test_2 - run(): SMC_BACKGROUND_ENABLE for site 4
Test_2 - run(): SMC_BACKGROUND_DISABLE
```

The output in the ui_report shows the following behavior of the example code:

- The common thread for all sites is armed in the run() function of test suite Test_1.
- The background process of Test_1 processes the first site while the SMC_FUNCTIONAL_TEST is executed in Test_2.
- The remaining sites are processed while calculations are emulated in the SMC_BACKGROUND block of Test_2.
