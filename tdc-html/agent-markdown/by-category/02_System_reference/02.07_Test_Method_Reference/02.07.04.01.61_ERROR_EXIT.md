# ERROR_EXIT

This API is used mainly for error handling purposes.

This API terminates the current testflow or test program execution with the specified termination type (error handler type) immediately.

This can also call your custom function in the test method shared library to be used currently before terminating the testflow or program execution. You can use this custom function for error handling purposes such as recovering the occurred trouble, and so on.Note Do not use this API inside any of the [Special test suites](<../02.08_Setup_and_Result_Tools/02.08.04.32.01.02.01.02_Special_test_suites.md>), as the handling is not compatible with the testflow executor.

## EXCEPTION_INFO

A class `EXCEPTION_INFO` is defined to contain the error information. In your custom function, you can refer to the error information using the `EXCEPTION_INFO` object and the member functions as below.

```
const EXCEPTION_INFO& info;
info.getExitCase()
```

One of `TM::EXIT_CASE` is returned. This indicates an error and its API category.

```
info.getName():
```

The name of the API where an error occurred is returned as string data.

```
info.getMessage():
```

Issued error message for the API is returned as string data.

## EXIT_CASE

The enumeration TM::EXIT_CASE defines the categories of APIs in which the error occurred. The categories include `SETUP`, `EXECUTE`, `RESULT`, `COMPUTATION`, `TEST_CONTROL`, `DC_TEST`, `GPIB`, `MULTI_SITE`, `MISC`, `DIGITAL_TEST`, `SPECSEARCH`, `SEQUENCER_CONTROL`, `COMMON_CLASS`, and `ALL`.

## EXIT_TYPE

The enumeration TM::EXIT_TYPE is defined to contain the exit types. Its options are listed in the table below:

 |

Error Handler Type (TM::EXIT_TYPE)

 |

Description

 |
 |

ABORT_FLOW

 |

All sites that have not been binned yet will be aborted and binned to the otherwise bin.

The testflow execution ends after the current run. It needs user interaction to restart the next testflow execution.

 |
 |

EXIT_FLOW

 |

All sites of the current test suite, which are to be executed, are sent to the otherwise bin.

All other sites continue their normal flow logic. There is no termination at the end of the current testflow execution.

 |
 |

EXIT_TO_BIN

 |

A failing site of the current test suite is disconnected and sent to the otherwise bin. Test suite execution continues with the other sites. There is no termination at the end of the current testflow execution.

 |
 |

RETURN_TO_FLOW

 |

For the current test site the test method execution is terminated and the test suite is set to fail (continues a fail branch in case of a "run and branch" node). The test method will be called for all the remaining sites without any more special handling.

 |
 |

RETRY

 |

For the current test site the test method execution is retried after the current result is logged as unreliable.

 |
 |

INTERACTIVE

 |

A dialog box opens. You can select one of the above error handler actions in the dialog box interactively.

 |
 |

THROUGH

 |

The test method program execution is continued even if an error occurs. Note that this is valid only for GPIB and Computation API (GPIB_XXXX and DSP_XXXX).

 |
 |

NONE

 |

No exception is thrown. The previously installed exception handlers will be removed.

 |

This API is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/ExceptionHandler.h.

## Syntax

For terminating testflow or program execution immediately, or for disconnecting a failing site of the current test suite and letting the other sites continue execution.

```
ERROR_EXIT(TM::EXIT_TYPE type);
```

For terminating testflow or program execution immediately and printing the warning message in UI report window

```
ERROR_EXIT(TM::EXIT_TYPE type, bool outputWarning);
```

For calling your custom function before terminating the execution

```
ERROR_EXIT(TM::EXIT_TYPE *func, void *arg);
```

To set up a custom function as an error handler, the type of a custom function must be defined as `TM::EXIT_TYPE`, and it must return a value as TM::EXIT_TYPE at the end of the function. This means to specify how to terminate the testflow or program execution after running your function code. The custom function is in the following structure.

```
TM::EXIT_TYPE Func_Name(const EXCEPTION_INFO& info, void* arg)
{
 //Your Error Handler Program
 return TM::ABORT_FLOW; //return one of TM::EXIT_TYPE
}
```

## Examples

### Terminate the execution interactively

```
INT timeout;
Routing.pin("Aout").connect(TM::SINGLE);
Analog.DGT("Aout").enable();
START_TEST();
WAIT_TEST_DONE(1, &timeout);

if (timeout == 1)
{
 ABORT_TEST();
 ERROR_EXIT(TM::INTERACTIVE);
}

Analog.DGT("Aout").disable();
Routing.pin("Aout").disconnect();
FLUSH();

// Code for retrieving/calculation/judgment
```

 .

 .

If a timeout error (fatal error) occurs in the WAIT_TEST_DONE API, the analog sequencers and digital sequencer are aborted by the ABORT_TEST API. Then, the ERROR_EXIT API opens a dialog box for asking the termination method of program execution.

### Handle the execution error with custom function (no second argument)

```
TM::EXIT_TYPE ErrHandler(const EXCEPTION_INFO& info, void *arg)
{
 static called = 0;
 if (called == 0)
 {
 called++;
 return TM::RETRY;
 }
 else
 {
 return TM::ABORT_FLOW;
 }
}

class ExMethod: public testmethod::TestMethod
{
 .
 .

 virtual void run( )
 {
 INT timeout;

 Routing.pin("Aout").connect(TM::SINGLE);
 Analog.DGT("Aout").enable();
 START_TEST();
 WAIT_TEST_DONE(1, &timeout);

 if (timeout == 1)
 {
 ABORT_TEST();
 ERROR_EXIT(ErrHandler, 0);
 }

 Analog.DGT("Aout").disable();
 Routing.pin("Aout").disconnect();
 FLUSH();
 // Code for retrieving/calculation/judgment
 .
 .
 return;
 }
 .
 .
}
```

The function ErrHandler is a user function set by the ERROR_EXIT API as an error handler. This example does not use the second argument of the function ErrHandler.

If a timeout error (fatal error) occurs in the WAIT_TEST_DONE API, program execution jumps to the function ErrHandler after the digital sequencer and analog sequencers are aborted by the ABORT_TEST API. In this function, if it is the first error, the current test suite execution (program execution) is retried, or the testflow execution is terminated.

These termination actions are defined on the return statement using one of the enumerator TM::EXIT_TYPE (that is, the return value of this user function).

### Handle the execution error with custom function (using second argument)

```
TM::EXIT_TYPE ErrHandler(const EXCEPTION_INFO& info, void *arg)
{
 static called = 0;
 ABORT_TEST();
 if (*((INT *) arg) == 1)
 {
 if (called == 0)
 {
 called++;
 cout << "Retry First Test!" << endl;
 return TM::RETRY;
 }
 else
 {
 cout << "Abort Testflow (1)" << endl;
 return TM::ABORT_FLOW;
 }
 }

 if (*((INT *) arg) == 2)
 {
 cout << "Abort Testflow (2)" << endl;
 return TM::ABORT_FLOW;
 }
}

class ExMethod: public testmethod::TestMethod
{
 .
 .

 virtual void run( )
 {
 INT timeout;
 static INT errno = 0;

 Routing.primary(1);
 Analog.DGT("Aout").enable();
 START_TEST();
 WAIT_TEST_DONE(1, &timeout);

 if (timeout == 1)
 {
 errno = 1;
 ERROR_EXIT(ErrHandler, &errno);
 }

 Analog.DGT("Aout").disable();
 FLUSH();

 // Code for retrieving/calculation/judgment

 Routing.primary(2);
 Analog.DGT("Aout").enable();
 START_TEST();
 WAIT_TEST_DONE(1, &timeout);

 if (timeout == 1)
 {
 errno = 2;
 ERROR_EXIT(ErrHandler, &errno);
 }

 Analog.DGT("Aout").disable();
 FLUSH();

 // Code for retrieving/calculation/judgment

 return;
 }
 .
 .
}
```

The function ErrHandler is a user function set by the ERROR_EXIT API as an error handler. This example uses the second argument of the function ErrHandler to indicate that a timeout error has occurred, and in which test (first or second).

If a timeout error (fatal error) occurs in the first WAIT_TEST_DONE API, program execution jumps to the function ErrHandler. In this function, the digital sequencer and analog sequencers are aborted by the ABORT_TEST API, and then the current testsuite execution (program execution) is retried if it is the first error, or the testflow execution is terminated.

If a timeout error (fatal error) occurs in the second WAIT_TEST_DONE API, program execution jumps to the function ErrHandler. In this function, the digital sequencer and analog sequencers are aborted by the ABORT_TEST API and the testflow execution is terminated.

### Handle a specific site that fails upon a safety disconnect

```
virtual void run()
{
    STRING fw_answer;
ON_FIRST_INVOCATION_BEGIN();
    CONNECT();
      FUNCTIONAL_TEST();
    ON_FIRST_INVOCATION_END();

    if (GET_FUNCTIONAL_RESULT()==1) {
        cout << "[INFO] The functional test passed on site " << CURRENT_SITE_NUMBER() << "." << endl;
        TEST("","",TM::Pass,0);
    }
    else {
        FW_TASK("PSAS? PQFC,260,(dps)\n",fw_answer);
        if (strstr(fw_answer.c_str(), "PSAS P,") != NULL) {
            cout << "[INFO] The functional test failed on site " << CURRENT_SITE_NUMBER() << " due to pattern compares." << endl;
            TEST("","",TM::Fail,0,TM::CONTINUE);
        }
        else {
            cout << "[INFO] The functional test failed on site " << CURRENT_SITE_NUMBER() << " due to safety disconnect." << endl;
            TEST("","",TM::Fail,0,TM::CONTINUE);
            cout << "[INFO] Calling exception: EXIT_TO_BIN. Failing site is sent to otherwise bin." << endl;
            ERROR_EXIT(TM::EXIT_TO_BIN);
        }
    }
    return;
}
```

In the example above, the termination type EXIT_TO_BIN disconnects a specific site of the current test suite which observes a safety disconnect, and sends the failing site to the otherwise bin. Testflow or program execution is not terminated because the other sites continue their normal flow logic.
