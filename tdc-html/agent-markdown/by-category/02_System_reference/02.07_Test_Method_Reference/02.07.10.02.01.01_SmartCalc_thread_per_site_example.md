# SmartCalc thread per site example

An SMC thread per site requires the implementation of SMC_ARM() outside of the ON_FIRST_INVOCATION block. A separate thread is created for each active site. The processed site is defined by the site that is in focus when the thread is created and can be read by SMC_SITE_NUMBER().

The following example shows how a thread is created per site: Function [SMC_ARM()](<02.07.04.01.231.01_SMC_ARM.md>) is called outside of the [ON_FIRST_INVOCATION](<02.07.04.01.138_ON_FIRST_INVOCATION_BEGIN.md>) block. The run() function of the test method class is invoiced once for each active site and function [SMC_backgroundProcessing()](<02.07.04.01.231.01_SMC_ARM.md#_120107__s_SMC_backgroundProcessing>) is therefore started in a separate thread for each active site.

 Some items to consider for the example:

- Data are transferred as parameter to the SMC_backgroundProcessing() function. For [thread safety](<02.07.10.02.02_Thread_safety.md>), SMC_ARM() transfers only a copy of the received data. For large amount of data, we recommend therefore using member functions of the test method class as shown in the [SmartCalc common thread example](<02.07.10.02.01.02_SmartCalc_common_thread_example.md>).
- The example shows only how to create a thread per site and contains therefore no real test code.
- Some dummy data are created using the std::rand() function. These data are for demonstration only and need not to be created or processed in a real test method.
- There are also some dummy wait times created using the std::rand() function. These wait times should emulate the time for processing data, are for demonstration only and need not to be implemented in a real test method.

```
#include "testmethod.hpp"
#include "mapi.hpp"

using namespace std;

class threadPerSite: public testmethod::TestMethod {

protected:

    virtual void initialize()
    {
    }

    virtual void run()
    {
        ON_FIRST_INVOCATION_BEGIN();
        {
            //
            // Start your test in on all active sites
            //
            // ...
        }
        ON_FIRST_INVOCATION_END();

        //
        // Create dummy data to be transferred to the background process
        //
        double testData = 1.0 * std::rand()/RAND_MAX;

        cout << "Testsuite: run() - Data of site " << CURRENT_SITE_NUMBER() << ": " << testData << endl;

        //
        // Arm the SMC_backgroundProcessing() method and transfer the dummy data
        //
        SMC_ARM(testData);

        return;

    } // virtual void run()

public:

    void SMC_backgroundProcessing(double receivedData)
    {
        //
        // Wait time emulates time for processing
        //
        WAIT_TIME (50.0 ms * std::rand()/RAND_MAX);

        //
        // Show processed site and data
        //
        cout << setw(45) << "" << "SMC thread of site " << SMC_SITE_NUMBER() << " - Data = " << receivedData << endl;

    } // void SMC_backgroundProcessing ...

}; // class threadPerSite

REGISTER_TESTMETHOD("threadPerSite", threadPerSite);
```

 Note

The example above contains a call of cout in function [SMC_backgroundProcessing()](<02.07.04.01.231.01_SMC_ARM.md#_120107__s_SMC_backgroundProcessing>). cout is not thread safe. In production test cout must never be used in a background process.

When using cout in a background process, you have to expect a mix up of the output in the ui_report window and possibly other unwanted behavior. For more information, refer to [Thread safety](<02.07.10.02.02_Thread_safety.md>).

 For a test program with eight configured sites and site 4 and 7 disabled, the code above results in an output in the ui_report window similar to the following text:

```
Testsuite: run() - Data of site 1: 0.156679
Testsuite: Thread_per_site PASSED on site 1
Testsuite: run() - Data of site 2: 0.12979
Testsuite: Thread_per_site PASSED on site 2
                                             SMC thread of site 2 - Data = 0.12979
                                             SMC thread of site 1 - Data = 0.156679
Testsuite: run() - Data of site 3: 0.998925
Testsuite: Thread_per_site PASSED on site 3
                                             SMC thread of site 3 - Data = 0.998925
Testsuite: run() - Data of site 5: 0.512932
Testsuite: Thread_per_site PASSED on site 5
Testsuite: run() - Data of site 6: 0.61264
Testsuite: Thread_per_site PASSED on site 6
                                             SMC thread of site 6 - Data = 0.61264
                                             SMC thread of site 5 - Data = 0.512932
Testsuite: run() - Data of site 8: 0.637552
Testsuite: Thread_per_site PASSED on site 8
                                             SMC thread of site 8 - Data = 0.637552
```

The output in the ui_report shows the following behavior of the example code:

- Although the independent threads are created in the same order as SmarTests loops through the active sites, the (emulated and variable) time for processing leads to an undefined execution order of the threads. This must be considered when accessing common data.
- The threads may need some more time for processing after the test method as been finished. This demonstrates the principle of saving test time by SmartCalc but requires also some more actions: [SMC_SYNCHRONIZE()](<02.07.04.01.231.43_SMC_SYNCHRONIZE.md>) or [SMC_SYNCHRONIZE_WITHOUT_BINNING()](<02.07.04.01.231.44_SMC_SYNCHRONIZE_WITHOUT_BINNING.md>) are to be called in a subsequent test suite to wait for the end of the execution of all threads.
