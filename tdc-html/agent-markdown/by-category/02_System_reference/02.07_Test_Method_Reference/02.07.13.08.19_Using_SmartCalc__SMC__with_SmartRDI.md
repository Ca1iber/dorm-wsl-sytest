# Using SmartCalc (SMC) with SmartRDI

#### Subtopics

- [Using hidden upload with SmartRDI](<02.07.13.08.19.01_Using_hidden_upload_with_SmartRDI.md>)
- [SmartRDI functions controlling SmartCalc (SMC)](<02.07.13.08.19.02_SmartRDI_functions_controlling_SmartCalc__SMC.md>)
- [SmartRDI examples for SmartCalc (SMC)](<02.07.13.08.19.03_SmartRDI_examples_for_SmartCalc__SMC.md>)

SmartRDI can be used in combination with the SmartCalc (SMC) framework. This allows you to move time consuming calculations and uploads of test results to separate background threads and executing them in parallel.

For concepts and detailed information refer to [SmartCalc framework](<02.07.10_SmartCalc_framework.md>).

For a list of all SMC related test method APIs, refer to [SMC_... (SmartCalc API reference)](<02.07.04.01.231_SMC_...__SmartCalc_API_reference.md>).

## Basic structure

A test suite, based on SmartRDI, utilizes the same structure as a test method that uses test method APIs only:

- Background processes are armed by the [SMC_ARM()](<02.07.04.01.231.01_SMC_ARM.md>) function or the variants of this function. Each [SMC_ARM()](<02.07.04.01.231.01_SMC_ARM.md>) call creates a new thread. For more information, refer to [SMC_... (SmartCalc API reference)](<02.07.04.01.231_SMC_...__SmartCalc_API_reference.md>).
- The background process itself is defined as public [SMC_backgroundProcessing()](<02.07.04.01.231.01_SMC_ARM.md#_120107__s_SMC_backgroundProcessing>) function within the test method class of the test suite.
- The SmartRDI functions used for the setup and used to retrieve the data are the same for tests utilizing hidden upload and tests without hidden upload: Just the functions to retrieve the results are to be moved from the run() function to the [SMC_backgroundProcessing()](<02.07.04.01.231.01_SMC_ARM.md#_120107__s_SMC_backgroundProcessing>) function.
- SmartRDI uses [rdi.hiddenUpload()](<02.07.13.08.19.02.03_rdi.hiddenUpload.md>) to enable the hidden upload feature, which allows SmartRDI to perform the upload of data in the [SMC_backgroundProcessing()](<02.07.04.01.231.01_SMC_ARM.md#_120107__s_SMC_backgroundProcessing>) function of the test suite.
- Ensure that SMC gets enough time to access the hardware in the background threads. For more information, refer to [Hide analog and digital data upload](<02.07.10.05_SmartCalc_recommendations.md#_119876__s_Hide_analog_and_digital_data_upload>) in [SmartCalc recommendations](<02.07.10.05_SmartCalc_recommendations.md>).

For general information on how to implement an SMC test, refer to [Four-step SmartCalc implementation](<02.07.10.04.03_Four-step_SmartCalc_implementation.md>) in the [SmartCalc framework](<02.07.10_SmartCalc_framework.md>) documentation.

## Thread per site and common thread

Each function call and each thread takes some time overhead for preparation and cleanup. This overhead in test time depends also on the ratio of function calls and threads and the number of available CPU cores. For high-site-count applications, the overhead my exceed the benefit of using background threads or hidden uploads respectively.

The [SmartCalc framework](<02.07.10_SmartCalc_framework.md>) supports therefore two implementations of background processes:

  Thread per site The "Thread per site" is armed by [SMC_ARM()](<02.07.04.01.231.01_SMC_ARM.md>) or the variants of this function outside of the [ON_FIRST_INVOCATION](<02.07.04.01.138_ON_FIRST_INVOCATION_BEGIN.md>) block. The "Thread per site" is recommended for low site-count applications. Common thread The "Common thread" (also know as "Single thread") is armed by [SMC_ARM()](<02.07.04.01.231.01_SMC_ARM.md>) or the variants of this function inside of the [ON_FIRST_INVOCATION](<02.07.04.01.138_ON_FIRST_INVOCATION_BEGIN.md>) block. The "Common thread" is recommended for high site-count applications.

For more information, refer to [SmartCalc "Thread per site" and "Common thread"](<02.07.10.02.01_SmartCalc__Thread_per_site__and__Common_thread.md>).

 CAUTION

Within a test suite, SmartRDI supports either the implementation "Thread per site" or "Common thread" with one thread for all active sites.

Mixing the two solutions by assigning multiple active sites to more than one thread (multisite per thread) is not supported and can lead to invalid logging of results. For example: A solution with 16 sites and 4 threads is not supported.
