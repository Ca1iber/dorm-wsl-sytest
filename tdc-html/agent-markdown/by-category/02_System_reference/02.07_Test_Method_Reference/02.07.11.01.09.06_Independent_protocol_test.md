# Independent protocol test

Independent tests serve to run a protocol pattern asynchronously to the simulation patterns. Typically, the simulation ports will be started before the protocol port. The execution of the protocol port may or may not overlap with the execution of the simulation ports. The asynchronicity is needed, for example, for trimming.

Since the simulation ports and the protocol port are to run asynchronously, they must be started from different execution contexts. The protocol context is started by the INDEPENDENT_TEST object. The simulation context can be started, for instance, with the START_TEST (which must be used if the two contexts are to run in parallel) or FUNCTIONAL_TEST APIs. For more information on execution contexts see [Using execution contexts](<../02.06_Command_Reference/02.06.07.01.08.05.03.02.03_Using_execution_contexts.md>).

 Note In general, if an execution context is to be run, the current start label must be a multiport burst, and the ports that occur in the execution context must be present in this multiport burst. But the port of an independent protocol test is an exception to this rule. Protocol ports must always be omitted from the start label; this holds not only for synchronized, but also for independent protocol tests. The reason for the general rule is that the multiport burst identifies the label that is to be executed for the respective port. But a protocol pattern is generated dynamically from the protocol and the parameter values provided by the test method. Thus, recourse to the start label is unnecessary and would lead an inconsistency.

In contrast to synchronized protocol tests, the transactions of an independent protocol test are not pre-compiled to cycle based vectors. The translation is only executed at runtime. Therefore, only the protocol pattern of the last executed independent test can be viewed in the Pattern Debug Tool in each case.

An independent protocol test may contain both static and dynamic transactions.
