# Note on cache management

The test method API's store the parameter sets which they have downloaded to the firmware in a cache. They use this cache to determine if a parameter set they are required to download is already present in the firmware (so that it need not be downloaded again), and to restore the original values of a set after a temporary modification. This behavior can be impaired by:

- Clearing the cache
- Declaring the objects of the API's as static or global

This can cause the following problems:

- By default, the cache is cleared whenever the test methods are notified that some fundamental settings have been changed by calling a firmware command. The clearing has the consequence that the test methods cannot recognize any longer which parameter sets are already present in the firmware, and will therefore unnecessarily download these sets when they are requested to do so the next time. This will slow down the testflow loop.
- If an object of one of the API's is declared as static or global, temporary modifications of a parameter set will no longer be canceled after termination of the test method. This can have the effect that other test suites, which also use the original parameter values, assume erroneously that their parameters are already present in the firmware, and consequently use incorrect data.
- If the cache is cleared and an API object is static or global, the testflow may crash. The reason for this is that the static object contains a pointer to the cache which will become invalid after clearing the cache.

You can cause the test methods to ignore the notification, and not to clear the cache, with the DISABLE_CHANGE_NOTIFICATION API (and restore the default behavior with the ENABLE_CHANGE_NOTIFICATION API). But this entails the risk that the cached data is no longer valid. Note also that the suppression is effective for only one notification. Therefore, you must call the DISABLE_CHANGE_NOTIFICATION API before every firmware call.

The clearing of the cache can also be prevented by setting the environment variable TM_AUTO_REFRESH to NO. In contrast to the API, the setting of the environment variable has a permanent effect.

When the cache is cleared, a warning is issued. You can suppress this warning with the DISABLE_CLEAR_CACHE_WARNING API. The ENABLE_CLEAR_CACHE_WARNING API restores the default behavior. The warning can also be suppressed by setting the environment variable TM_DISABLE_CLEAR_CACHE_WARNING to YES.
