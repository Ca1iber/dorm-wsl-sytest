# Controlling Multi-port Test

#### Subtopics

- [APIs for executing concurrent tests](<02.07.03.14.01_APIs_for_executing_concurrent_tests.md>)
- [Test Method Programs for Multi-port Test](<02.07.03.14.02_Test_Method_Programs_for_Multi-port_Test.md>)

The following test method APIs can be used to control and execute a multi-port test. For details of each API, see [API Reference](<02.07.04_API_Reference.md>). For details of the multi-port testing and its programming, see the manual "Multi-Port Testing".

- [DIGITAL_CAPTURE_TEST](<02.07.04.01.35_DIGITAL_CAPTURE_TEST.md>), [NB_DIGITAL_CAPTURE_START](<02.07.04.01.135_NB_DIGITAL_CAPTURE_START.md>) and [NB_DIGITAL_CAPTURE_END](<02.07.04.01.134_NB_DIGITAL_CAPTURE_END.md>), or [FUNCTIONAL_TEST](<02.07.04.01.75_FUNCTIONAL_TEST.md>)

Executes the multi-port test. If a capture pin is used in the multi-port test, DIGITAL_CAPTURE_TEST or

NB_DIGITAL_CAPTURE_START and NB_DIGITAL_CAPTURE_END must be used. Otherwise, use FUNCTIONAL_TEST.

In the [PMU_VFIM](<02.07.04.01.152_PMU_VFIM.md>), [PMU_IFVM](<02.07.04.01.151_PMU_IFVM.md>), or [DPS_VFIM](<02.07.04.01.51_DPS_VFIM.md>) API, you can execute the multi-port test to generate the digital vectors before the DC test.

- [TEST](<02.07.04.01.241_TEST.md>)(port, continue)

Retrieves, judges, and logs the functional test result of the specified port (port). This API also returns the judgment result.

This API without port judges pass/fail by whether all ports are all pass or not. Even in this case, the functional test results are logged for each port if the start label of the multi-port test is a multi-port burst label.

- [GET_FUNCTIONAL_RESULT](<02.07.04.01.88_GET_FUNCTIONAL_RESULT.md>)(port)

Retrieves and returns the functional test result of the specified port (port). No judgment and no data logging is performed. This API without port returns whether the functional test results in all ports are all pass or not.

- Primary.timing(tset, port)

Specifies a timing set (tset) to be defined as the primary at the specified port (port).

This is a statement of the [PRIMARY_STATUS - (Primary)](<02.07.04.01.167_PRIMARY_STATUS_-__Primary.md>)API.

- Primary.timing( SPECIFICATION(specif) );

Specifies a specification (specif) to be defined as the primary. The specification is specified by using the corresponding [SPECIFICATION](<02.07.04.01.232_SPECIFICATION.md>) API's class object.

- Primary.label(label)

Specifies the start label (label). A multi-port burst label can be specified as the start label.

- Primary.getSpecification().

 change("spec@port", value)

Specifies the new value (value) of a spec (spec) at the specified port (port) in the currently defined primary specification. The Primary.getSpecification() statement returns the SPECIFICATION API's class object currently defined as the primary.

- Primary.getSpecification().restore

Resets the values of all specs to the ones when the test method program in the current testsuite is started. These resetting is actually performed when the FLUSH API is executed.

- Primary.getSpecification().getName()

Returns the specification name currently defined as the primary.

- Primary.getTiming(port)

Returns the timing set number currently defined as the primary in the specified port (port).

- Primary.getLabel()

Returns the start label name currently activated. A multi-port burst label name is returned if it is activated as the start label.

- Primary.isTimingPortBased()

Returns true if any specification of the timing setup is currently defined as the primary (that is, true if the current timing setup is port-based). Otherwise (that is, a non-multi-port spec set or waveform set is used), this returns false.

 Note Do not mix the usage of the firmware command with the test method API to query or change the hardware status. The test method API uses an internal cache which is not known and not accessible to the firmware command. The hardware status change made with the firmware command is not recorded in the cache and the subsequent hardware status querying with the test method API may return an incorrect result. To query the hardware status with the test method API, you need to change the hardware status with the test method API. To query the hardware status with the firmware command, you need to change the hardware status with the firmware command.
- Primary.isLabelPortBased()

Returns true if any multi-port burst label is currently activated as the start label. Otherwise, this returns false.

Only the APIs that have the multi-port test unique functionality are listed in the above. The other APIs can also be used in the test method program where a multi-port test is executed.
