# Result areas for hidden digital upload

Result areas allow independent data capture and upload.

Capture samples of several test suites can be collected before an upload is executed. SmartCalc provides the framework to perform upload and calculation in such a way that the test suites remain self-contained, while ensuring excellent test time. For traditional error map data, see [Result areas for error map data](<02.07.04.01.190.09_Result_areas_for_error_map_data.md>).

By creating a `RESULT_AREA_CONFIG` object for all digital capture pins the number of bytes needed are specified. Each byte can hold the result of several capture samples, depending on the x-mode being used.

The function `appendArea()` allocates the memory of the given size and maps it to the identifier. The result size of selective capture depends on the following rules:

ResultAreaSizeInBytes = NumberOfSamples / SamplesPerByte + 1024

Parameter
 |

NumberOfSamples

 |

Total number of capture samples per pin to be recorded, including initial, inter-sample and inter-frame discards.

 |
 |

SamplesPerByte

 |

Depending on the x-mode used, either

4 in x1/2 mode or

8 in x4/8 mode.

 |
 |

1024

 |

internal Buffer.

   |  Note Discarded capture samples will not be uploaded, but require capture memory. Note Result areas reduce the available memory and accessing a large number of them may impact your test times. Therefore, the total number of allocated result areas should be minimized and stay below 465 in total. That is, the sum of all TMU, digital, and DC result areas must not exceed 465. Out of this, 15 areas are reserved as minimum for TMU and a maximum of 100 areas can be allocated for TMU.

In order to activate result areas defined by `appendArea()` use `activate()`. It is possible to re-define result areas within a test flow, however a re-issued `activate()` deletes all previously defined areas.

If you need to activate new result areas defined within individual test suites, use `activateWithoutOverwrite()` not to delete the previous result areas.

`RESULT_AREA_CONFIG` has two methods to release the allocated memory:

- `.release()`
- `RESULT_AREA_CONFIG::removeAllAreas()`

As `RESULT_AREA_CONFIG` internally does not access HW its overhead is negligible.

## Examples

### Determine NumberOfSamples

To determine the required memory size with the formula shown above, use 1536 for the NumberOfSamples, for a vector variable with an initial discard of 512 samples and 1024 capture samples.

Note Capture cycles are different to capture samples in all but the x1 mode!

- 1024 captures samples in x2 mode translate to 512 capture cycles.
- 1024 captures cycles in x2 mode translate to 2048 capture samples.

### Determine ResultAreaInBytes

- 1024 capture samples in X2 mode

NumberOfSamples = 1024

SamplesPerByte = 4

ResultAreaSizeInBytes = 1024 / 4 + 1024 = 1280

- 128000 capture samples in X1 mode

ResultAreaSizeInBytes = 128000 / 4 + 1024 = 33024

- 16000 capture cycles in x8 mode

NumberOfSamples = 16000 * 8 = 128000

SamplesPerByte = 8

ResultAreaSizeInBytes = 128000 / 8 + 1024 = 17024

- 8000 capture cycles in x4 mode

NumberOfSamples = 8000 * 4 = 32000

SamplesPerByte = 8

ResultAreaSizeInBytes = 32000 / 8 + 1024 = 5024

### Source code

```
ON_FIRST_INVOCATION_BEGIN();

    // Define resConf for all digital capture pins
    RESULT_AREA_CONFIG resConf("p1,p2,p3,p4,p5,p6,p6,p8");

    // Allocate and map memory to identifier
    resConf.appendArea("16KBITArea",3072).appendArea("128KBitArea",17408).activate();

ON_FIRST_INVOCATION_END();
```
