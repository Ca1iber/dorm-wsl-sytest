# SYNCHRONIZED_TEST

The `SYNCHRONIZED_TEST` class sets up a synchronized test within a test method. It is derived from the `PROTOCOL_TEST` class.

An object of this class is declared in the test method implementation. It can be populated with a sequence of transactions implemented by subsidiary classes `TRANSACTION_SEQUENCE()` and `TRANSACTION()`. The test can be synchronized to other ports by adding synchronization points between transaction sequences, which must be defined as part of another port's pattern. If multiple instances of one test should run in a single functional test, then they must be cloned and attached to new synchronization points.

The synchronized test is the main interface for execution of protocol based synchronized functional test. Each synchronized test object is associated with a port and uniquely named. At any functional test execution each port of the selected multiport burst can only be associated with a synchronized test or simulated vectors and it can execute only a single synchronized test. If similar transaction sequences are required on multiple ports, a separate function has to be defined to create multiple objects. This way no clone operation on the test or transaction sequence object is required.

Note If you want to debug a synchronized protocol test with the Timing Diagram, you must place a breakpoint in the test method code before calling the unlink() function.

This API is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/SynchronizedTest.h.

If no name is provided, the name will automatically be generated from the current test suite name, the provided port and the multi-port burst label.

If no multi-port burst label is provided, it will be specified through the sequencer start label set at the time when the synchronized test object is constructed.

The synchronized test's protocol pattern will be generated based on the provided wavetable and associate it with the given multi-port burst label. When the according sequencer program is generated, it is hooked into that multi-port burst label and thus can be executed as part of a functional test running on that label.

The actual test definition will be cached beyond the execution of a single test method so that subsequent identical definitions using the same name and same sequence of transactions will not require modifications of the resulting pattern.

Note If the same name is used sequentially for different synchronized tests for example, in different test suites) the previous definition will be overwritten.Note It is not allowed to specify several protocol test objects with identical name existing concurrently!Note Possible setup errors will be shown only when executing the member function `flush()`, refer to the description of this member function below.

Execution of synchronized test is performed by the standard APIs used to execute functional tests, after the synchronized test object is associated with a sequencer start label. The translation of a transaction sequence to a digital pattern is time critical and optimized for multiple executions of the same synchronized test.

Transactions which receive data from the device can cause two kinds of failures:

- Protocol violations: This may occur if fixed fields in the transaction do not match the data received.
- Expected data failure: This failure type depends on the mode in which a synchronized test is executed.

If a read transactions capture device responses the fail condition can only be determined in the test method code by checking the result value of the read operation.

If a read transaction is compare against expected data the global pass/fail condition will immediately be affected by the non-matching response.

## Member functions

### add()

```
TRANSACTION_SEQUENCE& add(const STRING& syncPort, const STRING& syncMarker);
```

Parameters
 |

 |

(optional) Port to be used for synchronization.

 |
 |

I

 |

syncMarker

 |

(optional) Name of the marker the new sequence will be synchronized with.

If not specified, an empty string "" has to be used.

 |

Adds an empty transaction sequence to the end of the test.

The new sequence is synchronized to the specified syncMarker which must be defined in the pattern selected on the specified syncPort.

Note Delay cycles or delay time specified in addition to synchronization will be applied after synchronization.

If no syncMarker is used, an empty string must be given. In this case the transaction execution will start without inserting any idle vectors (except a delay is specified via the `PROTOCOL_TEST` class).

If the syncMarker is specified, then also the syncPort must be specified.

If multiple transaction sequences are added all syncPorts must be in the same synchronization group. If none of these transaction sequences has a syncPort specified, the synchronized test will then run without the transactions being synchronized.

### flush()

```
Boolean flush();
```

Parameter
 |

I/O

 |

Parameter

 |

Description

 |
 |

O

 |

boolean

 |

TRUE is returned if no error occurred.

FALSE is returned if the test setup cannot be translated to a pattern.

 |

Finishes the definition of the synchronized test and translates it to a pattern representation ready to be executed by functional test. This method must be called before test execution because the functional test itself has no link back to the synchronized test. The link is established by this method, which hooks the synchronized test into the multiport burst label to be executed by a functional test. For executing the test, the associated multi-port burst label must be selected as the start label (either via test suite dialog settings or the `PRIMARY_STATUS` class).

Executing this method will prevent further access to previously acquired result values on the same test object.

The function will return FALSE if the test has a bad setup and cannot be translated to a pattern for example, missing synchronization point, missing label name...).

If the synchronized test object's name conflicts with other protocol test object names that exist concurrently, the method call will fail (refer to the constructor description).

### unlink()

```
static void unlink();
static void unlink(const STRING &label);
static void unlink(const STRING &name, const STRING &label);
```

Parameters

 |

 |

 |

 |

Multiport burst label used with the synchronized test.

Removes the association between the flushed synchronized test identified by its name and the multiport burst label. It must be used, for example, if the same multi-port burst is to be used for more than one protocol test within one testflow.

If name is not specified to identify the synchronized test, it removes existing associations between all flushed synchronized tests and the provided multi-port burst label.

If no parameter is given, it removes all existing associations between all flushed synchronized tests and their accordingly specified multi-port burst labels.

This method does not wait for the next `flush()` to update the synchronized test data. It immediately removes the associations between synchronized tests and multi-port burst labels.

### link()

```
void link();
```

Links the related synchronized test object to the originally defined multiport burst. This function works only, if `SYNCHRONOZED_TEST.unlink()` has been executed before.

### relink()

```
void relink();
```

Relinks the related protocol test object to the originally defined multiport burst after removing all associations between all protocol tests and existing multiport labels first. As such it combines the functions `SYNCHRONOZED_TEST.unlink()` and `SYNCHRONOZED_TEST.link()`.
