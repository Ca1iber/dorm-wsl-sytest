# PROTOCOL_TEST

`PROTOCOL_TEST` is an abstract class that contains the common member functions of several derived classes each of which represents a different kind of protocol based test. Two such classes are SYNCHRONIZED_TEST and SERIAL_LINK_TEST. You cannot create a PROTOCOL_TEST object directly, but only through a derived class.

## Using the SmartCalc framework for protocol tests

The SmartCalc framework can be used for result processing of protocol tests. In principle, all you have to do is to set the protocol test into background processing mode with the smcArm() member function. However, the following prerequisites must be fulfilled:

- In a multi-site setup, smcArm() must be called within the FOR_EACH_SITE block.
- smcArm() must be called before calling SMC_ARM().
- The protocol test must be defined dynamically within the run() function, otherwise it may no longer exist when the background process needs it to retrieve the results.
- Bulk upload must be enabled (see the enableBulkUploadMode() function).
- If the test object is reused, smcArm() must be called every time it is executed.

For a code example, see below.

This API is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/ProtocolTest.h.

## Member functions

### reserveTransactionMemory()

```
static Boolean reserveTransactionMemory(const STRING &port, INT sizeInBytes = TM::PROTOCOL_TEST_AUTO)
```

Parameter
 |

I/O

 |

Parameter

 |

Description

 |
 |

I

 |

port

 |

Identifier of the port to be used.

 |
 |

I

 |

sizeInBytes

 |

Memory size in Byte.

If omitted: `PROTOCOL_TEST_AUTO`, enables the uses up to all available channel memory.

 |
 |

O

 |

boolean

 |

TRUE, if memory could successfully be reserved.

FALSE, if memory could not be reserved.

 |

Sets the maximum memory size to be used for vector fragments of protocol test transactions per channel resource on the given port.

The size will be automatically increased to the closest size that is integer-dividable by 64 bit. If this function is called for several ports with overlapping channel resources, the memory size is applied per port, i.e. the size valid for a channel resource is finally determined by the sum of all ports definitions that contain the channel resource.

Calling `reserveTransactionMemory()` will internally clear the tester memory utilization log, but leave logging in its current state.

Execution of this method will perform a cleanup of all memory entries and a deletion of all patterns generated through protocol tests. Thus the pattern cannot be accessed from the pattern editor anymore.

If no sizeInByte is specified, the default `TM::PROTOCOL_TEST_AUTO` will be used. In this case the protocol test transaction memory with its cache will grow up to the maximum available free channel memory. However, this could mean that subsequent tests may not get sufficient memory, for example, for result storage, if the transaction memory grows into their demanded memory area. In this particular case the system will dynamically increase the size of reserved transaction memory needed until it reaches the system limit.

Defining a distinct transaction memory size reserves the according memory immediately and ensures its size does not grow beyond.

### add()

```
TRANSACTION_SEQUENCE& add(DOUBLE delayTime);
TRANSACTION_SEQUENCE& add(INT delayCycles = 0);
```

This function adds an empty sequence of transactions to the end of the test. The new transaction sequence is not synchronized to another port but may have an associated delay specified in cycles or seconds.

A transaction sequence must contain at least one transaction if the delay is 0. But it is allowed to be empty if the delay is > 0.

This member function uses the caching mechanism for transactions. This may prolong the test unnecessarily if the parameter values for the protocol change very often. In this case it is recommended to use addVolatile().

### getResult()

```
UINT64 getResult(const STRING& resultName);
STRING getResult(const STRING& name, TM::FORMAT format);
```

Parameter
 |

I/O

 |

Parameter

 |

Description

 |
 |

I

 |

resultName

 |

Name of a result area that has been used in a capture action (capture() function of the TRANSACTION class).

 |
 |

I

 |

format

 |

Specifies the format of the returned sting.

Possible formats are:

`TM::HEX` hexadecimal literal prefixed with 0x

`TM::BIN` binary literal prefixed with 0b

`TM::SCS` the captured bits without any prefix

`TM::SYMBOL` symbolic value, if the parameter was set up with symbolic values

 |
 |

O

 |

UINT64

 |

Result access with a max length of 64 bit.

 |
 |

O

 |

string

 |

Result access with a length more than 32 bit.

 |

This function returns the result data of the specified result area. If the enableBulkUploadMode() member function of the PROTOCOL_TEST class is set to TRUE (which is the default), the capture results are uploaded for all sites in parallel into a cache on the work station by the first call of getResult(); all later calls within the same test method access this cache. This is independent of whether or not the first call is placed within the ON_FIRST_INVOCATION block. If enableBulkUploadMode() is set to FALSE, getResult() only returns the result of the site that has the query focus; in this case, getResult() must be placed outside the ON_FIRST_INVOCATION block.

The UINT64 version allows at most 64 bit values to be reconstructed. If larger parameter values should be read then the alternative syntax must be used.

The string version should be used if expecting more than 32 bit length of result data. In this case the format of the returned string has to be specified! If the format is set to SYMBOL and the captured value does not match any symbolic value the operation will return an empty string.

Exceptions will occur if:

- called for an empty transaction object, respectively if no valid results are available, i.e. no test executed yet or results already invalidated again
- the parameter identified by name was not set up to be captured.

### getTransactionResult()

This function returns the result of the transaction that is associated with the specified string. If the return value comprises more than 64 bit, the version that returns a string must be used.

This function requires that the transaction has only one result. This is in contrast to the getResult() function of the TRANSACTION class, where each result is associated with a different result area.

```
UINT64 getTransactionResult(const STRING& transactionIdString);
STRING getTransactionResult(const STRING& transactionIdString, TM::FORMAT format);
```

Parameters
 |

I/O

 |

Parameter

 |

Description/Range

 |
 |

I

 |

transactionIdString

 |

The transaction ID of the transaction the result of which is to be retrieved. If the transaction ID is unique within the test method, you can simply specify this string. But since you can use the same transaction ID for transactions in different transaction sequences, this ID alone will not always be sufficient to identify the transaction within the test method. A similar situation arises when the same persistent pattern (precompiled transaction sequence) is used more than once in a test.

Whenever such an ambiguity exists, the transaction instance must be identified by the compound string

persistent_pattern_name:occurrence_no:transactionIdString,

where

- __MAPI_GENERATED_TS__ must be specified for persistent_pattern_name if an transaction ID is used more than once in the test method code,

and

- occurrence_no counts

  - either the instances of the persistent pattern,
  - or the MAPI generated transaction sequences containing the specified transaction ID

 within the test method, starting from 0.

 |

format

`TM::HEX` hexadecimal literal prefixed with 0x

`TM::BIN` binary literal prefixed with 0b

`TM::SCS` the captured bits without any prefix

`TM::SYMBOL` symbolic value, if the parameter was set up with symbolic values

## Example

The following code fragment shows the use of the Smartcalc framework for a single-site synchronized test:

```
class Mdio_SMC: public testmethod::TestMethod {

protected:

. . .

  virtual void run()
  {
    FW_TASK("DCRT RAM, (Po01)");

    // Declare the synchronized test dynamically:
       SYNCHRONIZED_TEST *mdioTest = new SYNCHRONIZED_TEST("Po01");

    const int numReads = 100;

    ON_FIRST_INVOCATION_BEGIN();

      SYNCHRONIZED_TEST::unlink();
      for(int i=0; i<numReads; i++) {
        stringstream resultId;
        resultId << "read" << i;
        STRING resultIdStr = resultId.str();
        mdioTest->transaction("read").set("phyaddr", 0x0F)
                                     .set("regaddr", 0x15)
                                     .capture("data", resultIdStr);
      }
      if (!mdioTest->flush()) {
        cerr << "flush error \n";
        ERROR_EXIT(TM::ABORT_FLOW);
      }
      SMC_FUNCTIONAL_TEST();

      // Call smcArm() before SMC_ARM():
      mdioTest->smcArm(true);

    ON_FIRST_INVOCATION_END();

    SMC_ARM(numReads, mdioTest);
  }

public:
  void SMC_backgroundProcessing(const int& numReads, SYNCHRONIZED_TEST* mdioTest)
  {
    UINT64 *results = new UINT64[numReads];

    for(int i=0; i<numReads; i++) {
        stringstream resultId;
        resultId << "read" << i;
        STRING resultIdStr = resultId.str();
        results[i] = mdioTest->getResult(resultIdStr);
        UINT64 expectedResult = i;
        SMC_TEST("","", (results[i] == expectedResult) ? TM::Pass : TM::Fail, 0, TRUE);
    }
    bool testFailed = mdioTest->hasFailed();
    SMC_TEST("","", testFailed ? TM::Fail : TM::Pass, 0, TRUE);
    bool testError = mdioTest->hasProtocolError();
    SMC_TEST("","", testError ? TM::Fail : TM::Pass, 0, TRUE);

    delete(mdioTest);
    return;
  }

  . . .

};
```
