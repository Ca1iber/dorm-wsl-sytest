# SMC_TEST()

The API judges the test data as pass/fail and logs it. It holds information that defines numbering procedures for results in a given test suite.

The testname and testNumber parameters are used to assign user defined names and numbers to specific tests. In addition SMC_TEST() also supports the usage of soft- and hardbins.

SMC_TEST() buffers the data log values and outputs them as soon as the synchronization point ([SMC_SYNCHRONIZE()](<02.07.04.01.231.43_SMC_SYNCHRONIZE.md>)) is reached in the order as the different background threads are started. The first fail will decide about the fail bin in which [SMC_SYNCHRONIZE()](<02.07.04.01.231.43_SMC_SYNCHRONIZE.md>) will bin.

For details on binning rules, see [Use of bins with multisite tests](<../../03_Use_cases_and_application_papers/03.02_How_to_do_Multi-Site_Testing/03.02.02.06.08_Use_of_bins_with_multisite_tests.md>) and [Use of multibins](<../../03_Use_cases_and_application_papers/03.02_How_to_do_Multi-Site_Testing/03.02.02.06.07_Use_of_multibins.md>).

SMC_TEST() combines functionalities of [TESTSET.judgeAndLog_ParametricTest()](<02.07.04.01.244.10_TESTSET__.judgeAndLog_ParametricTest.md>) and [SET_MULTIBIN()](<02.07.04.01.212_SET_MULTIBIN.md>). Since SMC_TEST() inherently uses SET_MULTIBIN(), it is required to define multibins in the test flow at the test suite that contains the SMC_SYNCHRONIZE() command (usually the last test suite in the testflow). Failure to insert multibins will lead to anomalies in behavior.

If the number of sites is large (for example, 96 or more) the [SMC_ARM()](<02.07.04.01.231.01_SMC_ARM.md>) overhead time increases a lot. Consequently the SMC_TEST() will take longer to finish. To speed up the SMC_TEST() execution you can process the sites sequentially for all sites, this is accomplished by applying the SMC_ARM() only once for all sites within the ON_FIRST_INVOCATION_BEGIN() / ...END() block. Then evaluating the SMC_TEST() for all sites sequentially by specifying the site number.

Note The system-prepared object [TestSet](<02.07.04.01.244_TESTSET.md>) is not thread safe! Do not use it with SmartCalc. Always use SMC_TEST() or the dynamically created TESTSET().judgeAndLog_...() with SmartCalc applications.Note

If you use TESTSET within the [SMC framework](<02.07.10_SmartCalc_framework.md>) instead of [SMC_TEST](<02.07.04.01.231.45_SMC_TEST.md>), binning happens in [SMC_SYCHRONIZE](<02.07.04.01.231.43_SMC_SYNCHRONIZE.md>) according to the binning rules as for SMC_TEST. For details, see [Use of SMC_TEST() with multibin](<../../03_Use_cases_and_application_papers/03.02_How_to_do_Multi-Site_Testing/03.02.02.06.07.02_Use_of_SMC_TEST___with_multibin.md>).

If you use, within a testflow, the [SMC framework](<02.07.10_SmartCalc_framework.md>) and TESTSET test suites independent of each other, binning happens according to the binning rules explained in [Use of TESTSET and SMC_TEST() test suites with multibin](<../../03_Use_cases_and_application_papers/03.02_How_to_do_Multi-Site_Testing/03.02.02.06.07.03_Use_of_TESTSET_and_SMC_TEST___test_suites_with_multibin.md>).

If an error occurs in your program or an unpredictable trouble of the tester hardware occurs during testing, the test program can log the result as unreliable. For this you have to use the reliability parameter of SMC_TEST(). With the reliability parameter set to TM::UNRELIABLE, the [TEST](<02.07.04.01.241_TEST.md>) API also logs the unreliable state to the event data log stream with the test data such as pass/fail, result values, and so on.

 Parameters

 | Parameter  | Description |
 | site  | The site number |
 | pin  | The pin name (single pin name). |
 | testname  | The test name that can be referred from the Properties view. |
 | tmLimit  | Specifies the [TMLimits](<02.07.04.01.250_TMLimits.md>)[object](<02.07.04.01.250_TMLimits.md>) which will be used to extract the data for testNumber, softbin, hardbin as well as the limit data. |
 | limit |

The (optional) limit value to be used for the judgment. This parameter is a [LIMIT](<02.07.04.01.126_LIMIT.md>) API's class object. Hence, you can specify TM::Pass or TM::Fail to make the test result pass or fail intentionally.

If the parameter limit is not specified, the limit values specified in the properties view of the test suite containing [SMC_SYNCHRONIZE()](<02.07.04.01.231.43_SMC_SYNCHRONIZE.md>) will be used.

If you specify TM:Pass within the [LIMIT](<02.07.04.01.126_LIMIT.md>) class, the test alway will pass, regardless of the actual test result.

If you specify TM:Fail within the [LIMIT](<02.07.04.01.126_LIMIT.md>) class, the test always will fail, regardless of the actual result.

 |
 | value  | The test result value. |
 | Continue |

This optional parameter controls whether the test should be continued if SMC_TEST() evaluates to FAIL. If it is set to TRUE, the test is continued in spite of a real FAIL result. If it is set to FALSE (default), the test is terminated.

 Note The API behaves differently for the first site in a multi-site setup. In this special situation, the test is always continued, even if the TEST API returns FAIL and the continue parameter is set to FALSE. For the following sites, the test is terminated under these conditions. |
 | reliability |

This optional parameter is used to indicate the reliability of the test result for data logging.

To indicate the test is reliable, specify TM::RELIABLE.

To indicate the test is unreliable, specify TM::UNRELIABLE.

You can omit this parameter. If so, use the syntax without this parameter. At that time, it is the same as specifying TM::RELIABLE.

 Note SMC_TEST() does not log the reliable state even if the parameter is set to TM::RELIABLE. |
 | testNumber  | An integer value that you assign to directly generate a subtest test number in the EDL. Value must be >= 0. |
 | softbin  | The software bin number of the multibin. For details see the [SET_MULTIBIN](<02.07.04.01.212_SET_MULTIBIN.md>) API. |
 | hardbin  | The hardware bin number of the multibin. For details see the [SET_MULTIBIN](<02.07.04.01.212_SET_MULTIBIN.md>) API. |
 | logTestNumber |

An optional test number.

If this test number is provided, it overrides the actual test number. If it is not provided, the actual test number is logged.

 |
 | testtext  | Text be added to the data log stream for this SMC_TEST() call.  |    Return value There is no return value.

## Examples

### Example 1: General usage

SMC_TEST() compares the thd_result data with the limit range specified in the parameter dialog of [SMC_SYNCHRONIZE()](<02.07.04.01.231.43_SMC_SYNCHRONIZE.md>), then judges it as pass or fail.

```
SMC_TEST("dgtz_pin", "THD", thd_result);
```

The first SMC_TEST() call judges the thd_result data as pass or fail. Then the second SMC_TEST() judges the snr_result data as pass or fail because the TM::CONTINUE is set int the first SMC_TEST(). When the result of the first SMC_TEST() is pass, the test will continue even if you do not set the Continue parameter to TRUE.

```
SMC_TEST("dgtz_pin", "THD", thd_result, TM::CONTINUE);
SMC_TEST("dgtz_pin", "SNR", snr_result);
```

SMC_TEST() compares the thd_result data with the limit range specified by the [LIMIT](<02.07.04.01.126_LIMIT.md>) API, then judges as pass or fail.

```
SMC_TEST("Aout", "THD", LIMIT(TM::GT, low_limit,TM::LT, high_limit), thd_result);
```

SMC_TEST() compares the thd_result data with the limit range specified by the [LIMIT](<02.07.04.01.126_LIMIT.md>) API, then judges as pass or fail. In fail case it will bin into the specified softbin and hardbin.

```
SMC_TEST("Aout", "THD", LIMIT(TM::GT, low_limit,TM::LT, high_limit), thd_result, false, testNumber, "softbin", hardbin);
```

### Example 2: Using hidden data logging

The following example shows how hidden data logging can be implemented using the [LIMIT](<02.07.04.01.126_LIMIT.md>) class, without having the hidden_datalog_mode testflow flag enabled.

```
#include "testmethod.hpp"
#include "mapi.hpp"

using namespace std;

class hiddenDatalogWLimit: public testmethod::TestMethod
{
protected:

    virtual void initialize()
    {
        addLimit("TestName");
    }

    virtual void run()
    {
        ON_FIRST_INVOCATION_BEGIN();
        {
            SMC_EXECUTE_TEST( 1.0 );

            LIMIT lim = GET_LIMIT_OBJECT("TestName");

            FOR_EACH_SITE_BEGIN()
            {
                SMC_ARM(lim);
            }
            FOR_EACH_SITE_END();
        }
        ON_FIRST_INVOCATION_END();

        return;
    }

public:

    void SMC_backgroundProcessing(LIMIT lim)
    {
        INT    site   = SMC_SITE_NUMBER();
        double result = ...;

        cout << "Site: <" << site << "> " << endl;

        SMC_TEST(site, "PinName","TestName", lim, result);
    }
};
REGISTER_TESTMETHOD("hiddenDatalogWLimit", hiddenDatalogWLimit);
```

 Note

The example above contains a call of cout in function [SMC_backgroundProcessing()](<02.07.04.01.231.01_SMC_ARM.md#_120107__s_SMC_backgroundProcessing>). cout is not thread safe. In production test cout must never be used in a background process.

When using cout in a background process, you have to expect a mix up of the output in the ui_report window and possibly other unwanted behavior. For more information, refer to [Thread safety](<02.07.10.02.02_Thread_safety.md>).

### Example 3: Using test tables

The following two examples show how to use the limits and bins that a user has defined in a test table ( *.csv file). tmLimits causes SMC_TEST() to look at the loaded test table file and to compare the value contained in result to the limits of "PowerOut0" and to bin the result accordingly.

```
SMC_TEST("dgtPinName", "PowerOut0", tmLimits, result, true);
SMC_TEST("dgtPinName", "PowerOut0", V93kLimits::tmLimits, result, true);
```

Do not use the following code for background processing, because this will use the system prepared TestSet object, which is not thread safe!

```
SMC_TEST("dgtPinName", "PowerOut0", tmLimits.getLimitObj("PowerOut0"), result, true);
```

### Example 4: Handling large numbers of sites

The following example shows how to speed up the SMC_TEST() execution when the large numbers of sites increase the total computing time.

The transfer of the required data from function run() to function backgroundProcessing() is done via member variables mResultArray and mActiveSitesArray. Transferring the data as parameter of SMC_ARM() is also supported but this will increase the test time because all data that are transferred to the background process must be copied by SMC_ARM(). The array mActiveSitesArray must be updated in function run() before function SMC_backgroundProcessing() is called to ensure that only activated sites are processed.

```
#include "testmethod.hpp"
#include "mapi.hpp"

using namespace std;

class hiddenDatalogSequential: public testmethod::TestMethod
{
protected:

    ARRAY_D mResultArray;
    ARRAY_I mActiveSitesArray;

    virtual void initialize()
    {
    }

    virtual void run()
    {
        ON_FIRST_INVOCATION_BEGIN();
        {
            //
            // Initialize the result array for all configured sites
            //
            ARRAY_I configuredSitesArray;

            mResultArray.resize (GET_CONFIGURED_SITES(configuredSitesArray));
            mResultArray.init   (-1.0);

            //
            // Start functional test and retrieve the result for active sites
            //
            FUNCTIONAL_TEST();

            FOR_EACH_SITE_BEGIN()
            {
                Boolean result = GET_FUNCTIONAL_RESULT();

                mResultArray[CURRENT_SITE_NUMBER()-1] = (double) result;
            }
            FOR_EACH_SITE_END();

            //
            // Show the result array
            //
            cout << "Result array:";

            for (int index = 0; index < mResultArray.size(); index++)
            {
                cout << " " <<  mResultArray[index];
            }

            cout << endl;

            //
            // Get and show active sites
            //
            GET_ACTIVE_SITES(mActiveSitesArray);

            cout << "Active sites:";

            for (int index = 0; index < mActiveSitesArray.size(); index++)
            {
                cout << " " << mActiveSitesArray[index];
            }

            cout << endl;

            //
            // Arm the SMC_backgroundProcessing() method
            //
            // Note: Data are transferred by member variables mResultArray[] and mActiveSitesArray[].
            //
            SMC_ARM();
        }
        ON_FIRST_INVOCATION_END();

    } // virtual void run()

public:

    void SMC_backgroundProcessing()
    {
        //
        // Parse the resultArray array for all active sites
        //
        for (int index = 0; index < mActiveSitesArray.size(); index++)
        {
            double result = mResultArray[mActiveSitesArray[index] - 1];

            cout << "SMC - Processing site " << mActiveSitesArray[index] << " - Result = " << result << endl;

            SMC_TEST(mActiveSitesArray[index], "PinName", "TestName", result);
        }

    } // void SMC_backgroundProcessing ...

}; // class hiddenDatalogSequential: public testmethod::TestMethod

REGISTER_TESTMETHOD("hiddenDatalogSequential", hiddenDatalogSequential);
```

Note

The example above contains a call of cout in function [SMC_backgroundProcessing()](<02.07.04.01.231.01_SMC_ARM.md#_120107__s_SMC_backgroundProcessing>). cout is not thread safe. In production test cout must never be used in a background process.

When using cout in a background process, you have to expect a mix up of the output in the ui_report window and possibly other unwanted behavior. For more information, refer to [Thread safety](<02.07.10.02.02_Thread_safety.md>).

 In offline mode, the example above results in the following output in the ui_report window if eight sites are configured, sites 3 and 7 are deactivated:

```
Result array: 1 1 -1 1 1 1 -1 1
Active sites: 1 2 4 5 6 8
SMC - Processing site 1 - Result = 1
Testsuite: Test_2 PASSED on site 1
SMC - Processing site 2 - Result = 1
SMC - Processing site 4 - Result = 1
SMC - Processing site 5 - Result = 1
SMC - Processing site 6 - Result = 1
SMC - Processing site 8 - Result = 1
Testsuite: Test_2 PASSED on site 2
Testsuite: Test_2 PASSED on site 4
Testsuite: Test_2 PASSED on site 5
Testsuite: Test_2 PASSED on site 6
Testsuite: Test_2 PASSED on site 8
```
