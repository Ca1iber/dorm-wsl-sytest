# Universal test method concept

#### Subtopics

- [Test method executor](<02.07.02.01.01_Test_method_executor.md>)

Using universal test methods gives you the following benefits.

- Test method parameters and limits can be changed in the test method code without invalidating existing testflow files.
- Test method libraries can be distributed with a single shared library file. You can install the libraries in a central location to make them available to all test programs on a single workstation or even on a network. No special registration is necessary to make them visible in a test program.
- All sources in a test method project can be read and edited. Besides the actual source files, there are just two files containing the build and project information.
- Pre-compiled libraries with standard test methods are shipped with SmarTest. They can be directly used without compiling the test method projects.
- You can execute a UTM-based test suite while a testflow execution is paused or the debugging of a test method is paused at a breakpoint.

## Test method project

A test method project is a pure C++ project. The project is independent of all devices. You can use the test method in multiple devices by making reference to it. (See [How to create and execute a universal-test-method-based testflow](<02.07.02.02.03_How_to_create_and_execute_a_universal-test-method-based_testflow.md>).)

A universal test method project directory must be outside of any device directory and any Eclipse project directory. By creating a test method project, two project environment files are created under the test method project directory.

- .project: The general descriptions of the Eclipse project.
- .cproject: The information about the build setup, for example, the setup for the source code / library search path, required libraries and compile options.

## Test method class

A test method class is a C++ class implementation file. This is the test method source file. It always contains the following methods:

- initialize()

The functions defines a parameter and limit interface to the test method.

Calling the function:

  - The function is called once when the testflow is opened or when a new test method is added.
  - The function is called once when an already loaded test method is changed and recompiled.
  - At run-time, the function is called for each run of the testflow once at the beginning of each test suite.
  - When [looping](<../02.08_Setup_and_Result_Tools/02.08.04.32.02.03.01_Loop_configuration_settings.md>) the testflow, the function is called only for the first iteration once at the beginning of each test suite.
  - When looping a single test suite, the function is called for each iteration at the beginning of the test suite.
  - For the first run of a looped testflow, the function is called for bypassed test suites as well.

The APIs [addParameter()](<02.07.04.01.03_addParameter.md>) and [addLimit()](<02.07.04.01.02_addLimit.md>) are used in the method to define parameters and limits for the test method. Other test method APIs for setup, execution, and result calculation cannot be used in this function.

The sequence of the parameters definition is important. When you change the parameter values outside the test method class, these values will take effect sequentially according to the definition sequence in the `initialize()` method. The parameters will also be displayed in the Properties view in the definition sequence.

- run()

The function defines the test setting and measurement.

Calling the function:

  - The function is called once in each test suite for each active site during the test suite execution.Note Although the initialize() function is called only once at the beginning of each test suite, SmarTest initializes the parameters to the default value for each invocation of the run() function and therefore for each active site.If site specific setting or result handling is not required in the run() function and all actions can be performed with the first invocation, the invocation for the following sites can be disabled using API [setStopSiteLoop()](<02.07.04.01.215_setStopSiteLoop.md>) to save some test time.

You cannot call a test method in another test method. But you can call your own C/C++ functions in a test method. See [Using C/C++ functions from external libraries in universal test methods](<02.07.02.11_Using_C_C___functions_from_external_libraries_in_universal_test_methods.md>). Refer to [Test Method Programming Essentials](<02.07.03_Test_Method_Programming_Essentials.md>) for the test method programming in this `run()` method.

The test method APIs except for `addParameter()` and `addLimit()` can only be used in the `run()` method.

- postParameterChange(const std::string& parameterIdentifier)

The optional function needs to be implemented only if the custom parameter checking functionality is required in a test method. It defines the actions that will be taken after a parameter's value is changed.

Calling the function:

  - The function is called once when the testflow is opened or when a new test method is added.
  - At run-time, the function is called if a parameter is changed by [getParameter(...)](<02.07.04.01.92_getParameter.md>).[setValueAsString(...)](<02.07.02.13.05_TestMethodParameterProxy.md#_99972__dle_setValueAsString>) in the run() function.
  - At run-time, the function is called for each testflow run at the beginning of each test suite for each parameter that has been defined in the initialize() function. This is done after SmarTest has reset the parameters to the default values.

Note that the function is called twice by the initialize() function. The first call initializes the parameter to the default value defined by the [addParameter](<02.07.04.01.03_addParameter.md>) function. The second call sets the parameter to the value defined on the [Parameters page](<../02.08_Setup_and_Result_Tools/02.08.04.32.03.01.02_Parameters_page.md>) or via the [Test suite properties view](<../02.08_Setup_and_Result_Tools/02.08.04.32.03.04_Testflow_Properties_view.md#_99279__s_Test_suite_properties_view>).

You can define any post checking for the parameter itself or inter-dependencies with others. The actions will take effect according to the parameter definition sequence in the `initialize()` method. Do not use the test method APIs in this function.

- getComment()

This function returns the comment of the test method class.

Calling the function:

  - The function is called once when the Select Test Method dialog of the New Run Node Wizard is opened and a test method is selected. The comment of the test method class is displayed in the Info section of the dialog.

## Universal test method library

The universal test method library is a plain C++ shared library. When you build a test method project, a Debug directory, which holds the test method library and the compilation related files, will be created in the test method project directory.

Dependent on the test method application scope, you can put the test method libraries in the following directories:

- To use the test method library in a device testing, copy the library to the testmethod/sh_lib-EL7-64bit sub-directory of the device directory.
- To share the test method library with other users of the same SmarTest system, copy the library to the directory /var/opt/hp93000/soc/testmethod/sh_lib or /var/opt/hp93000/soc_common/testmethod/sh_lib.
- To use the libraries in other directories, you must either put them in the directories defined by the V93000_TM_LIBRARY_PATH variable, or add these directories to this variable.

(For details, see [Managing the universal test method libraries](<02.07.02.03_Managing_the_universal_test_method_libraries.md>).)

The predefined Test Method Libraries reside in the directory /opt/hp93000/soc/testmethod/sh_lib. You can directly use these libraries in your testflow. You can also modify the test methods and build your own customized libraries. (For details see [Using the predefined universal Test Method Libraries](<02.07.02.07_Using_the_predefined_universal_Test_Method_Libraries.md>))

## Universal test method snippets

Snippets are sections of code which are used frequently enough that you would like to insert them with a few key strokes. The following categories of snippets are provided with SmarTest:

ADC test, DAC test, DC test, Base band to RF test, CODEC test, RF to base band test. (For details, see [Test method snippets provided with SmarTest](<02.07.06_Test_method_snippets_provided_with_SmarTest.md>).)

These snippets are included in the snippet file /opt/hp93000/soc/testmethod/library/testmethodsnippet.xml. You can use these snippets through the Templates page of the Preference window. (Refer to [How to use test method snippets in test method programming](<02.07.02.09_How_to_use_test_method_snippets_in_the_programming.md>).)

## Concurrent test framework

Concurrent test framework helps to combine multiple independent tests to one concurrent test execution while maintaining the structure of each test. It provides a test method interface to implement the concurrent test and an engine to execute the concurrent test. (For details, see [Concurrent test framework](<02.07.08_Concurrent_test_framework.md>).)

## Universal test method path search sequence

When SmarTest and the test method executor start, the universal test method libraries are searched in the directories in the following sequence.

- Firstly, the test method libraries in the current device's sub-directory testmethod/sh_lib-EL7-64bit are searched. You can manually copy test method libraries here. When you build a device project in the SmarTest Work Center, all its referenced test method projects will be automatically built and the shared libraries will be copied here.
- If the libraries have not been found yet, the libraries in the directory /opt/hp93000/soc/testmethod/library/sh_lib will be searched. Currently the DC, AC and ppTIA test method libraries libac_tml.so, libdc_tml.so and libpptia_tml.so are provided here. Typically you Do not need to copy any further test method libraries here.
- If the libraries have not been found yet, the libraries in the directory /var/opt/hp93000/soc/testmethod will be searched.
- If the libraries have not been found yet, the libraries in the directory /var/opt/hp93000/soc_common/testmethod will be searched.
- If the libraries have not been found yet, the libraries under the directories defined by environment variable V93000_TM_LIBRARY_PATH will be searched.

The external libraries can be loaded before the test method library with the preload mechanism. These libraries must be named like libxxx.so, where xxx is a combination of letters, numbers or "_". In this mechanism, the external test method libraries need to be put in the directory device/testmethod/sh_lib-EL7-64bit/preload, /var/opt/hp93000/soc/testmethod/preload or /var/opt/hp93000/soc_common/testmethod/preload. (For details, see [Using C/C++ functions from external libraries in universal test methods](<02.07.02.11_Using_C_C___functions_from_external_libraries_in_universal_test_methods.md>).)

Note A UTM project created with SmarTest 6.3/CDT 3.1 can be automatically converted to a project supported by SmarTest 6.5/CDT 4.0. This automatic conversion is not revertible. You can only convert the project back manually by creating a new project and copying the source code in the project.

If you have not added any advanced build settings to the project, the converted project for 6.5 can still be used on SmarTest 6.3. Otherwise, to use the test method libraries both on SmarTest 6.3 and later versions, you need to backup the test method project before conversion.

## Example

The example below is a template of the test method source file.

```
//for testmethod framework interfaces
#include "testmethod.hpp"
//for testmethod API interfaces
#include "mapi.hpp"

using namespace std;

/**
* Used defined TestMethod class must inherit from
* testmethod::TestMethod.
*
* NOTE:
* 1. User should NOT direct access this Object, but instead
* through the TestMethodProxy.
*/
class UserTestMethod: public testmethod::TestMethod
{
  protected:
  double mVoltage;

  protected:
  /**
  * All parameter and other initialization work for TestMethod
  * Class should go here.
  * It will be called just after object construction.
  */
  virtual void initialize()
  {
    addParameter("param1",
                 "double",
                 &mVoltage,
                 testmethod::TM_PARAMETER_INPUT)
    .setDefault("1.0")
    .setOptions("0.0:1.0")
    .setComment("voltage to charge");

    addLimit("leakage");
  };

  /**
  * Define the execution body here.
  */
  virtual void run()
  {
  //recommended approach is to break down the test into three sections:
  // 1. doSetup()
  // 2. doMeasurement()
  // 3. doDatalog()
  return;
  };

  /**
  *This function will be called once the specified
  *parameter's value is changed.
  *@param parameterIdentifier
  *
  *Note: TestMethod API should not be used in this method.
  */
  virtual void postParameterChange(const string& parameterIdentifier)
  {
  //Add your code
    return;
  }
  /**
   *This function will be invoked once the Select Test Method Dialog is opened.
   */
  virtual const string getComment() const
  {
    string comment = " please add your comment for this method.";
    return comment;
  }
};// register the class
REGISTER_TESTMETHOD("UserTestMethod", UserTestMethod);
```
