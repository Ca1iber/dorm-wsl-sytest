# EXECUTE_TEST

This API starts the digital sequencer from the specified start label, then changes the state of the digital sequencer from "BRK" to "RUN". Program execution waits until the digital and analog sequencers stop (except AWG sequencers) or until the specified timeout time. This API can also detect whether digitizers and samplers have received one or more trigger input or not during the execution of this API. For details of this functionality, see [Error Handling on Missing Trigger Input](<02.07.03.16.03_Error_Handling_on_Missing_Trigger_Input.md>).

In order for this API (or an API that internally executes the FLUSH API) to reflect the changes that are specified by ROUTING_STATUS/ANALOG_STATUS to an analog module hardware, the sequencers in all analog modules must be halted. For more information, see the [FLUSH](<02.07.04.01.69_FLUSH.md>) API.

Instead of the EXECUTE_TEST API, use the DIGITAL_CAPTURE_TEST API when executing the test which contains the digital capturing. If you attempt to execute the test containing the digital capturing with the normal EXECUTE_TEST, the test cannot done. For details, see the [DIGITAL_CAPTURE_TEST](<02.07.04.01.35_DIGITAL_CAPTURE_TEST.md>).

The test time is compared to a timeout value. This value can be defined with the timeout parameter. If this parameter is omitted, the default or the value that was last set is used. If the timeout_info parameter is omitted and the test exceeds the timeout value, the test will be aborted and the testsuite will be judged as FAILED. If the timeout_info parameter is set, EXECUTE_TEST() will return timeout information, and the test will continue with the next statement.

In a multi-site test, the reply of the timeout_info parameter depends on whether it is used in combination with the trigger_info parameter. If it is used alone, it will return global timeout information, that is, it will return 1 if a timeout occurred on any site, and 0 otherwise. If both parameters are specified, it will return site specific timeout information.

For the AWG, the timeout time has no effect. If an infinite loop sequence, LOOPI or RPTI, is used for AWG, you can use the ABORT_TEST API to stop the infinite loop of the AWG.

After starting test execution, the EXECUTE_TEST API executes the [FLUSH](<02.07.04.01.69_FLUSH.md>) API internally for reflecting the changes of the setting data by the following APIs to the setup data or hardware:

- ANALOG
- ANALOG_STATUS
- PRIMARY_STATUS
- TIMING_SPEC / LEVEL_SPEC / SPECIFICATION
- ROUTING_STATUS

This API is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/Execute.h.

## Syntax

```
EXECUTE_TEST(DOUBLE timeout = 360000);
EXECUTE_TEST(DOUBLE timeout, INT *timeout_info);
EXECUTE_TEST(DOUBLE timeout, INT *timeout_info, INT *trigger_info);
EXECUTE_TEST(const TM::WAIT_ACTION& wait_action);
EXECUTE_TEST(DOUBLE timeout, const TM::WAIT_ACTION& wait_action);
EXECUTE_TEST(DOUBLE timeout, INT *timeout_info, const TM::WAIT_ACTION& wait_action);
EXECUTE_TEST(DOUBLE timeout, INT *timeout_info, INT *trigger_info, const TM::WAIT_ACTION& wait_action);
EXECUTE_TEST(DOUBLE timeout = 360000, const STRING & context);
EXECUTE_TEST(DOUBLE timeout, INT *timeout_info, const STRING & context);
EXECUTE_TEST(DOUBLE timeout, INT *timeout_info, INT *trigger_info, const STRING & context);
EXECUTE_TEST(const TM::WAIT_ACTION& wait_action, const STRING & context);
EXECUTE_TEST(DOUBLE timeout, const TM::WAIT_ACTION& wait_action, const STRING & context);
EXECUTE_TEST(DOUBLE timeout, INT *timeout_info, const TM::WAIT_ACTION& wait_action, const STRING & context);
EXECUTE_TEST(DOUBLE timeout, INT *timeout_info, INT *trigger_info, const TM::WAIT_ACTION& wait_action, const STRING & context);
EXECUTE_TEST(DOUBLE timeout, ARRAY_I & timeout_sites, INT* trigger_flag); // For 32+ sites
EXECUTE_TEST(DOUBLE timeout, ARRAY_I & timeout_sites, INT* trigger_flag, const STRING& context); // For 32+ sites
```

Parameters

I/O

 |

Parameter

 |

Description / Range

 |
 |

I

 |

timeout

 |

Timeout time of the measurement (test) in sec. The default is 360000 s.

This cannot detect a timeout for the AWGs. Operations when timeout occurs depend on whether the timeout_info or trigger_info parameter is set or omitted.

 |
 |

O

 |

timeout_info

 |

This parameter returns timeout information. It can only be used in combination with the timeout parameter.

The reply of timeout_info depends on whether it is used with or without the trigger_info parameter.

If trigger_info is not specified, timeout_info returns global timeout information. Possible return values are:

0: No timeout occurred on any site.

1: A timeout occurred on one site at least.

If trigger_info is also specified, timeout_info returns site specific timeout information.

In this case, the returned integer must be converted into binary format. Every bit returns the timeout status of one site. Site 1 is represented by the LSB.

For example, if 13 is returned to this parameter, this corresponds to binary number 1101. This indicates that a timeout occurred on sites 1, 3, and 4.

 |
 |

O

 |

trigger_info

 |

This parameter returns site specific information on the trigger status of the digitizers. It can only be used in combination with the timeout_info parameter.

The reply refers to the following digitizers: MCA-ADGT/VDGT, MCB LF/VHF-DGT, and MCC. The state of the module (or MCA/MCB/MCC unit) is checked if a pin is defined and connected to the core.

The parameter informs about which of these digitizers have not been triggered during execution of this API. For more details of this functionality, see [Error Handling on Missing Trigger Input](<02.07.03.16.03_Error_Handling_on_Missing_Trigger_Input.md>).

The returned integer must be converted into binary format. Every bit returns the trigger status of one site. Site 1 is represented by the LSB. The bit states have the following meaning:

0: All the digitizer/sampler modules (and all the MCA/MCB/MCC measure units) on the site have been triggered at least once.

1: At least one digitizer/sampler module (or one MCA/MCB/MCC measure unit) on the site has never been triggered (missed a trigger).

In offline mode, this flag indicates whether the trigger signal input is enabled for all modules (and all the MCA/MCB/MCC units) (0) or not (1).

 |
 |

I

 |

wait_action

 |

This parameter allows you to select which sequencer's completion the API waits for, from the following hardware categories that are represented by the constant variables. It is also valid for combination of them by using "|" (use bitwise OR to select multiple ones).

For example, if you make this API waited until AWGs and digitizers/samplers complete the current sequencer programs, specify TM::WAIT_AWG|TM::WAIT_DGT to this parameter.

Default:

TM::WAIT_DIGITAL| TM::WAIT_DGT| TM::WAIT_TIA

- TM::WAIT_ALL:

waits until all used digital channels, AWGs, digitizers/samplers, and TIAs complete their tasks.

- TM::WAIT_DIGITAL:

waits until all used digital channels complete the current sequencer program.

- TM::WAIT_AWG:

waits until all used AWGs complete the current sequencer programs.

- TM::WAIT_DGT:

waits until all used digitizers and samplers complete the current sequencer programs.

- TM::WAIT_TIA:

waits until all used TIAs complete the current measurements.

 |
 |

I

 |

context

 |

Name of an execution context. The ports of the context must be included in the current start label (which must be a multiport burst). For more information on execution contexts see [Using execution contexts](<../02.06_Command_Reference/02.06.07.01.08.05.03.02.03_Using_execution_contexts.md>) .

The context must have been defined on the firmware level (with the SQEC command), or as a SEQUENCER_CONTEXT_ITEM object. In the latter case this object must have been included in a SEQUENCER_CONTEXT object, and must also have been activated on the firmware level with the apply() function of this SEQUENCER_CONTEXT object. If the context has been defined as a SEQUENCER_CONTEXT_ITEM object, you must use the name specified for its name parameter.

 |

## Examples

### Execute test

```
EXECUTE_TEST();
```

The EXECUTE_TEST API starts test execution. Here, the timeout value that was last set is used because the timeout parameter is omitted.

### Execute test with timeout and timeout information parameters specified

```
EXECUTE_TEST(0.1 sec, &timeout);
```

The timeout time is set to 0.1 sec, and timeout information requested . The timeout time is compared to the time from when the test started. If the test time exceeds the timeout time on any site, EXECUTE_TEST() returns this information to the timeout parameter, then the next statement is performed.

### Execute test with timeout, timeout information and trigger information parameters specified

```
EXECUTE_TEST(0.1 sec, &timeout_s, &mis_trg_s);
```

The timeout parameter is set to 0.1 sec. The timeout is compared from the start time of the test. `timeout_s` receives timeout information for every active site. mis_trg_s receives whether all the connected digitizers except for WDA have been triggered for every site.

See examples in [Error Handling on Missing Trigger Input](<02.07.03.16.03_Error_Handling_on_Missing_Trigger_Input.md>) as a reference for using the trigger_info parameter of this API.
