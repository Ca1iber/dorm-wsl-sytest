# TRANSACTION_SEQUENCE

The transaction sequence class is used to set up a sequence of transactions that is to be executed consecutively without intermediate synchronization. It cannot be instantiated directly, but can only be accessed by the add() and transaction() member functions of the PROTOCOL_TEST class, and the syncTransaction() function of the SYNCHRONIZED_TEST class.

A transaction sequence must contain at least one transaction if no delay is defined for it. But it is allowed to be empty if the delay is > 0. For the definition of a delay see the add(), setDelayTime(), and setDelayCycles() member functions of the PROTOCOL_TEST class.

You can translate a transaction sequence into a counted match loop of the resulting protocol pattern. But this requires that the protocol pattern is not synchronized with a simulation pattern by a marker, and that the sequence contains no capture transactions.

This API is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/TransactionSequence.h.

### getTransaction()

```
TRANSACTION_ITERATOR getTransactions();
```

List of parameters

There are no parameters.

Returns an iterator over all transactions in the sequence.

The returned object can be used to loop through all transactions that were previously added to the protocol test.

Note The iterator will become invalid if the transaction sequence is modified. In this case it will not return any further transactions.

### dump()

```
STRING dump();
```

There are no parameters.

Dumps the transaction sequence to a human readable format. This can be used for data log or debugging purposes.

### setLoop()

```
void setLoop(TM::LOOP_CONDITION condition, INT numLoopIterations);
```

This member function controls whether the respective transaction sequence is translated into a counted match loop withiin the protocol pattern, and defines the maximum number of loop repetitions. Note that a transaction sequence cannot be translated into a counted match loop if it contains capture transactions.

### setLoopDebugMode()

```
void setLoopDebugMode(Boolean loopDebugModeActive);
```

With this member function, you can switch the execution of the resulting match loop into a special debug mode. In standard mode, the match loop cycles are not recorded in the error map (for the 8-vector blocks at the start and end of the match loop see [Adjusting the junctions between match loop and surrounding label](<../02.06_Command_Reference/02.06.07.01.08.04.03.01.01_Adjusting_the_junctions_between_match_loop_and_surrounding_label.md>)). But if the match loop fails, you may want to analyze the errors. To render such an analysis possible, SmarTest provides the option to record the match loop cycles in the error map. If this option is active, the loop will be repeated as often as defined by setLoop().

### getLoopCondition()

```

```

This function returns the current loop mode of the transaction sequence. The function has no parameters. Possible return values are:

 |

 |

The transaction sequence is not converted into a match loop. This is the default.

 |
 |

TM::CONTINUE_ON_PASS

 |

The transaction sequence is converted into a match loop. If the match loop fails, the surrounding test will also be considered as failed.

 |
 |

TM::CONTINUE_ON_FAIL

 |

The transaction sequence is converted into a match loop. If the match loop fails, the surrounding test will nonetheless be continued.

 |

### getNumLoopIterations()

```
INT getNumLoopIterations();
```

This function returns the number of loop repetitions that are set for a translation of the transaction sequence into a match loop. It has no parameters.

### getLoopDebug

```
Boolean getLoopDebugMode();
```

This function returns TRUE if the debug mode for counted match loop translation is active for the respective transaction sequence, and FALSE if debug mode is switched off. It has no parameters.

### getLengthInStateChars()

```
INT getLengthInStateChars();
```

This member function returns the length of the respective transaction sequence in state characters (X-cycles). It presupposes that the protocol pattern has been generated with the flush() member function in the case of a synchronized test, and that the test has been executed in the case of an independent test. The function has no parameters.

### getLengthInCycles()

```
INT getLengthInCycles();
```

This member function returns the length of the respective transaction sequence in tester cycles. It presupposes that the protocol pattern has been generated with the flush() member function in the case of a synchronized test, and that the test has been executed in the case of an independent test. The function has no parameters.

### getLengthInNs()

```
INT getLengthInNs();
```

This member function returns the length of the respective transaction sequence in nano seconds. It presupposes that the protocol pattern has been generated with the flush() member function in the case of a synchronized test, and that the test has been executed in the case of an independent test. The function has no parameters.

## Example

The following example shows how to define a match loop for the protocol pattern. It is assumed that the state map section of the wavetable `prot_wvt` defines an x4-mode for the protocol port:

```
SYNCHRONIZED_TEST ML_test("prot_port","prot_brst","prot_wvt","prot_pat");

  ...

    // Define a named transaction sequence for calling the
    // match loop related member functions of TRANSACTION_SEQUENCE,
    // and define 7 tester cycles to buffer the match loop start:
       TRANSACTION_SEQUENCE & match = ML_test.add(28 /* = 4 * 7 */);
    // Define the match loop body:
       match.add("read").expect("data", "0xD430", "0xFF00");
    // Activate match loop creation and define the maximum number of repetitions:
       match.setLoop(TM::CONTINUE_ON_PASS, 1230);

   ...
```
