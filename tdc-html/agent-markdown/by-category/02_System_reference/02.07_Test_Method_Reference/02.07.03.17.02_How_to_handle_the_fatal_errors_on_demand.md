# How to handle the fatal errors on demand

This section explains the on-occurrence error handling approach.

Assume that you have created your test program without prim error handling and run it, but the program often aborts by a fatal error in a certain API. In a case such as this, you can use the C++ exception mechanisms that uses the try and catch conversion shown below:

```
try {
// API(s) that an error occurs
}

catch (Error & errobj){
// Error Handler Program
}
```

- try:

This block contains the code monitored for API fatal errors. It automatically throws the detected exception (error) to the catch block if a fatal error occurs in the API.

All exceptions derived from the Test Method API always use a class object of the special class Error.

- catch:

This block contains your error handler program for the API to be located in the try block. This block must follow immediately after the try block.

The parameter of the catch function specifies the exception type derived from APIs monitored within the try block. For the parameter, set an object of the special class Error.

With the try-catch convention, if an API fatal error occurs in the try block, program execution immediately jumps to the beginning of the catch block. Then the error handler program in the catch block will be executed, and the program execution goes to the next statement of the catch block. Therefore, the current program execution can be continued even if an error occurs in the API.

If the try block has multiple APIs and program statements, some APIs and program statements may be skipped depending on the location of the API where the fatal error occurred. For example, if a fatal error occurs at the first API, the program execution jumps to the catch block, skipping the rest of the try block. Hence, pay attention to this when you use this error handling approach.

You can also use the [ERROR_EXIT](<02.07.04.01.61_ERROR_EXIT.md>) API to terminate the current testflow or program execution in the catch block. At this time, you can select the desired error handler type similar to that of the SET_EXCEPTION_HANDLER API.

Further, you can use the [STOP_INVOCATION](<02.07.04.01.236_STOP_INVOCATION.md>) API in the catch block. The STOP_INVOCATION API pops up a dialog box. You can select whether to continue or terminate the test method program (the testflow execution is terminated) in the dialog box manually.

For details of these APIs, see the [API Reference](<02.07.04_API_Reference.md>).

The following shows a typical example of the try-catch convention.

```
try
{
    // Disconnect all pins manually
    FW_TASK("SQST OFF;CNCT OFF,(@)\n");
    FW_TASK("CHRS OFF\n");
    FW_TASK("ACMD \"CNCT\",\"OFF\",(@)\n");
    FW_TASK("FLSH MUX\n");
    FW_TASK("WSDN\n");
    FW_TASK("PSST OFF\n");
    FW_TASK("RLYC IDLE,OFF,(@)\n");
}
catch(Error &error)
{
    cout << "Error occurred in FW_TASK!" << endl;
    cout << "Retry the current testsuite!" << endl;
    ERROR_EXIT(TM::RETRY);
}
```

In this example, if a fatal error occurs in the FW_TASK APIs, program execution will jump to the beginning of the catch block. Then, two messages are displayed in the report window. The ERROR_EXIT API sets to retry the current testsuite execution. Hence, program execution returns to the beginning of this program, and this program will be executed again immediately.
