# PATTERN_CONTROLLER

#### Subtopics

- [PATTERN](<02.07.04.01.142.01_PATTERN.md>)

The PATTERN_CONTROLLER API serves to execute DC Scale DC and PPMU BADC tests from within a pattern (for conceptual information see [Executing PPMU tests from a pattern](<02.07.03.02.07_Executing_PPMU_tests_from_a_pattern.md>)). It can be used to execute DC tests in parallel with digital test for different ports, and also to alternate (switch between) digital and DC tests in one pattern run, without the need to stop and start the sequencer before the DC test. The API:

- Downloads measurement sets defined with the PPMU_... and BADC_... APIs
- Inserts instructions (which will execute these sets) into a predefined subpattern
- Executes the current primary sets

The API can also be used to retrieve global pass/fail test results.

The PATTERN_CONTROLLER API calls objects of the PATTERN class. This is a subsidiary data container that holds the measurement data for individual subpatterns.

Note For PPMU BADC tests with digital cards the subpattern must be empty, as the PATTERN_CONTROLLER will dynamically link the measurements defined with test method APIs into the empty subpattern in the order they are added to the PATTERN_CONTROLLER. This link uses internal IDs. Once the measurements are linked into the subpattern, it cannot be stored permanently, as these IDs are dynamically created depending on single test suite execution and complete test flow execution.

This API is defined in the header file /opt/hp93000/soc/prod_com/include/MAPI/PatternController.h.

Note

The typical time required for a BADC or PPMU measurement can be calculated as follows:

 |   | twait = (25 渭s + N * 4 渭s) |
 |   | where:  | 25 渭s is a one-time overhead |
 |   |   | "N" is the number of samples |

After the measurement is performed, SmarTest needs an additional time (typical) of 20 渭s * N, where N is the number of samples, to fetch the results. For this additional duration of time, the BADC cannot be used to perform a new measurement.

In additional, an extra wait time of, at least, 60 渭s must be added for the first BADC measurement after switching the measurement mode on one channel for EXA Scale digital cards or Smart Scale digital cards in Exa Scale compatibility mode.

## Syntax

The general format for setting up a DC subpattern is

```
obj.label().add(dc_task_1).add(dc_task_2)...add(dc_task_n);
```

The general format for downloading or executing a DC subpattern, or retrieving test results, is

```
obj.func();
```

The parameters have the following meaning:

 | obj  | Object of the PATTERN_CONTROLLER class |
 | func()  | Member function of the PATTERN_CONTROLLER class |
 | add()  | Member function of the PATTERN class |

## Member functions

 label(...)

```
PATTERN & label(const STRING& subpattern_name, STRING& port = "@");
```

This member function returns the reference to the [PATTERN](<02.07.04.01.142.01_PATTERN.md>) object holding the DC tasks for the specified label.

Note A call of this function must be followed by calls of member functions of the PATTERN class. You cannot call another member function of the PATTERN_CONTROLLER class after calling label().

Parameters
 | subpattern_name |

The subpattern for which the DC task are to be specified. Note that the subpattern must already exist.

For PPMU BADC tests with digital cards you must use an empty subpattern.

For DC tests with DC Scale DPS cards it can also be a MAIN or SVEC pattern.

 |
 | port  | The port for which the subpattern has been defined. If this parameter is omitted, the default port @ will be assumed.  |  execMode(...)

```
PATTERN_CONTROLLER & execMode(const TM::DCTEST_MODE mode);
PATTERN_CONTROLLER & execMode(const STRING& mode_string);
```

This member function specifies the execution mode for the DC test.

Note It is the execMode() function of the PATTERN_CONTROLLER API that determines the execution mode. The execution mode of the PPMU_MEASURE API is ignored. But it must be specified nonetheless, since otherwise no measurement would be performed.

Parameters
 | mode  | Execution mode. Possible values are: |
 | TM::GPF  | Global PASS/FAIL The test will pass if it passes for all measured pins. This is the default. |
 | TM::PPF  | Per pin PASS/FAIL. With this execution mode, the result can be retrieved for every measured pin. |
 | TM::DCTEST_AUTO |

Executes the DC test according to the test suite flags.

If the flag [Per pin on pass](<../02.08_Setup_and_Result_Tools/02.08.04.32.01.02.07.01_Alphabetical_list_of_flags.md#_342556__row_per_pin_on_pass>) or [Per pin on fail](<../02.08_Setup_and_Result_Tools/02.08.04.32.01.02.07.01_Alphabetical_list_of_flags.md#_342556__row_per_pin_on_fail>) is on, the DC test will executes in the same way as the mode TM::PPF.

If the flag [Per pin on pass](<../02.08_Setup_and_Result_Tools/02.08.04.32.01.02.07.01_Alphabetical_list_of_flags.md#_342556__row_per_pin_on_pass>) and [Per pin on fail](<../02.08_Setup_and_Result_Tools/02.08.04.32.01.02.07.01_Alphabetical_list_of_flags.md#_342556__row_per_pin_on_fail>) are off, the DC test will executes in the same way as the mode TM::GPF.

 |
 | mode_string  | Execution mode, specified as a string. Possible values are: |
 | "GPF"  | Global PASS/FAIL. This is the default. |
 | "PPF"  | Per pin PASS/FAIL |
 | "DCTEST_AUTO"  | Executes the DC test according to the test suite flags. This is the same with the mode TM::DCTEST_AUTO.  |  setup()

```
void setup();
```

This member function serves to download the previously defined DC tasks and to insert the corresponding MEAS instructions into the specified predefined subpattern. If the subpattern already contains any instructions, these are removed.

For performance reasons, the instructions are written into the subpattern only once within one testflow execution; that is, the API will not modify them later on. Therefore, if the same subpattern is used by more than one class object of the PATTERN_CONTROLLER API within one testflow, or if the testflow is executed in a loop, setup() expects that the same measurement sets can be used for the subpattern every time. If this is not the case (because the measurement parameters depend on variables so that they change from one loop repetition to the next, or because they are different for two class objects), it will issue an error message.

setup() can also temporarily modify a previous parameter definition within the same class object. This is exploited for measurement parameters that contain variables. For details, see [Managing DC Tests with Variable Parameters](<02.07.03.02.06.03_Managing_DC_Tests_with_Variable_Parameters.md>).

There are no parameters in this member function.

 execute()

```
void execute();
```

This member function executes the current primary sets. If the actual measurement parameters have not yet been downloaded, and the predefined subpattern is still empty, execute() first calls setup() to download the parameters and insert the MEAS instructions.

There are no parameters in this member function.

 getPassFail(...)

```
Boolean getPassFail() const;
Boolean getPassFail(const STRING & pinlist) const;
```

If no parameter is specified, this member function returns the global PASS/FAIL result of the test.

If a pin list is specified, the function returns a single PASS/FAIL result for these pins. PASS is only returned if all specified pins passed.

Parameter
 | pinlist  | List of pins for which a global result is to be retrieved |

Return value
 | true  | Value for pass result of the measurement. |
 | false  | Value for fail result of the measurement. |

## Important points

- When DC tests are executed with a DC subpattern, you cannot use the PPMU_MEASURE API to retrieve the test results; the execMode() settings of PPMU_MEASURE will be ignored. Instead, you must use the getPassFail member function of the PATTERN_CONTROLLER API or the GET_FUNCTIONAL_RESULT API. Therefore, you cannot retrieve the measured values of the test.
- If a test suite triggers a DC subpattern, and if all PPMU DC sets have been used up, then the PATTERN_CONTROLLER API will throw an error if the DC subpattern needs a new DC set. It does not employ the fall-back mechanism that is used for standard DC tests in this situation (for the fall-back mechanism, see [DC set management](<02.07.03.02.06.01_DC_set_management.md>)).
- The sequencer subpattern into which the PATTERN_CONTROLLER API writes the MEAS instructions cannot be modified with this API after insertion of the MEAS instructions. Therefore you must use the setup() member function, as illustrated in Example, if you want to run a variable dependent DC subpattern in a loop. This ensures that the same measurement sets are used for every loop repetition, and that the DC subpattern need not be changed. For more information see [Managing DC Tests with Variable Parameters](<02.07.03.02.06.03_Managing_DC_Tests_with_Variable_Parameters.md>).
- When the main pattern that calls the DC subpattern contains any vectors after the call, the temporal relations of these vectors to those of the digital ports will not be represented correctly by the Timing Diagram. The reason for this is that the Timing Diagram will display only a small amount of the break vectors that are generated during measurement execution for the pins of the port on which the PPMU test is executed.
- Global pass/fail results can be retrieved, but detail results per pin are not available. Pin results for the Board ADC measurement, for example, must be uploaded using the [DC_RESULT_ACCESSOR](<02.07.04.01.28_DC_RESULT_ACCESSOR.md>) API. Therefore, the execMode() is ignored for [BADC_MEASURE](<02.07.04.01.08_BADC_MEASURE.md>) objects. The pass/fail result of the Board ADC measurement is also part of the global pass/fail result of the functional test.

## Examples

### PPMU IVFM test

In this example, a PPMU IVFM test on the pin `S0` and a PPMU VFIM test on the pin `S1` are performed from the pattern. The subroutine label `DC_Sub_Q0` is used for the execution of DC test.

```
PPMU_SETTING        setting, precharge;
PPMU_RELAY          relay_on, relay_off;
PPMU_MEASURE        meas1;
PPMU_CLAMP          clamp_on, clamp_off;
PATTERN_CONTROLLER  controller;

ON_FIRST_INVOCATION_BEGIN();

    //
    // Setups for PPMU
    //
    setting.pin("S0").iRange(1 mA).min(0 V).max(4.3 V).iForce(10 uA);
    setting.pin("S1").iRange(10 mA).min(-10 uA).max(30 uA).vForce(3.3 V);

    precharge.pin("S0").iRange(20 mA).min(0 mA).max(30 mA) .vForce(2.8 V);

    //
    // Relay setups
    //
    relay_on.pin("S0,S1").status("PPMU_ON");
    relay_on.wait(1.3 ms);
    relay_off.pin("S0,S1").status("AC_ON");

    //
    // Measurement setups
    //
    meas1.pin("S0,S1").execMode(TM::PVAL);

    //
    // Hardware specific programming to avoid hot switching
    // on the Current Force setup
    //
    if(GET_TESTER_CLASS()==TM::PINSCALE)
    {
        clamp_on.pin("S0").status("CLAMP_ON").low(2.6 V).high(2.9 V);
        clamp_off.pin("S1").status("CLAMP_OFF");
    }

    //
    // Set up the controller
    //
    if(GET_TESTER_CLASS()==TM::PINSCALE)
        controller.label("DC_Sub_Q0","Q0_Port").add(setting).add(clamp_on)
              .add(relay_on).add(clamp_off).add(meas1).add(relay_off);
    else
        controller.label("DC_Sub_Q0","Q0_Port").add(precharge)
              .add(relay_on).add(setting).add(meas1).add(relay_off);

    controller.execMode("PPF").execute();

ON_FIRST_INVOCATION_END();

//
// Result upload and datalog
//
TEST("S0", "DC_TEST", controller.getPassFail("S0")?TM::Pass:TM::Fail,TRUE);
TEST("S1", "DC_TEST", controller.getPassFail("S1")?TM::Pass:TM::Fail,TRUE);
```
