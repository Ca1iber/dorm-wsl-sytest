# Device access file syntax

The syntax of the device access file follows the conventions of the [MTL compiler syntax](<02.12.03.02.02_MTL_compiler_syntax.md>).

Specifically, a device access file looks like this:

```
:deviceAccess:
{
[ :version:      <deviceAccessVersion>]
    :deviceParam:  {<deviceParamName>...}
    :groups:
    {
        :format:
        { :name:        :size:    }
        { <pinDefName><pinsNum> }
        { ......       }
    }
[ :subGroups:
    {
        :format:
        { :baseGroup:  :context:      :name:          :bits:     }
        { <groupName><contextName><subgroupName><numBits>  }
        { ............        }
    } ]
[ :constants:
    {
        :format:
        {  :name:           :bits:     :value:         }
        {  <constantName><numBits><int-hexValue>  }
        {  .........             }
    } ]
[ :muxModeDefinition:
    {
        :format:
        {  :pin:        :muxMode:  }
        {  <pin-name>   2 | 4     }
        {  ......        }
    } ]
  :apgAccess:
  {
    :name: <accessName>
    :interface: {  <interfaceParam>... }
    :table:
    {
        :format:
        { [ :instruction: ] :pin:    :states:    :data:  :operation:  :comment:  }
        { [<instrExpr>]<pinId>  {<i0><i1>} <data><op><comment>  }
        { [...]...............       }
    }
...
  }
 :countedMatchPad:
  {
    :name: <paddingName>
    :table:
    {
        :format:
        { :subroutine:       [ :port: ]  }
        { <paddingRoutine>[<port>]  }
        { ...[...]  }
    }
...
  }
}
```

Note The :devCyc: and :stateParam: keywords from older versions of MTL were used for specifying non-transparent x-modes. They are still supported but should not be used any more for new programs; support for them may be removed from a future version of MTL. See the [Non-transparent x-modes](<02.12.03.05.03_Non-transparent_x-modes.md>) appendix for more information.

The order of keywords shown above is typical, but not required; you can rearrange the keywords within a set of curly braces as desired.

Italic text indicates meta-syntax, as described in [Syntax conventions](<02.12.03.01.02_Syntax_conventions.md>).

## Keywords and parameters

These are the keywords and their parameters in alphabetical order:

 |

Keyword

 |

Parameters and descriptions

 |
 |

:apgAccess:

 |

Defines a device access call for use in the [APG program](<02.12.03.03.03_APG_program_file.md>) code.

A device access definition describes a way of accessing a device. Access definitions describe the actions that occur on each pin of the device in order to perform a particular access of the device (for example, read or write).

See the "APG access keywords" table below for details.

 |
 |

:constants:

 |

Defines constants (that is, named values) that can be used in the access definitions.

This section is optional, but it is good practice to store important and often-used parameters in these constants for easier maintenance.

See the "Constants keywords" table below for details.

 |
 |

:deviceAccess:

 |

This keyword is required at the start of the file.

 |
 |

:deviceParam:

 |

<deviceParamName>: The name of a device parameter that is to be used in the device access file.

The parameter must be specified in the [Device architecture file](<02.12.03.03.05_Device_architecture_file.md>). All parameters imported via this keyword can be used like constants in device accesses.

You can specify multiple device parameters; separate them with spaces.

 |
 |

:groups:

 |

Declares groups of pins that have been specified in the [Pin configuration file](<02.12.03.03.09.01_Pin_configuration_file.md>). Once declared, the groups can be used in device accesses.

See the "Groups keywords" table below for details.

The buses that you can configure in the pin mapping file fulfill the same purpose as groups and subgroups and are easier to use. We recommend that you use them and stop using groups. See the configure bus keyword in [Pin mapping file syntax](<02.12.03.03.06.01_Pin_mapping_file_syntax.md>) for details.

 |
 |

:subGroups:

 |

Defines pin subgroups.

Subgroups are subsets of groups (see the :groups: keyword, above) that simplify access in cases when only parts of groups are relevant and let you easily reorder pins.

See the "Subgroup keywords" table below for details.

The buses that you can configure in the pin mapping file fulfill the same purpose as groups and subgroups and are easier to use. We recommend that you use them and stop using groups. See the configure bus keyword in [Pin mapping file syntax](<02.12.03.03.06.01_Pin_mapping_file_syntax.md>) for details.

 |
 |

:version:

 |

<deviceAccessVersion>: Any string describing the version of the device access file.

This keyword is optional.

 |

## APG access keywords

These keywords let you specify device accesses for use in the program file (see :apgAccess:, above):

 |

Keyword

 |

Parameters and descriptions

 |
 |

:interface:

 |

Declares the interface parameter of an APG access so that you can pass values to the APG access when calling it in an [APG program file](<02.12.03.03.03_APG_program_file.md>).

In this row, you put interface parameters into {} and separate each with a space. Values that can be transferred with interface parameters are data, key, and string.

Those parameters will be used in the [macros](<02.12.03.03.04.02_Macros_and_functions_in_device_accesses.md>), [control instructions](<02.12.03.03.04.03_Control_instructions_in_device_accesses.md>), and :states: in this APG access. They can also be declared but not used at all in this APG access.

Note that:

- The :name: keyword of the device access corresponds to a function name in standard C syntax
- The parameters declared in the :interface: keyword correspond to C function parameters.
 |
 |

:name:

 |

The name of the device access by which it is called from the APG program code.

See [Naming rules and conventions](<02.12.03.02.03_Naming_rules_and_conventions.md>) for naming restrictions.

 |
 |

:table:

 |

The data that is sent to the individual pins when the device access is called from the APG program.

See the following table for details.

 |

The :table: element contains these keywords:

 |

Keyword

 |

Parameters and descriptions

 |
 |

:comment:

 |

An optional comment explaining the row.

The comment can be any text.

 |
 |

:data:

 |

A value or expression that determines which of the two values in the :state: column (the left or the right one) is sent to the pins.

:data: may contain:

- A fixed hexadecimal or decimal value. Hexadecimal numbers must be prefixed with `0x` to distinguish them from decimal numbers.
- An expression using predefined operators and parameters whose values are set by the APG program code. (For example, `xAddr(rowAddress)`, `data(0,xAddr)`, `data(0,xAddr,yAddr,zAddr)`.)

Each row of the table:

- Takes the value given in the :data: column or, if it is an expression, evaluates it.
- Maps the resulting bit (`0` or `1`) to the states given in the :states: column, a 0 indicating the left state and a 1, the right.

If the :pin: column contains a pin group, the first bit of the expression result is used to determine the state character for the first pin, the second bit for the second pin, and so on. If there are more bits in the result than there are pins in the group, the excess bits are discarded. For illustration, see Pin groups and the :data: column in the Examples section, below.

For an overview of the operators that you can use in the :data: column, see the description of operators for the APG program file in [Operators](<02.12.03.03.03.01.01_Operators.md>) and the description of data macros in [Macros in device accesses](<02.12.03.03.04.02_Macros_and_functions_in_device_accesses.md>).

Note that the :data: column is ignored in device accesses when the :operation: column comprises the crc macro and CRC is enabled.

 |
 |

:instruction:

 |

The :instruction: column can contain optional control instructions that affect the execution of the statements in the other columns.

For an overview of the statements supported in the :instruction: column, see [Control instructions in device accesses](<02.12.03.03.04.03_Control_instructions_in_device_accesses.md>).

 |
 |

:operation:

 |

The :operation: column contains specifications of [Cyclic redundancy checks](<02.12.03.04.09_Cyclic_redundancy_checks.md>) and [dynamic bus inversions](<02.12.03.04.10_Dynamic_bus_inversion.md>) to apply.

To apply multiple operations, specify them in the desired order and separate them with commas.

This column is optional; if neither cyclic redundancy checks nor dynamic bus inversion is required for an access, it can be omitted.

 |
 |

:pin:

 |

The pins or pin groups involved in the device access.

The pins or pin groups are listed one per row; they must be specified in the [Pin mapping file](<02.12.03.03.06_Pin_mapping_file.md>).

 |
 |

:states:

 |

The single state character from the wavetable. In this column, each row must contain two single state characters surrounded by {}. The two state characters are separated with space. For example, `{0 1}`. When the expression in the :data: column is evaluated to 0, the left of the two characters will be transferred to a pin. When the expression is evaluated to 1, the right one will be transferred to a pin.

You can also use the {} characters to reference the interface parameters of this APG access and transfer different state characters to the pins with the same APG access at different call times. Those interface parameters must have the following attributes:

- Data type must be string.
- String to be transferred with a parameter must be one character. For example, "0".
- Independent of any loop variable in this APG access-called program.

For example,

```
:apgAccess:
  {
    :name:  Write
    :interface: {zero one}
    :table:
    {
       :format:
       { :pin:           :states:           :data:     }
       { DQ              {zero one}          0         }
       { ""              {zero one}          1         }
    }
  }
 
main()
{
  Write("0", "1");
  //Be careful, do not code like Write(0, 1), or Write("01"), both of which are wrong.
}
```

 |

## Constants keywords

These keywords let you specify constants for use in device access (see :constants:, in the topmost table above):

 |

Keyword

 |

Parameters and descriptions

 |
 |

:bits:

 |

The width of the constant in bits.

For example, a constant may be 8 bits wide or 64 bits wide.

 |
 |

:name:

 |

The name of the constant.

The name can be any text that follows the [naming conventions](<02.12.03.02.03_Naming_rules_and_conventions.md>).

 |
 |

:value:

 |

Specifies the value of the constant.

You can enter hexadecimal or decimal values. Hexadecimal numbers must be prefixed with `0x` to distinguish them from decimal numbers. (For values greater than 64 bits, there are [special considerations](<02.12.03.04.15_Expressions_with_more_than_64_bits.md>).)

A constant's value can also be defined as an expression using any of these operators: `+ - * / << >> & | ~`

Comparison operators are not permitted in these expressions.

 |

## Counted match padding keywords

Note Counted match padding is available only in MTP on SOC.

These keywords let you define padding setups that are referenced in the APG pattern file (see :countedMatchPad:, above).

 |

Keyword

 |

Parameters and descriptions

 |
 |

:name:

 |

The name of the padding setup by which it is specified in the APG file.

See [Naming rules and conventions](<02.12.03.02.03_Naming_rules_and_conventions.md>) for naming restrictions.

 |
 |

:table:

 |

The references to padding routines and, optionally, ports to which to apply the padding.

See the following table for details.

 |

The :table: element contains these keywords:

 |

Keyword

 |

Parameters and descriptions

 |
 |

:subroutine:

 |

<paddingRoutine>: The name of a padding routine defined in the [APG program file](<02.12.03.03.03_APG_program_file.md>).

 |
 |

:port:

 |

<port>: The port that the relative padding routine will apply to. This port must be one of those ports in the [pin mapping file](<02.12.03.03.06.01_Pin_mapping_file_syntax.md>) specified by "using port".

If the port column is omitted, the padding routine will apply to all ports. In this case, only one padding routine can be specified in the subroutine column.

One port accepts only one padding routine.

 |

## Groups keywords

These keywords let you define groups of pins (see :groups:, in the topmost table above):

 |

Keyword

 |

Parameters and descriptions

 |
 |

:name:

 |

The name of the group.

The pins of the group must be included in the [Pin mapping file](<02.12.03.03.06_Pin_mapping_file.md>); for example, if the group is named "DQ" and specified as having eight pins, the pin mapping file must define the pins DQ.000 through DQ.007.

If the pin mapping file does not define these pins, pins with these name must be specified in the SmarTest pin configuration file.

If the pins are not found there either, an error results.

 |
 |

:size:

 |

The number of pins in the APG pin group.

Note that pin 0 of the group is the most significant bit.

 |

We recommend that you no longer use groups and instead use buses. See [Buses](<02.12.03.03.06.02_Buses.md>) for more information.

## Subgroup keywords

These keywords let you specify subgroup, that is, subsets of groups that you can address together (see :subGroups:, in the topmost table above):

 |

Keyword

 |

Parameters and descriptions

 |
 |

:baseGroup:

 |

The name of the pin group of which this group is a subset.

The group must be declared in the :groups: section of the device access file.

 |
 |

:bits:

 |

The bits of the group that are to belong to the subgroup, enclosed in square brackets.

Bit specifications can contain ranges as well as lists of pins.

For example: `[0..8,10,12]` which indicates pins 0 through 8, pin 10, and pin 12. The order of the bits is significant, that is `[0,1,2,3]` is a different subgroup from `[3,2,1,0]`.

If a range lists the higher number first, the order of most and least significant bits is reversed: Specifying bits `[15..0]` is an easy way of making bit 0 the least significant bit.

 |
 |

:context:

 |

The context of a APG pin subgroup.

All bits or pins belonging to the same context of a base group must be defined, with each pin belonging to exactly one subgroup. (Each pin must belong to a subgroup, no pin may belong to more than one subgroup.)

If a device access uses one subgroup of a context, it must use all subgroups of that context.

 |
 |

:name:

 |

The name of the subgroup

The name can be any text that follows the [naming conventions](<02.12.03.02.03_Naming_rules_and_conventions.md>). It must be unique per context.

 |

We recommend that you no longer use subgroups and instead use buses. See [Buses](<02.12.03.03.06.02_Buses.md>) for more information.

## Example

### Pin groups and the :data: column

Lets assume these settings for a device access (with `PinGroup` being a properly defined group of four pins):

```
{ :pin:     :states:  :data: }
{ PinGroup  { 0 1 }   0x5    }
{ ~         { 0 1 }   0x5    }
{ ~         { 0 1 }   0x5    }
{ ~         { 0 1 }   0x5    }
```

The pins of PinGroup are then set like this:

- PinGroup.000 is set to 0.
- PinGroup.001 is set to 1.
- PinGroup.002 is set to 0.
- PinGroup.003 is set to 1.

## Functional changes

- Introduced before SmarTest 6.3.2
- MTP 2.4.0: :operation: column added to :apgAccess:
- MTP 2.6.6: :countedMatchPadding: section added
- MTP 3.0.1: Using groups and subgroups no longer recommended
- MTP 3.0.3: (MTP on SOC 103.0.0) :countedMatchPadding: keyword changed to :countedMatchPad:
- MTP 3.3.2: The interface parameter supports the string data type.
- MTP 3.3.2: The string data type interface parameters can be referenced in the :states: column.
- MTP 3.3.2: Adds a limitation to the :port: keyword that the port specified here must be one of the ports that have been specified by "using port" in the pin mapping file.
