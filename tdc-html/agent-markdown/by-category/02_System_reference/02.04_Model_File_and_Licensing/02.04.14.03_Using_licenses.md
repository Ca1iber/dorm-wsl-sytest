# Using licenses

## If not enough licenses are available for a test I initiate because they have already been checked out, what will happen to my test license request?

- If too few, or no licenses, are available to run your test, all the licenses you have requested will be checked back into the server, and will be available for use by any requesting test system.
- An error message will be generated and you will be able to see the current status of your request in the report window. The report window shows how many licenses are needed for test, how many you requested, and how many are not available (unavailable licenses are described as "missing" in the report window).
- Note that a message that indicates that no licenses are available may also indicate a different problem: if a mistaken hostid number has been entered in the license file, the server will not be able to process the request and will return a message that indicates no license is available.

## What is "sharing" licenses? How is it done?

- "Sharing licenses" refers to the aspect of FLEXlm license flexibility that enables you to (1) use the same license on different pins (one use at a time) on the same test head, and (2), on different test heads, located either locally or remotely. In this way you optimize test by using the licenses where they are needed at any time.
- You "share" licenses by following the regular process for assigning licenses and hardware parameters to different channels using the model file. Every time you test a different device which requires different hardware parameters for specific pins, you potentially share a license by reusing it on a different pin.

## Can I add licenses to a license server while test systems are testing devices?

- Yes, you can. In order for each test system to recognize the new licenses, SmarTest must be shut down and restarted. For a full explanation see [Adding licenses](<02.04.06.09.10_Adding_licenses_with_lmreread.md>).

## What are "scalable" licenses?

- "Scalable" licenses allow you to scale the hardware parameters you use for a device. These parameters currently include speed, memory, waveforms, drive edges, receive edges, ppTIA, and the optional use of a differential receiver. Scalability allows you to allocate these features from your server, not only on a pin by pin basis on a card, but as needed on cards across a test system, and on any test system anywhere that is networked to your server. These features are allocated, not by the hardware (which always has a maximum configuration) but by the license server that, for example, allows you to assign 100 pins of 300 Mbps speed to a test system in Tokyo and another 200 pins to a test system in Chicago - from a license pool stored in the same server.

## How do I scale my hardware features?

- You scale hardware features when you define test parameters by editing the model file before loading your DUT. Here you will enter hardware parameters, such as speed and memory, consistent with the installed hardware and the test you have selected.

## Is the break waveform definition taken into account when checking for speed licenses?

- Break waveforms are not considered in the timing module during speed license checks. The timing module counts the drive actions of all "normal" waveforms, but not the break waveforms.
