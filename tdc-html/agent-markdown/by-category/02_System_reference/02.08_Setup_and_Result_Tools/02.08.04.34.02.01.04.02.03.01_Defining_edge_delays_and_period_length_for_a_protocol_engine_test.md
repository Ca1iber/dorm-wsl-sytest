# Defining edge delays and period length for a protocol engine test

The keyword TTMODE marks a pin or pin group as a protocol engine test pin. It defines the x-mode for the protocol engine test and must be specified within the timing set immediately below the PINS statement. Possible x-modes are X4 and X6.

The x-mode of the protocol engine test must be the same for all timing sets of the same equation set for the same pin. Also, if a pin is activated as a protocol engine test pin in one timing set, it must be activated in all timing sets. If these requirements are not satisfied, the configuration found first will be used for all timing sets.

The TTMODE keyword must also be specified in the wavetable. When a wavetable is combined with a timing set in a timing specification, both must specify the same value for this keyword.

In addition, the following special features must be observed:

- Only the first receive edge (r1) is programmable. The other edges are distributed equidistantly within one tester cycle. The distance between two edges will be one UI.

The delay that is defined for r1 will determine the position of the first observation window. For more information see [Positioning the first observation window and jump by 2](<../02.06_Command_Reference/02.06.15.01.01.02_Positioning_the_first_observation_window_and_jump_by_2.md>).

The receive edges also determine the delays for the transition tracking actions (4th action string of native Pin Scale 9G waveforms).

- By default, the first 4 or the first 6 drive edges, depending on the current TTMODE value, are also distributed equidistantly within one tester cycle. But you can override these default values.
- If the protocol engine test is to run in x6-mode, the period length must be 1, 2, 3, or 4 times the clock resolution. The range of the clock resolution on the Pin Scale 9G cards is 0.88 ≤clock_resolution < 1.86 ns. Thus the range for the user period TTMODE_X6_period of an x6 protocol engine test is 0.88 ≤ TTMODE_X6_period < 4 * 1.86 = 7.44 ns.

The clock resolution is calculated as period_resolution / p, where p is an integer (for details see [Period resolution, clock resolution, and master clock period](<../02.06_Command_Reference/02.06.06.01.04.01.02.03_Period_resolution__clock_resolution__and_master_clock_period.md>)). Note that even if user_period < 4 * 1.86 = 7.44 ns, p can be set to an integer > 4. For example, it will be set to 5 if 5 produces an exact result, but no smaller integer does (within the admitted range). In this case a protocol engine test in x6 mode is not possible. However, this problem can only arise if the user period has more than 7 decimal places (up to 9 decimal places are taken into account, and division by 4 requires 2 additional decimal places at most).

## Example

```
TIMINGSET 1 "eq 1 ts 1"
period=150

PINS  IO1
TTMODE X4
r1=22.5
```

If this definition is queried with ETDS?, the answer will be as follows:

```
> ETDS? 101,1,,(IO1)
< ETDS 101,1,,"f1:0 f2:37.5 f3:75 f4:112.5 s1:0 s2:37.5 s3:75 s4:112.5 r1:22.5 r2:60 r3:97.5 r4:135",(IO1)
```
