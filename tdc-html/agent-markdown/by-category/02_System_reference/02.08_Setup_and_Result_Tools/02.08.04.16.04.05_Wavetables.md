# Wavetables

#### Subtopics

- [Function of the base wavetable](<02.08.04.16.04.05.01_Function_of_the_base_wavetable.md>)

A wavetable consists of a series of pins or pin groups; for each of these, a set of physical waveform DC/DC power units are listed (these are sequential integers, starting at zero for each pin or group; in the example below they are listed under `PhyIndex`).

For each index, an action or combination of actions is defined; the actions defined for one index value are referred to collectively as a device cycle.

A name is defined for each device cycle. This name is simply an alias for the physical waveform index and the actions it defines. The device cycle name is not actually stored in vector memory, but it is read from the waveform table and displayed when vectors are shown in Pattern View; this makes the vectors easier to interpret, provided that the names have obvious meanings. The x-mode mapping is implied by the device cycle name, so the number of characters in the name must always match the desired x-mode[1)](<#fntarg_1>).

In this excerpt from a physical waveform table, two values for the drive edge "d1" are provided (in this case the device cycle names happen to be identical to the physical waveform DC/DC power units).

```
PINS input_pins
#       PhyIndex        Action          DevCyc
        0               "d1:0"          0
        1               "d1:1"          1
```

The first waveform drives a DUT input pin low ("d1:0"), and the second drives it high ("d1:1").

For the I/O pins as shown below, five different DC/DC power units are defined, and the device cycle names mostly differ from the waveform DC/DC power units. (Refer to [Physical drive edge action (physical_drive_edge_action)](<02.08.04.34.04.03.02.03_Physical_drive_edge_action__physical_drive_edge_action.md>) for the available drive edge actions in the wavetable.)

PINS io_pins

```
#       PhyIndex        Action          DevCyc
        0               "d1:F00 r1:X"   0
        1               "d1:F10 r1:X"   1
        2               "d1:F0Z r1:L"   L
        3               "d1:F0Z r1:H"   H
        4               "d1:F0Z r1:X"   X
```

- The first waveform drives an input low ("d1:F00"), while ignoring the output ("r1:X").
- The second drives an input high ("d1:F10"), while ignoring the output ("r1:X").
- The third drives an input low and sets tri-state on ("d1:F0Z"), and expects a low output ("r1:L").
- The fourth drives an input low and sets tri-state on ("d1:F0Z"), and expects a high output ("r1:H").
- The fifth drives an input low and sets tri-state on ("d1:F0Z"), and ignores the output ("r1:X").

Because the actions are defined in a way which specifies data values, a vector which refers to this wavetable need not include data parameters; the data is already implicit in each reference to a waveform index.

## Wavetables and vectors

A vector does not actually contain definitions of the waveforms it generates. Instead, a vector contains pointers to definitions in a wavetable. Because there are different types of wavetables, the content of a vector is partly determined by the type of wavetable it points to.

### Types

The definitions in a wavetable are identified by index numbers. The content of a vector, as saved in vector memory, consists of examples of these index numbers, each of which functions as a pointer to an entry in a waveform table. (Some vectors contain other information as well, in the form of data parameters.)

A wavetable has two basic purposes: to define the actions that will occur during execution, and to define the device cycle names that will be displayed in the pattern tool. Both kinds of definition are associated with a particular index number. For example, a wavetable could include the following entry for a given input pin:

 0 "d1:0" zero

In this table entry, the index number "0" is associated with the action definition "d1:0" and the device cycle name "zero". Therefore, during test execution, whenever a vector uses the index number "0" (at least for this pin in this table), the action definition drives a DUT input pin low, and the pattern tool displays the device cycle name "zero". (This is only an example; waveform tables can be configured and used in other ways.)

Because the actions occurring during test execution are defined in the waveform table (not in the vector), the test system cannot execute a vector without referring to an appropriate waveform table. Also, because the device cycle names displayed in the pattern tool are actually defined in the waveform table (not in the vector), the test system cannot correctly display a vector in the pattern tool without referring to an appropriate waveform table.

Normally, the same waveform table is used for both test execution and pattern viewing, but during debugging it is sometimes helpful to set up a separate waveform table for pattern viewing.

### Waveform Tables for Debugging

When the Pattern View is unable to display a device cycle name (because the physical waveform index given by the vector is not defined in the waveform table), a question mark is displayed instead. If the displayed pattern contains a large number of question marks, it may be difficult to determine what the problem is. A question mark does not indicate which index value is being used; it only indicates that the value, whatever it may be, is wrong.

In such a situation, it can be helpful for debugging purposes to use a special-purpose wavetable for pattern viewing only (while continuing to use the normal waveform table for test execution). This debug-view table consists of a list of all possible physical waveform DC/DC power units (from 0 to 1f), each of which is paired with a null definition for the action (" ") and a device cycle name which simply echoes the value of the index. For example:

```
PINS io_pins
#       PhyIndex     Action     DevCyc
        0            " "        0
        1            " "        1
        2            " "        2
        ...          ...        [etc.]
        1f           " "        1f
```

When this table is used for pattern viewing, an index value, rather than a device cycle name or question mark, is displayed for all possible DC/DC power units. This makes it possible to tell from the displayed pattern which index values are actually being called by each vector.

This type of wavetable should be used with care, and only for the limited purpose described above. It should not be used for test execution, because its actions are all defined as null; in other words, the vectors will not do anything. Also, this type of waveform should not be used during examination of a timing diagram, because in that case the diagram display will show nothing but empty graphs.
