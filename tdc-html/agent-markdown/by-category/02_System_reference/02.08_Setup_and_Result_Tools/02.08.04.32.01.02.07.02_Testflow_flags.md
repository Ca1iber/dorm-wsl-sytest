The testflow flags are stored in the `flags` section of the [Testflow file](<02.08.04.32.03.05_Testflow_file.md>).

Testflows are parsed as they are loaded. A warning message is displayed.if an undefined or invalid testflow flag is found.

The following warning messages are displayed in the case of an

- Undefined testflow flag:

```
Testflow flag "<flag_name>" is not defined.
```

- Invalid testflow flag:

```
Warning: Invalid flag statement encountered in testflow file,
in the "flags" section:
The flag "<bad_flag_name>" is not defined.
Use the "user" keyword to define a user flag.
```

## Additional information: check_testmethod_api

When the Check Test Method API flag is set to "on", the software checks the pin name parameter in the TEST API and the PUT_DATALOG API. If the specified pin name parameter is not an existing, defined pin name, a fatal error occurs during runtime. (You can handle an exception error generated by the Check Test Method API feature using the SET_EXCEPTION_HANDLER.)

When the Check Test Method API flag is set to "off" (this is the default), the pin name parameter is not checked in the TEST API or the PUT_DATALOG API. In this case, the user can enter any string for the pin name parameter without a resulting error during runtime.

Data from the Event Data Log that is converted to Standard Test Data Format (STDF) loses the information specified for the pin name parameter in the TEST API and the PUT_DATALOG API if it is not an existing, defined pin name. This makes STDF results analysis impossible. Therefore, the Check Test Method API flag should be set to "on" if Standard Test Data Format (STDF) will be used for test result data analysis.

You can also set this flag using SET_TESTFLOW_FLAG API (test method), or SetTestflowFlag API (CI_CPI). You can determine the current setting of the flag using GET_TESTFLOW_FLAG API (test method), or GetTestflowFlag API (CI_CPI).

 Note The Check Test Method API feature only checks for valid single pin names, not pin groups.

## Additional information: global_hold

Setting this flag allows you to execute the test suites step by step. The test system goes into a hold state whenever a test suite has been executed. A window then lets you select whether to continue or abort the testflow.

   Note We recommend using the single step procedure for testflow debugging, see [Single step testflow debugging](<02.08.04.32.02.04.01_Single_step_testflow_debugging.md>).

When testflow execution is held upon a failed test suite which has the Hold on Fail flag set to on, a window prompts asking for confirmation to continue.

- To continue testflow execution, click Continue.

When executing a multisite testflow with some test suites having this flag set to on, a pop-up window is displayed for each and every site to get confirmation from user to continue. That is to say, user needs to make confirmation for each site of a held test suite. To confirm once and ignore the remaining sites, use Skip instead.

- To abort testflow execution, click Abort.
- To skip the confirmation for the remaining sites in the currently held test suite, click Skip.

## Additional information: test_number_inc

The test_number_inc flag specifies the value by which a test number is incremented when the test is executed in a loop: In the first loop iteration, the test has the number specified for it. The number of the test executed in the second loop is the sum of the first number and the increment. In the next loop iteration, the increment is added to that number, and so on.

This applies to all kinds of loops, whether in test methods or in testflows, and to all ways of setting test numbers.

Example for test_number_inc:

 |   | If test_number_inc is 3, a test that has been assigned the number 14 will have these numbers if it is executed in a loop: |
 | |

- First iteration: 14
- Second iteration: 17
- Third iteration: 20
- Fourth iteration: 23
 |
