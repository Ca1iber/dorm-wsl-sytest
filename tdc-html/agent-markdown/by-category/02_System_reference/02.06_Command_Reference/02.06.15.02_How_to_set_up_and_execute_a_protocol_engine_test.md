# How to set up and execute a protocol engine test

#### Subtopics

- [Combining transition tracking with a PRBS or pattern‑based SmartLoop test](<02.06.15.02.01_Combining_transition_tracking_with_a_PRBS_or_pattern__ased_SmartLoop_tes.md>)

The following describes how to set up, execute, and analyze a protocol engine test on the firmware level.

## About this task

Protocol engine tests serve to cope with non-deterministic behavior of devices (for example, drift or initial latency) when such a behavior is not a sufficient reason to reject the device. See [Overview of the protocol engine per pin](<02.06.15.01_Overview_of_the_protocol_engine_per_pin.md>) for more information.

## Procedure

-  Configure the protocol engine test by defining a transition test set:

  -  Create a transition test set with TTDF.
  -  Define the transition test parameters for the appropriate pins with TTCF.

The parameters can be grouped into

    - transition tracking parameters,
    - pattern matching parameters,
    - error handling.

  -  Optionally, check the consistency of your definition with TTVD.
  -  Make the transition test set the primary such set with TTPR.

Note that the primary transition test set is not automatically executed when you issue FTST?. You must activate it with the keyword TTMODE in the timing setup for the respective pins.

-  Define the timing setup:

The main points that are to be observed when defining a timing setup for a protocol engine test are:

  - The timing setup for a protocol engine test must be coded in native Pin Scale 9G format (see [Defining waveform shapes for Smart Scale pins](<02.06.06.01.03.02_Defining_waveform_shapes_for_Smart_Scale_pins.md>) and [Defining edge delays for Smart Scale pins](<02.06.06.01.04.02.03_Defining_edge_delays_for_Smart_Scale_pins.md>)).
  - The pins for which a protocol engine test is to be executed must be marked with the TTMODE keyword in the wavetable and in all timing sets of the primary timing specification (see [Defining waveforms for a protocol engine test](<02.06.06.01.03.02.01_Defining_waveforms_for_a_protocol_engine_test.md>) and [Defining edge delays and period length for a protocol engine test](<02.06.06.01.04.02.03.01_Defining_edge_delays_and_period_length_for_a_protocol_engine_test.md>)).
  - In certain situations it is desirable to "freeze" the transition tracker, that is, to suppress adjustment of the observation window. This is controlled by the window formatter (which therefore cannot be used for compare actions in a protocol engine test). For more information see [Tracking bi-directional pins](<02.06.15.01.01.04_Tracking_bi-directional_pins.md>).

-  Execute the test with FTST?. Note If the TTMODE keyword is not specified within the primary timing specification, FTST? will ignore all transition test settings.

If you want to execute a protocol engine test for a pair of differential pins, configure the test for both pins in the same way. Note that only the positive connection of the pair will be considered in the test, and that consequently results will be returned only for the positive connection.

## Results

FTST? will return a global P/F result. The outcome also depends on the error handling defined with TTCF.

## What to do next

If you want to check the details of the test execution, issue the TTDB? and/or TTST? queries.
