# DFTD, DFTD? (DeFine Test Data)

The DFTD command is a generic command which serves to download or upload a collection of event based test data coded in XML. The elements of the collection have a certain type, which is defined within the XML code. Currently, two such types are supported, namely DC sets and (only for Smart Scale) DC waveforms. The DFTD? query returns selected test data elements.

With this command you configure setups of those sites that have the setup focus: For more information, see also: [PSFC, PSFC?](<02.06.02.02.191_PSFC__PSFC__-__Parallel_Setup_FoCus.md>).

With this command you can retrieve site specific information (only one site can be in focus at a time). For the site in focus, SmarTest displays results in the Testflow Editor and in the result tools. Also, any firmware queries report setup and results for the site currently in focus only.

## Predependencies

The DFTD command is based on XML (eXtended Markup Language). Only the ISO-8859-1 character encoding is supported.

## Mode of operation

DC sets and DC waveforms are intended for different channel types. DC sets only work with DC Scale channels, DC waveforms can only be defined for digital channels. Thus, DC sets and DC waveforms cannot be mixed within the same collection.

DC sets and DC waveforms are both executed from within a pattern. With DC sets, the connection between the test data collection and the respective pattern is established by the [TPSE](<02.06.02.02.268_TPSE__TPSE__-__Test_Point_SEquence.md>) command. The DC set collection is associated by DFTD with a freely definable name. This name is passed on to the TPSE command, which connects the collection to a pattern and specifies the vector addresses at which the individual DC sets are to be processed (for an example, see the TPSE command). With DC waveform collections, the respective pattern (which must be of type SVEC) is already identified by DFTD, and the vector addresses at which the DC waveforms are to be executed are defined by the sequencer instruction [XACT](<../02.08_Setup_and_Result_Tools/02.08.04.16.02.06.10.02_Sequencer_instructions.md#_99880__row_XACT>) (see example 3 below).

The XML code of a test data collection must have the following general structure:

```
<?xml version="1.0"?>
<testdata>
    <td id="name1" type="type">
        <operation1 attribute11="value11" attribute12="value12"
            ... />
        <operation2 attribute21="value21" attribute22="value22"
            ... />
        ...
    </td>
    <td id="name2" type="type">
    ...
    </td>
    ...
</testdata>
```

DFTD associates every <testdata>` ...` </testdata> collection with a name. In the case of a DC set collection, this name is freely definable. It serves to identify the collection to the [TPSE](<02.06.02.02.268_TPSE__TPSE__-__Test_Point_SEquence.md>) command. In the case of a DC waveform collection, the name must specify the SVEC pattern which is to execute the DC waveforms.

The td elements are also called test events. Every td element within a testdata collection must have a different value for its id attribute. The type of a td element determines which operation elements it may contain. Operation elements cannot be combined arbitrarily; the allowed combinations for DC sets are listed below. All this is verified by DFTD.

Feature restrictions of DC sets that are due to hardware limitations (for example, a measurement range not supported by the hardware) will be reported in the context where the test data is referenced (for example, TPSE). Functional restrictions (for example, a conflict between the parameters of a td operation and the level setup) will be reported by [FTST?](<02.06.02.02.127_FTST__-__Functional_TeST.md>).

Feature restrictions of DC waveforms that are due to hardware limitations (for instance, a wrong vector distance), will be reported by the DFTD. Functional restrictions (for example, inconsistencies between DFTD setup data and the pins of the subpattern port), will be reported by FTST?.

For the query, td elements are divided into categories. A category corresponds to a setup component. Currently the only supported category is LEV, which corresponds to the level setup. Accordingly, test point data changes within the LEV category are reflected by the LEV flag of an [UPTD?](<02.06.02.02.306_UPTD__UPTD__-__UP_To_Date.md>) status query.

## Postdependencies

DC sets can be referenced within a test point sequence defined by [TPSE](<02.06.02.02.268_TPSE__TPSE__-__Test_Point_SEquence.md>) in order to apply the settings of the element within a sequencer pattern. DC waveforms can be referenced for the same purpose with the XACT sequencer instruction within the subpattern with which the respective testdata collection is associated. You can also change existing elements with DFTD (see the edit_mode parameter).

Any test event data that was defined with DFTD will be removed by [*RST](<02.06.02.02.345_RST_-__ReSeT.md>).

If you want to integrate the test event data into your setup, you can insert the DFTD commands at the end of the level setup file. This is also where the commands are stored if you edit the test elements in the pattern debug tool. If you split up the level setup with the setup management tool, the DFTD instances will be put into a separate subfile (for details see [Level setup master file](<../02.08_Setup_and_Result_Tools/02.08.04.14.02.05_Level_setup_master_file.md>)).

## Parameters

 | testdata_name |

A mandatory name that identifies a collection of test data elements (td).

If the collection contains DC sets, the name is freely definable. Note that all test data elements that are to be used with one label (as defined with the TPSE command) must belong to the same collection.

If the collection contains DC waveforms, the name must be the name of the sub-pattern by which the DC waveforms are to be executed.

 |   | ALL  | Returns all test data collections (only in the query).  | |
 | edit_mode |

The mandatory parameter specifies the editing mode for the test data elements.

 |   | REPLACE  | Replaces all existing td elements with the new definitions. |
 |   | UPDATE |

Modifies operation elements of existing td elements, or adds new operation elements to an existing td element.

Note the UPDATE mode is restricted for DC waveforms: their vectorDistance attribute, and also the number of values of their values attribute cannot be modified.

 |
 |   | INSERT |

Defines additional td elements. Existing td elements remain unchanged.

 |
 |   | DELETE  | Removes all specified td elements.  |  The DFTD? query responds with UPDATE if an element_id was specified, otherwise it responds with REPLACE. |
 | pinlist |

The mandatory parameter defines the pin or pins on which this command is applied. To specify multiple pins, separate the names with a comma, or use @ to specify all pins. You can also use pin groups.

If the collection contains DC sets, only pins that are associated with DC Scale channels are taken into account.

If the collection contains DC waveforms all pins must be digital pins. If this requirement is not satisfied, DFTD will issue an error message. Furthermore, the specified pins must be exactly the pins that belong to the port of the sub-pattern specified as testdata_name.

 |
 | category |

The mandatory parameter is for queries only. The admitted values are:

 |   | ALL  | returns all elements of all categories. |
 |   | LEV  | returns all elements of all types within the LEV category. The possible types are dcset and dcWaveform.  | |
 | element_id |

The mandatory parameter selects a test data element that is to be returned by the query. This parameter does not occur in the command because it corresponds to the id attribute of the td element (see the #spec(data) parameter).

 |
 | ALL |

Returns all test data elements of the specified collection.

 |
 | #spec(data) |

The binary data stream that contains the test data. The general format is:

#Nn1n2...nNdata_stream

where the digit N defines the number of the digits ni (1 = i = N) that specify the length of data_stream in bytes.

The format of the data stream itself depends on the edit mode:

- For edit mode DELETE, the td elements of the testdata collection must not contain any operation elements.
- For all other edit modes, the td elements should contain one or more operation elements.

Currently, two types of td elements are supported, dcset and dcWaveform.

## Down-ranging

The down-ranging mechanism for PMU current measurements is applied under the following conditions:

- setForceRange event: Sets the combined force / measure range.
- setMeasureRange event:

  - Current measurement: Set the target range for downrange; start down ranging immediately.
  - Voltage measurement: Set the combined force / measure range.

- measure event: Start measurement immediately.
- restoreMeasureRange event: Restores the current range to the range of the static setup or - if executed - to the last current range executed by setForceRange (type=current).

## Examples

### Example 1

```
# For pin vdd, define dc test data:
DFTD "DCTasks",REPLACE,(vdd),#3237<?xml version="1.0"?>
<testdata>
 <td id="0" type="dcset">
 <setMeasureRange type="voltage" minValue="0" maxValue="3"/>
 </td>
 <td id="1" type="dcset">
 <measure type="current" failOnLowClamp="true" failOnHighClamp="true"/>
 </td>
</testdata>
```

### Example 2

```
DFTD "DCTasks",REPLACE,(vdd),#3233<?xml version="1.0"?>
<testdata>
 <td id="maxVoltage" type="dcset">
 <setForceValue type="voltage" value="LEV:maxVoltage"/>
 </td>
 <td id="derivedVoltage" type="dcset">
 <setForceValue type="voltage" value="LEV:derivedVoltage"/>
</td>
</testdata>
```

This example shows how base and derived variables can be referenced within a test event. A test in which this setForceValue element is executed must be run with a primary level equation set where these variables are declared, for example:

```
EQNSET 1 "level1"
 SPECS
 maxVoltage [V]
 EQUATIONS
 derivedVoltage = maxVoltage/2
 ...
```

### Example 3

The following example shows a test data collection of DC waveforms, and how an element of this collection is referenced in a SVEC pattern:

```
DFTD "dcSubLabel",INSERT,(pmuPort),#9000000352<?xml version="1.0"?>
<testdata>
<td id="force1V" type="dcWaveform">
<setForceWaveform type="voltage" vectorDistance = "16" iRange="0.01" values="0,0.5,1"/>
</td>
<td id="force0V" type="dcWaveform">
<setForceWaveform type="voltage" vectorDistance = "16" iRange="0.01"
values="1,0.75,0.5,0.25,0"/>
</td>
</testdata>

SQLB "dcSubLabel",SVEC,0,2,"functional_MP",(pmuPort)
...
SQPG 0,STVA,,0,SM,(pmuPort)
SQPG 1,XACT,,"force1V",SM,(pmuPort) # execute ramp to force 1V
SQPG 2,RSUB,,,,(pmuPort)
```

The subpattern named `dcSubLabel` executes the first of the two DC waveforms that are contained in the test data collection of the same name.
