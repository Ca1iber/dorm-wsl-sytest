# TPSE, TPSE? - (Test Point SEquence)

The TPSE command serves to define and modify a test point sequence for channels with test point capability like DPS128. The TPSE? query returns the current definition of a selected or all test point sequences.

With this command you configure setups of those sites that have the setup focus: For more information, see also: [PSFC, PSFC?](<02.06.02.02.191_PSFC__PSFC__-__Parallel_Setup_FoCus.md>).

With this command you can retrieve site specific information (only one site can be in focus at a time). For the site in focus, SmarTest displays results in the Testflow Editor and in the result tools. Also, any firmware queries report setup and results for the site currently in focus only.

## Terminology

A test point connects a test event (td element defined with [DFTD](<02.06.02.02.68_DFTD__DFTD___DeFine_Test_Data.md>)) with a logical vector of a pattern. Test events are instructions to the hardware to perform some action, for example, set the measurement range for a DC measurement or execute such a measurement. These actions can be executed synchronously with digital vectors. In fact, test point sequences are the counterpart of digital vectors for channels with test point capability (however, vector download with [VECD](<02.06.02.02.325_VECD__VECD__-__VECtor_Download.md>) or [VECC](<02.06.02.02.324_VECC__VECC__-__VECtor_download_Compressed.md>) is not allowed for such channels).

## Predependencies

The overall number of usable test points for all patterns must be defined per pin in the .technology file (testpoints keyword) or the Device settings editor; the default is 0. The test point data collection specified in the testdata_name parameter of TSPE, which contains the data for the sequence, must have been defined with [DFTD](<02.06.02.02.68_DFTD__DFTD___DeFine_Test_Data.md>) for all pins wth test point capability that are specified in the pinlist parameter of TSPE.

The TPSE command is based on XML (eXtended Markup Language). Only the ISO-8859-1 character encoding is supported.

## Mode of operation

Every test point sequence is associated with a pattern. The sequence attaches test events defined with the DFTD command to vectors of this pattern. When a functional test is run with the pattern, the test event is executed at the specified vector. All test events within one test point sequence must belong to the same test data collection, the name of which is specified in the TPSE call.

Only one test point sequence can be defined for any combination of pin and pattern. It is not necessary to define a test point sequence for every pin with test point capability. If no such sequence is defined, hold vectors are generated for every cycle that is executed by the sequencer. Cycles that are not needed to communicate data to the hardware are also filled with hold vectors.

Partial save in the Pattern Debug tool is supported, that is, only the TPSE commands of the selected patterns will be stored in the new vector setup file. Changes of the test point sequence are reflected in the VEC flag of [UPTD?](<02.06.02.02.306_UPTD__UPTD__-__UP_To_Date.md>) status query.

The definition of the test point sequence is coded as an XML string. The XML data must have the following general structure:

```
<?xml version="1.0"?>
  <sequence>
    <tp anchor="vector_nr_1" td="td_1">
    <tp anchor="vector_nr_2" td="td_2">
    . . .
    <tp anchor="vector_nr_n" td="td_n">
  </sequence>
```

Every test point (tp element) has two attributes. The anchor attribute defines the vector to which the test point is attached, the td attribute points to the test event. For details see the description of the #spec(test_points) parameter.

## Postdependencies

If you want to integrate the test point data into your setup, you can insert the TPSE commands at the end of the vector setup file. This is also where the commands are stored if you edit the test points in the pattern debug tool.

## TPSE

```
TPSE {testdata_name}, {label_type}, {label_name}, {edit_mode}, {(pinlist)}, [#spec(test_points)]
```

## TPSE?

```
TPSE? {label_type}, {label_name}, [anchor_number],{(pinlist)}
```

returns:

```
TPSE {testdata_name}, {label_type}, {label_name}, REPLACE, {(pinlist)}, [#spec(test_points)]
```

## Parameters

 |

testdata_name

 |

Specifies the test data collection from which the test events are to be selected. The collection must have been defined with [DFTD](<02.06.02.02.68_DFTD__DFTD___DeFine_Test_Data.md>).

 |
 |

labelType

 |

The following types are supported:

 |
 |

 |

MAIN

 |

requires a label name defined with [SQLB](<02.06.02.02.236_SQLB__SQLB__-__SeQuencer_LaBel_definition.md>).

 |
 |

 |

SVEC

 |

requires a label name defined with SQLB.

 |
 |

 |

PPSQ

 |

Per pin subroutine defined with [DPPS](<02.06.02.02.81_DPPS__DPPS__-__Define_Per_Pin_Subroutine_label.md>). This type is only used for memory tests. You should not define a test point sequence for a per pin subroutine manually. Note also that the anchor of a per pin subroutine is an address, not a vector number.

 |
 |

 |

ALL

 |

reports the test points of all label types (query only).

 |
 |

label_name

 |

The name of the pattern to which the test point sequence belongs.

 |
 |

 |

ALL

 |

returns the test points of all labels (query only)

 |
 |

edit_mode

 |

Possible modes are:

- REPLACE: All existing test point definitions are replaced with the new definitions.
- UPDATE: Existing test points can be modified, that is, you can associate a different test event with the given vector position. You cannot add new test points or remove existing ones.
- INSERT: Additional test points can be defined. The existing setups are unchanged. Existing test points cannot be replaced.
- DELETE: All specified test points are removed. If a group does no longer contain a test point, it will be removed as well.

The TPSE? query always responds with REPLACE mode.

 |
 |

anchor_number

 |

Selects a single test point for the query. In the command, the anchor numbers are specified within the XML code (anchor attribute of the tp element).

 |
 |

pinlist

 |

Only pins with test point capability (DC Scale DPS32 and VI32 pins) are considered.

 |
 |

#spec(test_points)

 |

The binary data stream that contains the test points. The general format is:

`#`Nn1n2n...nNdata_stream

where the digit N defines the number of the digits ni (1 鈮?i鈮?N) that specify the length of data_stream in bytes.

The general format of the XML string is explained above. The two attributes of the tp element must take the following values:

 |
 |

 |

anchor

 |

The value of this attribute must be a logical vector number of the specified pattern. This is the vector at which the test point becomes active. At least 32 vectors must be generated before the first anchor and between any two anchors. These vectors are needed to download data to the hardware.

 |
 |

 |

td

 |

The value of this attribute must be the identifier of a td element in the test data block specified with the testdata_name parameter.

 |

## Application

DC Dynamic

## Example

This example sets up a test label that generates a ramp of 4 samples on pin `vdd` in the default port.

```
DFTD "ramp_events",REPLACE,(vdd),#3628<?xml version="1.0"?>
<testdata>
  <td id="init" type="dcset">
    <setMeasureRange type="voltage" minValue="0" maxValue="3.0"/>
  </td>
  <td id="1" type="dcset">
    <setForceValue type="voltage" value="0.0"/>
  </td>
  <td id="2" type="dcset">
    <setForceValue type="voltage" value="0.5"/>
  </td>
  <td id="3" type="dcset">
    <setForceValue type="voltage" value="1.0"/>
    <measure    type="current" samples="4"/>
  </td>
  <td id="4" type="dcset">
    <setForceValue type="voltage" value="1.5"/>
  </td>
</testdata>

SQLB "ramp4",SVEC,0,3,"wavetable",(@)
. . .
SQPG 0,STVA,0,,,(@)
SQPG 1,STSA,,,,(@)
SQPG 2,GENV,512,,,(@)
SQPG 3,STOP,,,,(@)

TPSE "ramp_events",SVEC,"ramp4",REPLACE,(vdd),#3226<?xml version="1.0"?>
<sequence>
  <tp anchor="64" td="init"/>
    <tp anchor="120" td="1"/>
    <tp anchor="200" td="2"/>
    <tp anchor="300" td="3"/>
    <tp anchor="400" td="4"/>
</sequence>
```
