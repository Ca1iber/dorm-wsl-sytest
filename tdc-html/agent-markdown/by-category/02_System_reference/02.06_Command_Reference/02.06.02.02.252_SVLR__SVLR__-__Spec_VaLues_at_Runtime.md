# SVLR, SVLR? - (Spec VaLues at Runtime)

The SVLR command sets a base (spec) variable to the supplied value and recalculates the timing or levels. The value must be within the minimum and maximum range specified in the given spec set. The new values are activated at the start of the next functional test. Note that SVLR does not change the setup value of the spec variable. The previous modifications are reset to the setup values when you make a new one.

The SVLR? query either returns the current runtime values of one or more base or derived (spec or equation) variables, or the associations between variables and equation sets.

CAUTION Never mix the LEVEL_SPEC or TIMING_SPEC API and firmware commands modifying values for other reasons than debugging purposes (see note below)! LEVEL_SPEC and TIMING_SPEC test method APIs cache values in order to enable the .restore() functionality. This caching is not available on the firmware level. In both cases, changing spec values takes effect without changing the level or timing file! If you want to change spec values permanently you must do so in the corresponding setup file itself.Note For debug purpose only: If you want to change the spec value while the application model is running without having to abort the execution, you can pause the application model, change the spec value with the firmware command [SVLR](<02.06.02.02.252_SVLR__SVLR__-__Spec_VaLues_at_Runtime.md>) directly from hpt and then resume the running of the application model.Note The SVLR command does not set the Test Program Explorer out of date, but it sets the status bit 10 of the affected spec set. The status bits can be queried with the SPST? query.

With this command you configure setups of those sites that have the setup focus: For more information, see also: [PSFC, PSFC?](<02.06.02.02.191_PSFC__PSFC__-__Parallel_Setup_FoCus.md>).

With this command you can retrieve site specific information (only one site can be in focus at a time). For the site in focus, SmarTest displays results in the Testflow Editor and in the result tools. Also, any firmware queries report setup and results for the site currently in focus only.

## For single-port specifications

- SVLR

```
SVLR {spec_type}, {equation_set_no}, {specset_no}, {"spec_name"}, {value} [,(pinlist)]
```

- SVLR?

SVLR? {spec_type}, {equation_set_no}, [specset_no], {"spec_or_equ_name"} [,MAX|MIN|UNIT]

```
SVLR? {spec_type}, {equation_set_no}, [specset_no], {ALL|EQUA|MAX|MIN|SPEC|UNIT}
```

Both query types return:

```
SVLR {spec_type}, {equation_set_no}, [specset_no], {"spec_or_equ_name"}, [value]
```

## For multiport specifications

- SVLR

```
SVLR {spec_type},, {"multi-port_spec"}, {"spec_name"|"spec_name@port_name"}, {value} [,(pinlist)]
```

- SVLR?

```
SVLR? {spec_type},, {"multi-port_spec"}, {"spec_or_equ_name"|"spec_or_equ_name@port_name"} [,MAX|MIN|UNIT]
SVLR?{spec_type},, {"multi-port_spec"}, {ALL|EQUA|MAX|MIN|SPEC|UNIT}
```

Both query types return:

```
SVLR {spec_type},, {"multi-port_spec"}, {"spec_or_equ_name"|"spec_or_equ_name@port_name"}, [value]
```

## For both types of specifications

- SVLR

```
SVLR {spec_type},PRM,, {"spec_name"|"spec_name@port_name"}, {value} [,(pinlist)]
```

- SVLR?

```
SVLR? {spec_type},{ALL|PRM},[ALL|specset_no], {"spec_or_equ_name"|"spec_or_equ_name@port_name"} [,MAX|MIN|UNIT]
SVLR? {spec_type},{ALL|PRM},[ALL|specset_no], {ALL|EQUA|MAX|MIN|SPEC|UNIT}
```

Both query types return:

```
SVLR {spec_type},[equation_set_no], ["multi-port_spec"|specset_no], {"spec_or_equ_name"|"spec_or_equ_name@port_name"}, [value]
```

## Parameters

 |

spec_type

 |

Which specification type to use. Use:

 |
 |

LEV

 |

to specify levels, or

 |
 |

TIM

 |

to specify timing.

 |
 |

equation_set_no

 |

Equation set number. An integer in the range 1 to 99.

Use PRM to specify the primary equation set, or, in a multi-port setup, the primary specification as defined with SPRM. In this case, the specset_no parameter is ignored.

In the query, use ALL to display all equation sets.

This parameter must be omitted if a multi-port specification is specified for the thirdparameter.

 |
 |

specset_no

 |

Specset number. An integer in the range of 1 to 99. In the query, use ALL to select all defined specsets.

If specset_no is not set, and equation_set_no is set to ALL or a number, only the spec names in the specified equation sets, but no values are returned.

 |
 |

multi-port_spec

 |

In a multi-port setup, enter the name of a specification instead of a spec set number. In this case, the secondparameter must be left empty.

 |
 |

spec_name

 |

The name of a base (spec) variable. In a multi-port setup, the same variable name can occur among the spec variables of more than one port within the same specification. In this case, you can qualify the variable name by a port name in the following format

<spec_name>@<port_name>,

if you want to modify the variable on that port only.

Note, however, that the scope of the variable will be set to local for the port in question after such a modification (even if it is set to global in the setup), until the setup is downloaded again.

Note also that in a multi-port setup, you cannot change the value of a variable globally (that is, without specifying a port) unless at least one of the variable instances has its scope set to global in the setup. For basic information on the local and global scope of spec variables in a multi-port setup see [Global and local scope of base variables](<02.06.06.01.05.03.01_Global_and_local_scope_of_base_variables.md>).

 |
 |

spec_or_equ_name

 |

The name of a base (spec) or derived (equation) variable. An equation variable cannot be specified in the command or in a query which uses the extra parameter.

 |
 |

ALL

 |

Requires that the actual values of both base and derived variables are returned.

 |
 |

EQUA

 |

Requires that the actual values of only the derived (equation) variables are returned.

 |
 |

MAX

 |

Requires that the maximum values of all the base (spec) variables are returned.

This keyword can also be specified as an extra parameter in combination with the spec_name parameter to retrieve only the maximum value of the specified spec variable.

 |
 |

MIN

 |

Requires that the maximum of all the base (spec) variables are returned.

This keyword can also be specified as an extra parameter in combination with the spec_name parameter to retrieve only the minimum value of the specified spec variable.

 |
 |

SPEC

 |

Requires that the actual values of only the base (spec) variables are returned.

 |
 |

UNIT

 |

Requires that the units of all the base (spec) variables are returned.

This keyword can also be specified as an extra parameter in combination with the spec_name parameter to retrieve only the unit of the specified spec variable.

 |
 |

value

 |

Float with 5 possible decimal places.

 |
 |

pinlist

 |

By this extra parameter, you can modify the runtime definitions for an individual pin. Note that you cannot retrieve the pin specific values with SVLR?.

 Note You can use the pinlist parameter to modify the value of a spec variable of an individual pin, temporarily. If you make a new modification on a different spec variable, only the last modification is kept while the previous spec variable is reset to the setup value defined in the spec file. To make a permanent modification on a spec variable, specify all pins (that is, @) as the pinlist. Otherwise, to change the value of a spec variable of an individual pin permanently, you have to use a specset for each pin and modify the spec variable in that specset. |

## Application

- The assign value node in the testflow.Note Each site in a multisite environment can set its own value.

## Errors

An error is generated if:

- The spec does not exist.
- The change to the spec's value results in violations of range, limit, etc.

## Examples

### Example 1

The following example queries the values of the spec variable f in a setup where both single-port and multi-port specifications occur:

```
> SVLR? TIM,ALL,ALL,"f"
< SVLR TIM,,"spec_p_1_p_2","f@p_1",35
< SVLR TIM,,"spec_p_1_p_2","f@p_2",33
< SVLR TIM,1,1,"f",37
```

### Example 2

The next example queries in which equation sets the spec variable f occurs:

```
> SVLR? TIM,ALL,,"f"
< SVLR TIM,1,,"f",
< SVLR TIM,2,,"f",
```

### Example 3

For this example assume that the primary timing is a multi-port specification which contains the two ports p_1 and p_2, and that p_1 and p_2 share the spec variable f in this specification. Assume further that f has been set to scope global for the port p_1. Now query the current value of f for p_1, change it globally, and query it again:

```
> SVLR? TIM,PRM,,"f@p_1"
< SVLR TIM,,"spec_p_1_p_2","f@p_1",33
> SVLR TIM,PRM,,"f",43
> SVLR? TIM,PRM,,"f@p_1"
< SVLR TIM,,"spec_p_1_p_2","f@p_1",43
```

Since f is global for p_1, its value has been modified. Now change the value a second time, but this time locally, and then try to change it globally again:

```
> SVLR TIM,PRM,,"f@p_1",53
> SVLR TIM,PRM,,"f",43
> SVLR? TIM,PRM,,"f@p_1"
< SVLR TIM,,"spec_p_1_p_2","f@p_1",53
```

The second global command has no effect because f has only local scope after issuing the local command.
